🎯 Why Priority Scheduling Exists

Not all processes matter equally

The real-world requirement

A desktop has the compositor that draws your mouse at 60 fps, a music player that must deliver audio frames on time, and a background backup job that can wait. Treating them all equally (plain RR) makes the mouse lag when the backup hogs CPU.

The solution

Assign each process a priority value. The scheduler always picks the highest-priority READY process. Higher number (or lower number, depending on convention) means it runs first.

Priority vs. nice

On Linux, normal processes use nice values from −20 (highest priority) to +19 (lowest). Real-time tasks use a separate RT priority range 1–99. The kernel combines both into a single scheduling hierarchy.

💡
Priority is a lever: system administrators use it to guarantee audio doesn't skip, admins use it to protect the shell from runaway builds, and real-time OSes use it to guarantee deadlines.
Priority spectrum
HIGH Real-time audio · GUI compositor RT 1–99
MED Interactive apps · user shell nice −5 to +5
LOW Background backup · compile nice +10 to +19

Priority lets the kernel express the difference between "must run now" and "whenever there's spare time".

🏥 Analogy 1 · The Hospital Emergency Room

Triage: the sickest go first

The setup

An ER waiting room. Patients arrive with different severities. A triage nurse assigns a priority level: critical (bleeding out), urgent (fractured bone), moderate (high fever), minor (sprained ankle).

The rule

When a doctor frees up, they call the highest-priority waiting patient. This is priority scheduling — the same logic your CPU uses to guarantee the GUI stays responsive.

Why it works

If a critical patient arrives while the doctor is treating a minor injury, the doctor preempts the minor case to save the critical one. That's preemptive priority scheduling.

🏥 Analogy 1 · The Starvation Problem

If criticals keep arriving, the minor case never gets seen

The scenario

Every few minutes a critical patient arrives. The doctor always picks them first — correctly. But Dave's sprained ankle sits in the lobby for three consecutive days, never getting called. This is starvation.

Why it's a real problem

In an OS, this translates to a background process that never runs because the system is perpetually busy with higher-priority work. Your compile job never finishes because the browser is constantly at high priority.

Not a bug — a policy consequence

The scheduler is doing exactly what it was told. The problem is that the policy doesn't bootstrap fairness — some tasks may never run. This is why aging exists.

🏥 Analogy 1 · The Aging Fix

Boost a patient's priority the longer they wait

The rule

The triage nurse uses aging: every hour a patient sits in the waiting room, their effective priority is boosted slightly. Dave's sprained ankle is "minor" at hour 0, but after 8 hours it becomes "urgent" — after 24 hours, "critical".

Why it works

Eventually, any starving process's priority catches up to the fresh arrivals. It gets scheduled, finishes, and the starvation loop is broken. The wait is bounded — not eliminated, but guaranteed to end.

The cost

Aging partially defeats strict priority's efficiency. Higher-priority fresh tasks are no longer always run first. But on a general-purpose system, bounded starvation is far more important than optimal throughput.

💡
The formula: effective_priority = base_priority + (wait_time × aging_rate). At rate 1, every second of wait adds 1 to the effective priority.

📖 Priority Scheduling — The Formal Algorithm

Same as SJF, but the comparison key is priority

Non-preemptive priority

When the CPU is free, pick the READY process with the highest priority. Run it to completion. No interruption. Simple. Still suffers starvation and convoy-style issues.

⚠ Starvation · convoy

Preemptive priority

When a new process arrives with a higher priority than the running one, immediately preempt. Otherwise let the running one continue. This is what most RTOSes and Linux RT tasks do.

⚠ Context switch cost

The starvation problem

Any process with a lower priority than the freshest arrival may never run if high-priority arrivals are continuous. This is worse than SJF's starvation because priority is often static.

The aging fix

Periodically boost the priority of every waiting process. Over time, the priority gap closes and starvation is bounded. Costs scheduling optimality, gains fairness.

⚠️ Starvation — The Full Anatomy

Why some processes never get to run

Formal definition

A scheduling defect where a process remains indefinitely delayed inside the ready state because higher-priority tasks keep seizing control.

How it manifests

1. A background backup process is set to low priority
2. User activity constantly generates high-priority tasks
3. The backup never gets a turn
4. It sits in READY for hours or days

Why it's a real problem

Not just "the job is late". If that backup is a log shipper, a watchdog, or a health check, the system's correctness depends on it eventually running. Starvation breaks system invariants, not just performance.

♿
Micro-Accessibility Context: On Unix, nice +19 is the lowest priority a normal process can have. Kernel watchdog processes are often RT priority 99 — not because they need to run often, but because when they do need to run, they must not be starved.

📈 Aging — The Mitigation

The fix that turns infinite wait into bounded wait

The rule

Every time the scheduler wakes up, increment the effective priority of every process in the READY queue by a small amount. Processes that have waited a long time eventually out-prioritize even fresh arrivals.

The formula

effective_priority = base_priority + (wait_time / aging_factor)

Example: factor = 1000 ms. After 1 s wait, +1. After 10 s, +10.

The cost

Aging breaks strict priority optimality. A low-priority task that has aged enough will preempt a fresh high-priority one. Throughput can decrease slightly, but fairness is guaranteed.

Practical numbers

Linux uses aging-like mechanisms in CFS (via vruntime). RT scheduling is not aged — RT tasks never starve each other because they have bounded execution windows. Aging matters most in best-effort scheduling.

🏗️ Multi-Level Feedback Queue — The Modern Scheduler

Combine multiple priority queues with dynamic migration

The insight

Static priority has a fatal flaw: it requires knowing the process's behavior in advance. But we don't know if a process will run for 1 ms or 1 hour. MLFQ learns the behavior by observing the process.

The structure

Multiple queues (typically 3–8), each with a different priority and a different quantum. Higher-priority queues get tiny quanta. Lower-priority queues get longer quanta. New processes enter at the top.

The learning mechanism

If a process uses its entire quantum without blocking → it's CPU-bound → demote to a lower-priority queue. If it blocks before the quantum → it's I/O-bound or interactive → keep it high.

💡
MLFQ is the closest thing to a universal scheduler. It doesn't require predicting burst times, it handles both CPU-bound and interactive workloads well, and — with aging — it prevents starvation.

⚙️ MLFQ Mechanics — Promotion, Demotion, Quantum

Three rules that make MLFQ self-tuning

Rule 1 · Priority order

If Priority(A) > Priority(B), A runs. Only within the same queue does RR apply. Q0 always beats Q1, always beats Q2.

Rule 2 · Demotion

If a process uses its entire quantum without yielding, its priority is reduced one level. CPU-bound tasks naturally sink to the bottom.

Rule 3 · Aging/priority boost

Periodically (e.g., every 100 ms), move every process back to Q0. This breaks starvation and prevents gaming — a task that sinks to Q2 gets a chance again.

Optional · Promotion

Some MLFQs promote a process one level if it blocks before using half its quantum. Rewards I/O-bound behavior with faster access to CPU next time.

💡
Why aging matters here too: without Rule 3, a long-running CPU job would sink to Q2 and stay there — potentially starved by continuous short arrivals in Q0. The periodic boost fixes this, matching what we covered for plain priority aging.

Step 1 · Initial arrival

A new process arrives and enters Q0 with the 8-ms quantum. All new processes get top priority.

Step 2 · Quantum expires

The process uses the full 8 ms without yielding (it's CPU-bound). Kernel demotes it to Q1 with the 16-ms quantum.

Step 3 · Another expiry

It burns the full 16 ms too. Demoted to Q2 with the 32-ms quantum. Now it runs in long bursts, minimizing scheduler overhead.

Step 4 · Periodic boost

Every 100 ms (or similar), all processes go back to Q0. Even our CPU-bound task gets a fresh chance to compete at high priority.

🎮 MLFQ — The Gaming Problem

A clever process can cheat the reward system

The vulnerability

Rule 2 says: "If the process blocks before using its full quantum, keep it at high priority." A malicious process can exploit this by deliberately yielding at 90% of its quantum — never losing priority, but still consuming almost all CPU time.

Why it breaks fairness

Legitimate interactive tasks (mouse, keyboard) yield quickly. The malicious process mimics them — keeping itself in Q0 while actually consuming the CPU. Other processes get squeezed out.

The fix — cumulative accounting

Instead of per-slice tracking, the kernel tracks the process's cumulative CPU time at each level. Even if the process yields, once its total time at Q0 exceeds a threshold, it's demoted.

♿
Micro-Accessibility Context: Real kernels implement this with a "vruntime budget" — each process can accumulate only so much high-priority execution before being forced down. Linux's CFS is essentially a continuous version of this idea.

🔄 Priority Inversion — The Architectural Trap

Where a low-priority task blocks a high-priority one

The setup

Three tasks: TH (high priority), TM (medium), TL (low). TL acquires a shared lock (say, for a file). TH wakes up and needs that same lock — but it's held by TL. TH must wait.

The inversion

While TH is waiting, TM becomes ready. TM is higher priority than TL but doesn't need the lock. The scheduler correctly runs TM. But now TL can't run to release the lock, so TH can't run either.

The result

TH — the highest-priority task — is effectively blocked by TM — a medium task that has nothing to do with TH's lock. Priority has been inverted. The low-priority TL is "carried" by the medium TM, and the high-priority TH is starved.

💡
Why this is catastrophic in real-time systems: a deadline could be missed. On a general-purpose OS, it just makes things slow. On a spacecraft, it causes system resets. Which brings us to the next slide...

🚀 Real Case — The Mars Pathfinder Glitch (1997)

Priority inversion almost killed a Mars rover

The scenario

NASA's Pathfinder lander used VxWorks RTOS. The bc_sched task (medium priority) ran a communication bus. The ASI/MET task (high priority) handled critical sensor data. A low-priority task held a mutex that ASI/MET needed.

The failure

The low-priority task held the mutex. ASI/MET (high) waited. bc_sched (medium) preempted the low task. The low task never released the mutex. ASI/MET never ran. The watchdog timer saw the stall and rebooted the spacecraft.

The fix on Mars

NASA engineers remotely enabled priority inheritance on the mutex. This instantly fixed the inversion. The fix was so important it was later added to many RTOSes as the default mutex behavior.

💡
The lesson: priority inversion isn't a theoretical curiosity. It caused real hardware to reboot on another planet. Every RTOS engineer knows this story.

🔧 Priority Inheritance — The Fix

The low task temporarily becomes high priority

The rule

When a high-priority task TH blocks on a lock held by low-priority TL, the kernel temporarily boosts TL's priority to match TH's. Now TL can preempt TM, run, release the lock, and let TH proceed.

The mechanics

1. TH tries to acquire lock L held by TL
2. Kernel detects the inversion risk
3. TL inherits TH's priority
4. TL preempts TM, finishes critical section
5. TL releases L, returns to original priority
6. TH runs at its proper high priority

The cost

Priority inheritance requires tracking priority chains (in case of nested locks) and can be expensive. But it's far cheaper than a missed deadline in RT systems.

♿
Micro-Accessibility Context: In POSIX, mutexes created with PTHREAD_PRIO_INHERIT automatically use priority inheritance. Without this flag, the mutex is vulnerable to inversion. Linux supports this via the PI-futex mechanism.

🔧 Alternative — Priority Ceiling Protocol

A different fix: boost the lock, not the task

The rule

Every lock has a priority ceiling — the priority of the highest task that could ever acquire it. When a task acquires the lock, its priority is immediately boosted to the lock's ceiling, whether or not a high task is currently waiting.

What this prevents

The inversion scenario can't happen because TL is already at max priority while it holds the lock. TM can never preempt TL. TH can never be blocked behind TM.

Inheritance vs. Ceiling

Inheritance reacts — boosts only when the inversion risk appears. Ceiling prevents — boosts proactively. Ceiling is simpler to analyze for worst-case timing, but can overshoot priority for short critical sections.

💡
Which to use? Priority inheritance is more common in general OSes (Linux uses it). Priority ceiling is common in hard RTOSes where worst-case timing must be provable. Both solve the same underlying problem.

💻 Code — Priority Scheduler with Aging

The aging formula, in C

aging_scheduler.c
// Simplified priority scheduler with agingtypedef struct {    int pid;    int base_priority;   // static priority (0-99)    long wait_time;     // ms since last run    enum {READY, RUNNING, DONE} state;} task_t;#define AGING_FACTOR 1000  // 1 priority point per second waitingint effective_priority(task_t *t) {    int boost = t->wait_time / AGING_FACTOR;    int prio = t->base_priority + boost;    return prio > 99 ? 99 : prio;  // clamp}task_t* pick_next(task_t *tasks, int n) {    task_t *best = NULL;    for (int i = 0; i < n; i++) {        if (tasks[i].state != READY) continue;        if (!best ||            effective_priority(&tasks[i]) >            effective_priority(best))            best = &tasks[i];    }    return best;}
The key idea

The effective_priority function computes a task's current priority from its base priority plus whatever boost it's earned by waiting.

Why AGING_FACTOR = 1000

One priority point per second waited. After 10 seconds, a low-priority task gains +10 — enough to beat most medium-priority tasks. This is a real-world tuned constant.

The clamp

prio > 99 ? 99 : prio prevents overflow when a task waits for hours. Real kernels use similar bounds.

The performance cost

pick_next is now O(n) — must call effective_priority for each task. Real kernels use heaps/red-black trees keyed on effective priority to get O(log n).

💻 Code — Priority Inheritance in Action

The mutex boosts the holder

pi_mutex.c
// Simplified priority-inheritance mutextypedef struct {    task_t *owner;    int locked;    int original_priority;  // to restore later} pi_mutex_t;void pi_acquire(pi_mutex_t *m, task_t *caller) {    if (!m->locked) {        m->locked = 1;        m->owner = caller;        m->original_priority = caller->base_priority;        return;    }    // Lock is held. If caller is higher priority,    // boost the owner so it can finish faster    if (caller->base_priority > m->owner->base_priority) {        m->owner->base_priority = caller->base_priority;    }    block_caller(caller);}void pi_release(pi_mutex_t *m) {    m->owner->base_priority = m->original_priority;    m->locked = 0;    m->owner = NULL;}
The core mechanic

When a higher-priority task tries to acquire a held lock, the current owner's priority is boosted in place. The owner immediately becomes as high-priority as the waiter.

The restore step

On release, the owner's original priority is restored. This must be tracked carefully — if a task holds multiple locks with different boosters, only the maximum boost applies at any moment.

The real complexity

In production code, you need to handle: nested locks (A holds L1, blocks on L2 → chain of boosts), multiple waiters on the same lock, and boost chains of length > 2. This is why PI mutexes are tricky to implement correctly.

Why Linux uses PI-futex

Modern Linux implements this in the kernel with PI-futex — a fast userspace futex with kernel-assisted priority inheritance when contention occurs. Userspace handles the fast path; the kernel handles the inversion-prone slow path.

🏷️ System Lexicon — MLFQ & Inversion
MLFQ
Term 03 of 04
Formal Definition

Multi-Level Feedback Queue — an adaptive CPU scheduling architecture that shifts tasks dynamically between historical execution runtime rows.

Plain Translation

( Multiple priority queues where processes migrate based on how they behave — CPU hogs sink, interactive tasks rise. )

The mechanism

Full quantum used → demote. Blocked early → stay high. Periodic boost → everyone returns to top.

Priority Inversion
Term 04 of 04
Formal Definition

An operational trap where a low-priority thread holding a resource indirectly delays a high-priority thread due to an intermediate medium-priority thread preempting the resource holder.

Plain Translation

( The high-priority task is stuck behind the low one — and the medium task is in the way of both. )

The fix

Priority inheritance (boost the low task temporarily) or priority ceiling (pre-boost the holder).

🌍 Real World — Linux's Priority Machinery

What's actually in a modern kernel

Two scheduling classes

CFS (Completely Fair Scheduler) for normal tasks — uses vruntime, red-black tree, dynamic quanta. RT (Real-Time) for RT tasks — strict priority 1–99, always preempts CFS.

Priority translation

Userspace sees nice values −20 to +19. The kernel translates these to weights (see set_load_weight()). RT tasks bypass this entirely and use raw RT priority.

Priority inheritance in Linux

RT-mutexes support PI via PI-futex. Userspace pthread mutexes can enable it with PTHREAD_PRIO_INHERIT. The kernel tracks boost chains and adjusts priorities dynamically.

💡
What this means practically: if you write an RT task that acquires a lock shared with a non-RT task, you MUST use a PI mutex or you risk the Mars Pathfinder bug happening on your system. Same physics, different planet.

🏆 Grand Summary — L08 Key Takeaways

Four things to walk out with

01

Priority scheduling is necessary for real systems — but naive priority causes starvation. The fix is aging: boost a process's priority the longer it waits.

02

MLFQ dynamically classifies processes by observing their behavior. Interactive tasks stay in high queues. CPU hogs sink to low queues. Periodic boosts prevent starvation.

03

Priority inversion is the trap where a low-priority lock holder blocks a high-priority task while a medium task runs. It caused the Mars Pathfinder to reboot — nearly a mission failure.

04

Priority inheritance (boost the holder) and priority ceiling (pre-boost the lock holder) are the two canonical fixes. Use PI mutexes for any lock shared between real-time and non-real-time tasks.
