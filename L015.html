The Core Question of L15

L14 gave us mutexes to protect shared state. But what happens when a program needs multiple locks at once? The very tool that prevents races introduces a new failure mode — one where everything is blocked and nothing can proceed.

🎯 The Core Problem — When Mutexes Fight Each Other

Preventing races can create deadlock

The trap

L14 said "wrap shared state in a mutex." But if a thread needs to update two shared variables, it must hold two locks. If another thread grabs them in the opposite order, both block forever. Each waits for the other.

Why this is catastrophic

The system doesn't crash. It doesn't throw an error. It just... stops. Two threads are now permanently blocked, holding resources nobody else can use. If those threads are the only ones that can free those resources, the entire system is frozen.

The requirement

We need a way to reason about concurrency that catches this failure mode — and a strategy to prevent it. That's what this lecture delivers: the four conditions that must be true for deadlock, and how to break any one of them.

💡
The stakes: deadlock isn't a theoretical concern. Real production incidents involve deadlocked databases, frozen audio servers, and systems that need to be force-rebooted because no thread can make progress.
The canonical two-thread deadlock
🍽️ Analogy 1 · The Dining Philosophers Dilemma

Five philosophers. Five forks. Everyone starves.

The setup

Five philosophers sit around a circular dinner table with exactly five forks total, placed between them. To eat a bowl of noodles, a philosopher must pick up both their left fork and their right fork.

The failure

All five philosophers reach out and grab their left fork at the exact same millisecond (Hold and Wait). Now everyone holds one fork, and nobody can grab their second because the neighbor holds it (No Preemption). Everyone sits frozen staring at their food forever.

The fix

Break the loop condition (Circular Wait) by forcing just one philosopher to grab their right fork first instead. The lock cycle is shattered, and progress resumes.

💡
The whole lecture in one image: shared resources (forks) + multiple acquisitions (two per philosopher) + no preemption = potential deadlock. Every strategy in this lecture is a variation on "how do we prevent this exact scenario?"

Circular Wait — philosopher N waits for a fork held by philosopher N+1

Why "politeness" doesn't help

Even if every philosopher is perfectly well-behaved — no one grabs a fork out of turn, everyone follows the rules — deadlock still occurs. The problem is the rules themselves, not the behavior.

A locks row 1, wants row 2. B locks row 2, wants row 1. Neither can proceed.

The setup

A classic banking deadlock: two transactions transferring money in opposite directions. Each locks the source row, then tries to lock the destination row — which is held by the other transaction.

The parallel to L14

This is the two-mutex deadlock from slide 2, dressed in banking clothes. Same pattern: acquire A → acquire B in one thread, acquire B → acquire A in another. The circular wait is the culprit.

The fix

Enforce a global lock ordering: always acquire row 1 before row 2, regardless of transfer direction. Both transactions now compete for row 1 first — one wins, one waits. The winner completes, releases, the loser proceeds.

💡
This is how real databases work: lock ordering is enforced at the storage engine level. Every transaction that touches multiple rows must acquire them in a consistent order (typically by row ID).

📖 Core Breakdown — What Is a Deadlock?

A set of processes permanently blocked

Formal definition

A deadlock is a critical gridlock error state where multiple competing threads are paralyzed permanently while waiting for a closed loop of dependencies to clear. Every thread in the set is waiting for a resource held by another thread in the same set.

Key characteristics

Permanent — no thread can break the cycle
Silent — no error, no crash, just frozen
Total — every thread in the cycle is stuck
Unrecoverable — from the program's perspective

What "unrecoverable" means

The kernel doesn't detect this — as far as it's concerned, the threads are just blocked waiting for a mutex. The kernel happily schedules other runnable threads. It's the application that's frozen, not the whole system — unless all threads are in the cycle.

💡
The tricky part: a deadlock is a bug in your logic, not a bug in the OS. The kernel just follows instructions. Preventing deadlock is the programmer's responsibility — which is why knowing the four conditions matters.
The essential picture
📖 Core Breakdown — The Resource Allocation Graph

Graph the cycles. Find the deadlock.

The model

A Resource Allocation Graph has two node types and two edge types:

◯ circle = process
▢ square = resource
→ (solid) = process holds resource
→ (dashed) = process waits for resource

The rule

A cycle in the graph means deadlock is possible. If every resource has only one instance (mutexes typically do), a cycle means deadlock is guaranteed — the threads will remain frozen forever.

Why this matters

Drawing the graph by hand for a real program is impractical, but the mental model is invaluable. When you suspect deadlock, ask: "Can I trace a cycle of waits?" If yes, that's the bug.

💡
Automated detection: the kernel can maintain this graph and periodically check for cycles. Linux's lockdep does exactly this (see slide 23).

📖 The Four Coffman Conditions

All four must hold. Break any one — no deadlock.

The mathematical requirement

The Coffman Conditions are the definitive mathematical requirements that must all hold true simultaneously for a deadlock to manifest. If even one fails, deadlock is impossible.

Why this is powerful

Instead of trying to prove your code is deadlock-free (impossible in general), you can prove that one specific condition can never hold. That's a much more tractable problem, and it's how real systems prevent deadlocks.

The order in the name

Edward Coffman identified these in 1971. The order matters only historically — they're a set. The next four slides cover each one.

💡

📖 Coffman 1 — Mutual Exclusion

A resource that only one can hold

The condition
The condition

Mutual Exclusion: at least one resource must be held in a non-shareable mode. Only one process can use it at a time. The mutex you studied in L14 is exactly this — a lock that one thread holds at a time.

Can we break it?

Rarely. Some resources genuinely can't be shared — a printer can only print one job at a time. But some can: read-only files, immutable data, atomic counters. Breaking this condition means redesigning the resource to be shareable — which isn't always possible.

The practical takeaway

This is the hardest condition to break. Most deadlock prevention focuses on the other three. Accept mutual exclusion as a given and design around it.

📖 Coffman 2 — Hold and Wait

Holding one, waiting for another

The condition

A process must be holding at least one resource while waiting to acquire additional resources held by other processes. This is the "I'm not done, but I need more" situation.

Can we break it?

Yes — with a trade-off. Two strategies:
1. Acquire all at once: request every lock at the start. If any is unavailable, release everything and retry.
2. Release before wait: release all held locks before acquiring new ones.

The cost

Both strategies reduce resource utilization — you hold locks you don't need yet (blocking others) or release and re-acquire (losing progress). The classic tradeoff: less deadlock, less parallelism.

💡
Practical example: database transactions that need to update 10 rows could acquire all 10 locks upfront (safe but slow) or update one row at a time (fast but deadlock-prone). Most databases choose a middle ground: acquire in a consistent order.
Hold and wait in action
📖 Coffman 3 — No Preemption

Resources can't be forcibly taken

The condition

No Preemption: resources cannot be forcibly taken from a process. They must be released voluntarily by the holder. If T1 holds lock A, no one can just "snatch" it — T1 must call unlock.

Can we break it?

Sometimes. If a process requests a resource that's unavailable, we can preempt — forcibly release all resources it currently holds, forcing it to restart. This is what happens when you kill a process that holds locks (the locks get released).

The cost

Preemption means losing work. If a thread is midway through a multi-step transaction and gets preempted, its partial changes may need to be rolled back. This is fine for databases (which have transaction rollback), but disastrous for many other kinds of code.

♿
Micro-Accessibility Context: most mutexes are non-preemptible by design — that's the whole point. Some specialized locks (like read-write locks) allow preemption of readers, but the general case is: if you hold it, you hold it until you release.
The preemption dilemma
📖 Coffman 4 — Circular Wait

A closed loop of "you first"

The condition

A closed ring of processes exists such that each process waits for a resource held by the next process in the loop. Thread A waits for B's lock, B waits for C's, C waits for A's — the ring closes and everyone is stuck.

Can we break it?

Yes — and this is the most practical fix. Impose a global ordering on all locks. Every thread must acquire them in ascending order (e.g., by lock ID). A circular wait becomes mathematically impossible — you can't have A<B and B<A.

The discipline

If you need lock B (ID 2), you must have already acquired lock A (ID 1). If you hold lock A and need lock C, that's fine (1<3). If you hold lock C and need lock A — not allowed. Release C, re-acquire A, then C.

💡
Real-world usage: the Linux kernel uses strict lock ordering. Filesystem code acquires locks in a documented order; breaking the order triggers a lockdep warning (see slide 23). This is the single most effective anti-deadlock strategy.
Breaking the circle
📖 The Key Insight — All Four Must Hold

Remove any one — deadlock is impossible

The logical structure

The four Coffman conditions form a necessary and sufficient set: deadlock happens if and only if all four hold. This means we don't need to prevent all four — preventing just one is enough to prevent deadlock entirely.

Which one to break?

Mutual Exclusion — rarely possible (resources genuinely shared)
Hold and Wait — possible but costly (reduces utilization)
No Preemption — possible but loses work
Circular Wait — easiest and most common choice

Why circular wait wins

Lock ordering is a design-time, zero-runtime-cost fix. Just establish a total order over locks and enforce it. No extra API calls, no lost work, no reduced utilization. It requires discipline, not machinery.

💡
The pattern: most concurrency problems have a "cheap fix" (discipline) and an "expensive fix" (runtime mechanism). Lock ordering is the cheap fix for deadlock — it wins because it's essentially free.
Break any one — deadlock is gone

HOLD+WAIT Acquire all upfront or release before wait — possible but reduces parallelism ⚠️
NO-PREEMPT Allow forced release — loses work, only viable with transactions ⚠️

📖 Prevention · Avoidance · Detection

Three philosophies for handling deadlock

✓ Prevention

Design the system so that one Coffman condition cannot hold. Lock ordering is the classic example. Deadlock is impossible by construction.

COST: RESTRICTIVE · EASY TO VERIFY

⚠ Avoidance

Before granting a lock request, check whether granting it would lead to an unsafe state. Banker's algorithm is the canonical example. Deadlock is impossible but some allocations are denied even when safe.

COST: MODERATE · NEEDS ADVANCE INFO

🔍 Detection & Recovery

Allow deadlock to occur, then periodically check for it (build the graph, look for cycles) and recover (kill a thread, preempt a resource). Linux lockdep is a runtime approximation.

COST: REACTIVE · RECOVERY IS DISRUPTIVE
What production systems do

Combination: prevention (lock ordering) + detection (lockdep-style tooling) as a safety net. Avoidance (banker's) is mostly academic — it requires knowing future requests, which real workloads don't provide.

The practical reality

Most real deadlocks are bugs, not architectural problems. A developer violated lock ordering. A refactor changed the acquisition sequence. Detection catches these; prevention prevents these.

What you're seeing

Thread 1 acquires lock A, sleeps briefly, then tries to acquire lock B. Thread 2 acquires lock B, sleeps briefly, then tries to acquire lock A. The sleeps are deliberate — they ensure both threads grab their first lock before trying for the second.

The freeze

After both threads have made their first acquisition, both reach for the second. Neither can proceed. The process hangs — pthread_join never returns, the shell prompt never reappears.

The fix (slide 19)

Same code, but both threads acquire locks in the same order (A then B). No cycle. No deadlock. Correct behavior restored by ordering discipline alone.

💻 Code — The Deadlock-Prone Version

Two threads. Two mutexes. Opposite order.

deadlock_demo.c
#include <pthread.h>#include <unistd.h>pthread_mutex_t lock_A = PTHREAD_MUTEX_INITIALIZER;pthread_mutex_t lock_B = PTHREAD_MUTEX_INITIALIZER;void* thread_one_routine(void* arg) {    pthread_mutex_lock(&lock_A);   // T1 locks A    sleep(1);                      // let T2 lock B    pthread_mutex_lock(&lock_B);   // T1 blocks on B    pthread_mutex_unlock(&lock_B);    pthread_mutex_unlock(&lock_A);    return NULL;}void* thread_two_routine(void* arg) {    pthread_mutex_lock(&lock_B);   // T2 locks B    sleep(1);                      // let T1 lock A    pthread_mutex_lock(&lock_A);   // T2 blocks on A    pthread_mutex_unlock(&lock_A);    pthread_mutex_unlock(&lock_B);    return NULL;}
The exact problem

T1 acquires A, sleeps. T2 acquires B, sleeps. Both wake up. T1 tries to acquire B — held by T2. T2 tries to acquire A — held by T1. Circular wait. Both block. Deadlock.

Why the sleep is critical

Without the sleep, the deadlock might not manifest on every run — one thread might finish before the other starts. The sleep is a deliberate synchronization that forces the interleaving. In real code, this timing happens naturally, unpredictably.

Note the order

T1: A → B. T2: B → A. Opposite orders. That's the bug. Lock ordering would fix this — see the next slide.

💻 Code — The Fixed Version

Same locks. Same order. No deadlock.

no_deadlock.c
// Both threads acquire in the SAME order: A then B#include <pthread.h>#include <unistd.h>pthread_mutex_t lock_A = PTHREAD_MUTEX_INITIALIZER;pthread_mutex_t lock_B = PTHREAD_MUTEX_INITIALIZER;void* thread_one_routine(void* arg) {    pthread_mutex_lock(&lock_A);   // 1st    pthread_mutex_lock(&lock_B);   // 2nd    // ... critical work ...    pthread_mutex_unlock(&lock_B);    pthread_mutex_unlock(&lock_A);    return NULL;}void* thread_two_routine(void* arg) {    pthread_mutex_lock(&lock_A);   // SAME order — 1st    pthread_mutex_lock(&lock_B);   // SAME order — 2nd    // ... critical work ...    pthread_mutex_unlock(&lock_B);    pthread_mutex_unlock(&lock_A);    return NULL;}
What changed

Thread 2 now acquires lock_A first, then lock_B — matching Thread 1's order. Both threads compete for A first. One wins, one waits. The winner proceeds to B, completes, releases both. The waiter now acquires A, then B, completes.

Why no sleep is needed

Even without the sleep, even with any interleaving, the ordering prevents the deadlock. The lock ordering is a structural guarantee — it doesn't depend on timing.

The cost

Almost zero. Threads now serialize slightly more on lock A (since both need it first), but there's no deadlock. The tradeoff — a tiny bit of contention — is essentially free compared to a frozen program.

Counter = number of permits available. wait() takes one, signal() returns one.

Formal definition

A semaphore is an advanced signaling synchronization variable that maintains an internal integer counter to manage thread traffic access caps. Two operations: wait() (decrement) and signal() (increment).

The counting semantics

When a thread calls wait() and the counter is 0, it blocks. Otherwise, it decrements and proceeds. When a thread calls signal(), it increments the counter — potentially waking a waiting thread.

Binary vs counting

Binary semaphore — counter is 0 or 1. Functionally equivalent to a mutex (though not identical in ownership rules).
Counting semaphore — counter can be any non-negative integer. Used to limit concurrency (e.g., "allow 3 database connections at a time").

📖 Semaphores & Deadlock

Same conditions apply — different primitive

The insight

Deadlock isn't a property of a specific primitive. It's a property of the pattern of acquisition. You can build a deadlock out of mutexes, semaphores, spinlocks, or anything else — the Coffman conditions apply uniformly.

The famous example

Dijkstra's classic: two semaphores S1=1, S2=1. Thread A does wait(S1); wait(S2);. Thread B does wait(S2); wait(S1);. Same deadlock as two mutexes.

The fix

Same as before: order the waits. Both threads wait(S1) first, then wait(S2). Or use a single semaphore initialized to 1 (equivalent to a mutex) — which solves the ordering problem trivially.

💡
Why this matters: beginners often think "semaphores are safer than mutexes." They aren't — they're just a different tool with different semantics. The Coffman conditions don't care which primitive you use.

🌍 Real World — Linux lockdep

The kernel's runtime deadlock detector

What lockdep does

The Linux kernel has a runtime deadlock detector called lockdep (the lock dependency validator). It tracks the order in which locks are acquired throughout the system and warns if a potential deadlock pattern is detected.

How it works

Every lock is instrumented. When a lock is acquired, lockdep records the sequence of locks currently held. If it sees A→B in one place and B→A elsewhere, it prints a warning to dmesg.

The catch

lockdep only catches observed patterns. If the deadlock requires a specific timing that hasn't occurred yet, lockdep won't see it. It's a safety net, not a proof.

The impact

Running with lockdep enabled is slow (2–10× performance hit) but catches real bugs before they ship. Linus Torvalds has publicly praised lockdep as one of the most valuable kernel debugging tools ever built.

🎭 Interactive Activity — The Dining Philosophers Roleplay

Five students. Five forks. Break the deadlock.

The setup

Arrange five students in a circle. Place a single object (pen, eraser, small notebook) between each pair of students — that's 5 objects total. Each student needs both their left and right object to "eat."

Round 1 · Deadlock

Have all five students grab their left object simultaneously. Then have them try to grab their right. Everyone fails — the right object is held by the neighbor. The classroom is deadlocked.

Round 2 · Discussion

Ask the class: "What would fix this?" Expect suggestions: "one student grabs right instead of left," "students release and retry," "wait for the neighbor to finish first." Each maps to a prevention strategy.

Round 3 · Lock ordering fix

Assign each object a number (1–5). Rule: always grab the lower-numbered object first. Student 1 (between objects 5 and 1) grabs object 1 first (right). Student 2 (between 1 and 2) grabs object 1 first (left). They now contend for object 1 — one wins, proceeds to object 2, and the chain unblocks. No deadlock.

💡
Debrief: ask why "grab the lower number first" prevents deadlock. Answer: it breaks the circular wait — no cycle of "I hold X, want Y" where Y has a lower number than X, since everyone always grabs lower first.

🏆 Grand Summary — L15 Key Takeaways

Four things to walk out with

01

A deadlock is a set of threads permanently blocked waiting for each other's resources. It's not a crash — it's a silent freeze. The kernel doesn't detect it; it just sees blocked threads.

02

The four Coffman conditions — Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait — must ALL hold for deadlock to occur. Break any one, and deadlock is impossible.

03

Circular Wait is the easiest condition to break, via global lock ordering: every thread acquires locks in the same predefined order. Zero runtime cost, complete prevention.

04

Real systems combine prevention (lock ordering discipline) with detection (Linux lockdep, runtime cycle checking). Avoidance (banker's algorithm) is mostly academic — it needs advance knowledge of future requests.
