What happens when power fails mid-write?

The Core Question of L19

L18 showed us that a file update touches multiple metadata structures — the inode, the block bitmap, the directory entry, and the data itself. If power fails midway through these updates, the filesystem is left corrupted. How do we prevent that?

🎯 The Core Problem — Multi-Block Updates Are Not Atomic

A single file operation touches multiple disk sectors

The reality of writes

Writing 4 KB to a file at a new offset requires: (1) find a free data block, (2) mark it allocated in the block bitmap, (3) write the data to the block, (4) update the inode to add a pointer, (5) update the file size, (6) update timestamps. That's 6 separate writes.

Why this is dangerous

The disk can only do one write at a time. Between any two of these six writes, the disk controller can lose power. The order is arbitrary — the write to the block bitmap could complete while the inode update never does.

What "crash consistency" means

After a crash, the filesystem must be in a state where it's usable and self-consistent — no dangling pointers, no leaked blocks, no half-updated files. Either the whole update happened, or none of it did.

💡
The word for this: "atomicity." The write is atomic if the filesystem behaves as if it either happened completely or not at all. Individual disk writes are atomic, but groups of writes are not.

✏️ Analogy 1 · Writing a Financial Check in Pencil First

The journal notebook comes before the main ledger

The setup

You want to transfer $1,000 to a business partner. If you start making the change across multiple account books and the room suddenly catches fire midway through, your records get half-updated and ruined.

The fix

Keep a tiny notebook chained to your desk. Before you modify any main bank ledgers, you write a clear note in the journal: "I intend to add $1,000 to Book B and subtract $1,000 from Book A." That's the Write-Ahead Log.

The safety

Once that intent note is written in ink, you can update the main books. If the building loses power midway, recovery is trivial: check the journal, read exactly what your intent was, and replay the work smoothly until everything balances.

💡
The whole lecture in one sentence: write down what you're about to do, then do it. If you crash before doing it, either replay from the note (if it was committed) or discard it (if it wasn't).

✏️ Analogy 1 · The Full Walkthrough — Five Steps

From intent note to committed transfer

Step 1 · Write the intent

Before touching the main books, write both changes in the journal notebook. "I will add $1,000 to Book B and subtract $1,000 from Book A."

Step 2 · Flush to disk

Make sure the journal entry actually reaches the disk (not just the cache). This is the critical commit point — before this, the transaction doesn't exist; after this, it does.

Step 3 · Update the main books

Now update Book A → $4,000 and Book B → $4,000. If a crash happens here, the journal entry can be replayed to fix the books.

Step 4 · Mark complete

Write "checkpoint complete" or clear the journal entry. The transaction is now fully in the main books; the journal can be reused.

Step 5 · Recovery (if crash)

On boot: scan the journal. If the commit marker exists → replay. If not → discard. In both cases, the system returns to a consistent state.

The five-step pipeline

1 · write intent to journal

Log "intend to change A and B" in the journal region.

2 · flush + commit marker

Force journal to stable storage. Write the commit record. This is the atomic point.

3 · checkpoint to main disk

Apply the changes to A and B in their real locations.

4 · clear journal slot

Mark the journal entry as free for reuse.

crash after 2 → replay · crash before 2 → discard

The structural match

Journaling operates identically to a non-volatile undo-redo database transaction pipeline, wrapping nested write modifications inside a strict validation framework that rolls back partial commits.

What a DB guarantees

When you commit a transaction, the changes are durable — even if power fails immediately after. When you don't commit, the changes never happened. This is the "A" and "D" of ACID (Atomicity, Durability).

The cost

Every commit requires an fsync — a real disk flush. That's the price of durability. Databases often batch commits (commit N transactions together) to amortize this cost.

📖 Core Breakdown — The Multi-Block Update

A single operation touches three critical structures

The structural dependency

A typical file-system update requires modifying multiple separate disk blocks simultaneously. Adding a data block to a file is three related writes:

[B] — data bitmap (mark block used)
[I] — inode (add pointer, update size)
[D] — data block (the actual bytes)

The problem

If a sudden power loss occurs midway through this sequence, the file system is left in an inconsistent state, leading to orphaned blocks or corrupted file-system metadata.

What "inconsistent" means

B written, I not → block marked used but no file owns it (leaked block)
I written, D not → inode points to stale garbage
D written, I not → data exists but no file references it

The three sectors of a write
[B]
Data Bitmap
Mark the target block as allocated
[I]
Inode
Add pointer to the block, update size
[D]
Data Block
Write the actual file content bytes

Any interruption between these writes leaves the filesystem with dangling pointers or leaked blocks.

📖 Core Breakdown — What Happens Without Journaling

The mid-write failure scenario

The setup

A user is appending text data to a file. This action requires writing to three separate disk sectors: Inode [I], Data Bitmap [B], and Data Block [D].

The failure

Power fails after writing [B] and [D], but before [I] is updated. The disk bitmap now marks the block as filled, but no inode owns it. The result is an unrecoverable memory leak — a block permanently lost to the filesystem.

The journaling fix

The system writes the intent block [Journal Start: update I, B, D] to the log sector first.
Crash before log commit → discard the partial entry
Crash after log commit, before checkpoint → replay from journal
Crash after checkpoint → already safe

📖 Core Breakdown — Journaling (Write-Ahead Logging)

The three-phase pipeline

The Write-Ahead Logging cycle

Phase 1 · Write intent to journal

Log all the intended changes to a dedicated journal region of the disk. Do not touch the main filesystem yet. The journal entry contains: transaction ID, list of (target block, new content) pairs, and a "commit" marker if the log is complete.

Phase 2 · Force journal to stable storage

Issue a flush command (fsync / barrier) so the journal entry actually reaches the disk platter or NAND cells. This is the atomic commit point — before this, the transaction can be discarded; after, it must be replayed.

Phase 3 · Checkpoint to main filesystem

Now apply the changes to their real locations: update the inode, the bitmap, and the data block. If power fails during this phase, the journal still holds the intent → recovery can replay it.

Phase 4 · Clear journal entry

Mark the journal slot as free. The transaction is now fully persisted in the main filesystem; the journal record can be overwritten by future transactions.

Why it works

The journal entry is a single small contiguous block. Writing a single block is atomic on most hardware. So "write the intent" is a single atomic action — either fully written or not at all.

The key guarantee

Crash before commit: journal has no complete entry → discard
Crash after commit: journal has the full intent → replay to main FS
Either way: main filesystem is consistent

The cost

Every transaction now requires writing to the journal twice (intent + checkpoint), plus an fsync. This is why journaling has a 20–50% performance cost for write-heavy workloads.

💡
Historical context: journaling filesystems (ext3, 1999) replaced non-journaling ones (ext2) because the fsck recovery time for large drives became unacceptable — hours of scanning for a possibly-broken filesystem. Journaling reduced recovery to seconds.
📖 Core Breakdown — The Commit Point

The atomic moment in the pipeline

The commit record

After writing all the intent records to the journal, the filesystem writes a final commit record — usually a magic number plus a checksum of the preceding entries. This single write is the atomic point of the transaction.

What makes it atomic

The commit record itself is a single sector. Single-sector writes are atomic on disk hardware — either fully written or not at all. If the commit record is present, the transaction happened. If it's absent (or its checksum fails), the transaction never happened.

The recovery rule

if commit_record.present && checksum_valid:
  replay(all_intent_entries)
else:
  discard(transaction)

♿
Micro-Accessibility Context: think of the commit record as a "final signature" on a contract. All the preceding pages are irrelevant if that final page is missing — the contract never took effect. If the signature is present, all the pages are binding.

📖 Core Breakdown — Checkpointing

Moving the journal into the real filesystem

The checkpoint operation
JOURNAL · committed
txn #001 → [I] new inode content
txn #001 → [B] bitmap update
txn #001 → [D] data block content
▼
MAIN FILESYSTEM
inode 9042 → updated ✓
block bitmap → block 8841 marked used ✓
data block 8841 → new bytes written ✓
What checkpoints do

A checkpoint is the process of copying the journal entries to their real locations in the main filesystem. Each journaled update becomes a real metadata update.

Why it's not the atomic point

Checkpointing can happen partially. If power fails halfway through, the journal still has the full intent — recovery can replay the rest. That's why the journal is written first.

When it happens

Immediately — for high-durability workloads
Deferred — during idle time (batch checkpoints)
Triggered — when the journal is running low on space
Forced — on fsync / sync / umount

💡
The performance trick: the journal can be flushed to main disk lazily — in the background, batched, or on demand. This decouples "commit durability" from "main filesystem update" and makes journaling much cheaper than a full synchronous write.
📖 Core Breakdown — Recovery After a Crash

On boot: scan, replay, resume

The recovery algorithm

1. Mount the filesystem read-only (or replay-only)
2. Scan the journal region from start to end
3. For each complete transaction (has commit record):
    • Replay its intent records to the main filesystem
4. For each incomplete transaction (no commit):
    • Discard it (write a "no-op" over the journal slot)
5. Once journal is drained, mount read-write

The guarantee

After recovery, the filesystem is consistent — every committed transaction is visible, every uncommitted transaction is gone. The OS doesn't have to know which transactions were in flight; the journal is the source of truth.

The timing

Recovery time is proportional to the size of the journal (typically 32–128 MB), not the size of the filesystem. This is why journaling makes boot recovery seconds instead of hours for large disks.

The recovery decision tree
START · mount filesystem
Filesystem was not cleanly unmounted. Begin journal scan.
SCAN · read journal region
Read all transaction slots from start to end.
✓ COMMITTED transaction
Commit record present, checksum valid → replay intent to main filesystem.
✗ INCOMPLETE transaction
No commit record → discard, skip this slot.
✓ ALL DONE
Journal drained → mount read-write → system usable.
📖 Core Breakdown — The Three Crash Cases

Same journal, three different outcomes

Live · Where the crash happens

Case 1 · crash BEFORE commit

Journal has partial entries, no commit record. Action: discard. Main filesystem is unchanged — consistent.

Case 2 · crash AFTER commit, before checkpoint

Journal has commit record, main FS may be partial. Action: replay. Main FS is brought up to date from the journal.

Case 3 · crash DURING or AFTER checkpoint

Main FS is mostly/fully updated. Action: replay is idempotent. Re-applying the same changes is a no-op — no harm done.

The key insight

Case 2 is the one that makes journaling valuable. Without the journal, a crash here leaves the filesystem in an ambiguous state. With the journal, we know exactly what to do: replay from the committed intent.

Why replay is safe

Replaying the same intent twice produces the same result. Overwriting the inode with the same content is idempotent. Overwriting the same data block is idempotent. This is why recovery can safely replay transactions without tracking "was this already applied?"

The idempotence requirement

Journaling only works if every operation is idempotent — reapplying it doesn't change the result. This is a design requirement for the journaling layer: the intent must describe the final state, not the delta ("set block to X", not "increment block by 1").

💡
The tradeoff: idempotent operations are slightly larger in the journal (they carry the full new content, not just the change), but they make recovery trivial. This is why journal entries are usually full-block writes, not byte-level diffs.

💻 Code — The Journal Write Path

A conceptual write-ahead logging implementation

journal.c · conceptual
// Simplified write-ahead log implementationstruct journal_txn {    uint32_t magic;        // identifies a valid entry    uint32_t txn_id;       // transaction sequence    uint32_t num_ops;      // number of intent records    struct { uint32_t block; void* data; } ops[64];    uint32_t checksum;     // integrity check};int journal_write(struct journal_txn* txn) {    // 1. write intent records to journal region    for (int i = 0; i < txn->num_ops; i++) {        write_block(journal_region + i, txn->ops[i].data);    }    // 2. write the commit record — atomic point    txn->magic = 0x4A524E4C;  // "JRNL"    write_block(journal_region + txn->num_ops, txn);    // 3. flush — force to stable storage    if (disk_flush() != 0) return -1;    // 4. checkpoint — apply to main filesystem    for (int i = 0; i < txn->num_ops; i++) {        write_block(txn->ops[i].block, txn->ops[i].data);    }    return 0;}
The three critical lines

write_block(magic) — the commit marker
disk_flush() — the durability barrier
write_block(target) — the checkpoint

Why order matters

If the checkpoint (step 4) runs before the flush (step 3), the main filesystem might be updated while the journal hasn't reached disk. A crash then leaves the main FS partial with no journal to replay from — inconsistent.

The magic number

0x4A524E4C spells "JRNL" in ASCII. If recovery finds a block where this magic is present and the checksum matches, it's a valid commit record — the transaction happened.

💻 Code — The Recovery Path

What the kernel does on boot after a crash

recover.c · conceptual
// Scan the journal on mount, replay committed transactionsvoid journal_recover(void) {    for (int i = 0; i < num_journal_slots; i++) {        struct journal_txn* txn = read_slot(i);        // Is this a valid committed transaction?        if (txn->magic != 0x4A524E4C) {            // No commit marker → discard            continue;        }        if (checksum(txn) != txn->checksum) {            // Corrupted commit → discard            continue;        }        // Valid transaction → replay to main FS (idempotent)        for (int j = 0; j < txn->num_ops; j++) {            write_block(txn->ops[j].block, txn->ops[j].data);        }    }    // Journal is drained → safe to mount read-write    clear_journal();}
The two checks

1. Magic number present?
If no → discard (crash before commit)
2. Checksum valid?
If no → discard (partial write)
If yes → replay

Why idempotent replay is safe

The replay just calls write_block on the target block with the recorded content. If the block already has that content (because a partial checkpoint happened), writing it again produces the same result. No tracking needed.

The scan is fast

The journal is typically 32–128 MB. Reading it sequentially takes milliseconds on SSD, tens of milliseconds on HDD. For a 1 TB filesystem, that's thousands of times faster than scanning the whole filesystem for consistency.

💡
Why mount read-only first: to prevent new transactions from being written to the journal during recovery. Only after the journal is drained does the filesystem transition to read-write.

The "data=ordered" default is a sweet spot: metadata is journaled, so the filesystem is always consistent. Data blocks are written before the metadata that points to them, so a crash can't leave a metadata pointer to uninitialized data. But data isn't in the journal — saving the "write twice" cost.
🌍 Real World — Copy-on-Write: ZFS & Btrfs

An alternative to journaling

The CoW approach

Instead of overwriting existing blocks and journaling the change, Copy-on-Write filesystems never overwrite in place. They write new blocks, then atomically update the pointer to point at them.

How it stays consistent

Because writes are always to new locations, the old data is untouched until the new data is fully written. The single atomic pointer update is the commit point. No journal needed — every write is atomic.

The extras

✓ Snapshots — just save the root pointer; O(1) snapshots
✓ No fsck — filesystem is always consistent
✓ Checksums — every block verified on read
✗ Fragmentation — writes scatter across disk
✗ More space — writes don't reuse old blocks immediately

💡
ZFS and Btrfs are the classic CoW filesystems. ZFS in particular is famous for its data integrity guarantees — every block is checksummed, every transaction is atomic, and scrubs can detect and repair silent corruption. But CoW has its own tradeoffs (fragmentation, write amplification on SSDs).

🏷️ System Lexicon — Crash Consistency & Journaling
Crash Consistency
Term 01 of 04
Formal Definition

The ability of a file system to recover structural data integrity safely and coherently after an ungraceful system crash or power loss event.

Plain Translation

( After a crash, is the filesystem still consistent? Can it be recovered automatically? )

Without it

The filesystem must be manually checked (fsck) — potentially hours of scanning for large disks.

Journaling
Term 02 of 04
Formal Definition

A reliability mechanism that logs all structural changes into an isolated scratch space on disk before executing updates on main file structures.

Plain Translation

( Write down what you're going to do before you do it. )

Also called

Write-Ahead Logging (WAL). The journal region is a pre-allocated circular buffer (typically 32–128 MB).

🏷️ System Lexicon — Checkpointing & Metadata Journaling
Checkpointing
Term 03 of 04
Formal Definition

The file system cycle step that safely copies verified, journaled file modifications out of the log buffer and writes them down onto the primary disk layout.

Plain Translation

( Moving the journal's intent into the real filesystem. )

When it runs

Immediately (data=journal), lazily (default), or when the journal is nearly full. Order doesn't matter for correctness — the journal is the source of truth until checkpoint completes.

Metadata Journaling
Term 04 of 04
Formal Definition

A performance optimization mode that logs only structural layout mutations (inodes, bitmaps) into the journal log, allowing raw file content bytes to stream directly to data blocks.

Plain Translation

( Only the metadata is crash-safe. The data itself is written directly, without journaling. )

The tradeoff

Metadata is always consistent, but file content might be stale after a crash (the write happened or it didn't). This is the ext4 default "data=ordered" mode.

🛑 Three Student Pitfalls

What beginners get wrong about crash consistency

PITFALL 01
"Journaling means no data loss"
Not necessarily. With metadata journaling (the ext4 default), the metadata is always consistent, but your data might not be on disk when you get a crash. If you wrote "hello" and the metadata (inode) was journaled but the data block wasn't yet flushed, recovery restores the metadata pointing at a block that might be partially written or stale. To guarantee data safety, use data=journal mode (slower) or explicitly call fsync after writes you care about.
PITFALL 02
"The journal is just an undo log"
No — the journal is a redo log. It records the final state you want to achieve (e.g., "inode 9042 should contain X"), not the change from previous state (e.g., "increment size by 4096"). This is why replay is idempotent — applying "inode = X" twice produces the same result. If the journal were a delta log, replay would double-apply the change and corrupt the filesystem.
PITFALL 03
"fsync guarantees durability of the file"
Only if you fsync the file AND its parent directory. Fsyncing the file flushes its data and its inode. But the directory entry that makes the file findable lives in the parent directory's data blocks — which are separately journaled. To durably create a file, you must fsync the file, then fsync the parent directory. This is a common source of "my file disappeared after a crash" bugs.

🏆 Grand Summary — L19 Key Takeaways

Four things to walk out with

01

A single file write touches multiple disk blocks (inode, bitmap, data). If power fails between writes, the filesystem is inconsistent — leaking blocks or corrupting files.

02

Journaling (Write-Ahead Logging) solves this: write the full intent to a dedicated log region first, force-flush it, then apply it to the main filesystem. The commit record is the atomic point.

03

Recovery is deterministic and bounded: scan the journal, replay committed transactions (idempotent), discard uncommitted ones. Seconds instead of hours, regardless of crash timing.

04

ext4 has three journaling modes — data=journal (slowest, safest), data=ordered (default, metadata-safe), data=writeback (fastest, weakest). Modern CoW filesystems (ZFS, Btrfs) achieve the same consistency goal without a separate journal.
