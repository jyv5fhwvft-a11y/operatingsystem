🎯 The Core Problem — Hardware Heterogeneity

Every manufacturer builds a completely different device

The reality

Every peripheral manufacturer builds hardware with completely different electrical and protocol characteristics. A keyboard from Logitech, a keyboard from Razer, a keyboard from a white-label OEM — three different register layouts, three different protocols, three different quirks.

The scaling problem

The OS kernel cannot contain unique, bespoke code for 10,000 different models of keyboards or network cards. That would make the kernel unmaintainable, giant, and impossible to update.

The resolution

Build a single, unified device abstraction layer that presents every device through the same interface. The OS then needs to know only one API — open, read, write, close — regardless of what hardware sits underneath.

💡
The design pattern: hide hardware variety behind a uniform interface. This is the same idea as the file abstraction in L17 — the app doesn't care if the file is on ext4, NFS, or tmpfs. Here, the app doesn't care if the "file" is an SSD, a keyboard, or a network card.
The heterogeneity problem
🔌 Analogy 1 · The Universal Wall Power Outlet Adapter

The outlet doesn't care what you plug in

The setup

Imagine an electricity grid. The wall outlet doesn't know or care whether you plug in a luxury toaster, a floor lamp, or a complex gaming laptop. It presents a simple, standardized two-prong interface that delivers voltage uniformly.

The adapter

A Device Driver is that exact adapter plug. To the operating system, every device looks like a standard file container that can handle basic operations: open(), read(), and write().

The translation

The driver sits between the kernel and the custom hardware, translating standard, generic file commands from the OS into the unique, bizarre language of that specific hardware manufacturer's circuit board.

💡
The design win: the app writer only needs to know the file API. The kernel only needs to know the VFS. Only the driver author — one per hardware family — needs to know the electrical specifics.

🔌 Analogy 1 · Two Layers of Standardization

The outlet standard, and the appliance's plug

Layer 1 · The wall outlet

The outlet is the kernel's VFS interface. It defines the shape of the plug (open, read, write, close) and the voltage (the syscall contract). Every device must speak this protocol to be plugged in.

Layer 2 · The appliance

The device is the appliance on the other side. It has an internal power supply, a heating element, a screen — things the outlet doesn't know or care about. That's the actual hardware.

The adapter — the driver

Between them sits the driver — the adapter plug. It knows the wall outlet's shape (the file_operations API) and the appliance's internal needs (register writes). It translates between them.

♿
Micro-Accessibility Context: on modern Linux, the "adapter" lives inside the kernel as a loadable kernel module (.ko file). Loading a driver is literally plugging in a new adapter without rebuilding the wall outlet.

🔗 Analogy 2 · The OOP Interface Polymorphism Pattern

Every driver overrides the same virtual table

The structural match
abstract class Driver {
virtual open(path, flags);
virtual read(buf, count);
virtual write(buf, count);
virtual close(fd);
class KeyboardDriver extends Driver {
override read(buf, count) {
  copy_scancodes_from_register(buf);
  return count;
}
class DiskDriver extends Driver {
override read(buf, count) {
  issue_SATA_read_to_DMA(buf);
  return count;
}
The structural match

A uniform device driver operates identically to an abstract base class or interface framework (e.g., implementing an interface OutStream with a virtual function virtual void write()), where completely different hardware components override the base pointer array to run unique hardware assembly loops.

The parallel

abstract class Driver → struct file_operations
virtual method write() → function pointer .write
subclass override → driver-specific .write implementation
dispatch via vtable → dispatch via file_operations table

Why polymorphism matters

The VFS doesn't need to know which driver it's talking to. It just looks up the function pointer in the file_operations table and calls it. Every device runs its own code through the same call site.

💡
The C equivalent: C has no classes — but it has function pointers. The kernel uses struct file_operations as a manual vtable. Each driver fills it in with its own functions.

📖 Core Breakdown — The Three Device Categories

Every hardware device fits one of three boxes

The abstraction

To keep the operating system scalable, hardware details must be masked behind a unified abstraction. The kernel divides the physical hardware universe into three distinct architectural categories.

Why three, not one?

Because the three categories have genuinely different I/O semantics. Block devices have random access; character devices don't. Network devices don't fit the file model at all (no seek, no read/write to a specific offset). Trying to shoehorn them all into one category would be worse than three.

The classification test

Can you seek? → block device
Is it a byte stream? → character device
Is it a packet stream? → network device

Fixed-size, addressable sectors

The defining property

Block devices store data in fixed-size, addressable blocks (typically 512 or 4096 bytes). You can jump to any block by its number — the device supports random access.

The kernel optimization

Because block devices are uniformly addressable, the kernel can build heavy caching layers on top: the page cache, the buffer cache, and the block layer's I/O scheduler. This wouldn't work for byte streams or packets.

Examples

/dev/sda — SATA disk
/dev/nvme0n1 — NVMe SSD
/dev/vda — virtual disk (VM)
/dev/loop0 — loop device (file-backed)

📖 Category 2 — Character Devices

Byte streams. No seeking.

The defining property

Character devices deliver data as a non-addressable, continuous stream of sequential characters or bytes. There are no blocks, no sector numbers, and you can't seek backwards or forwards to an arbitrary position.

Why no seek?

A keyboard produces bytes as you type them — there's no "position 500 in the keyboard's byte stream" because the stream is generated in real time. Same for a mouse, a serial port, or an audio device.

Examples

/dev/ttyS0 — serial port

/dev/null — discards everything

The defining property

Network devices stream data inside packet chunks, bypassing standard file operations entirely. They're accessed through a dedicated socket network subsystem — not through the file system's read/write interface.

Why not files?

A network interface doesn't have a fixed address space — you can't seek into "the network." Packets arrive from many sources, each with its own destination, headers, and framing. File semantics would be wrong.

The socket API

socket(AF_INET, SOCK_STREAM, 0) — TCP

bind · connect · send · recv

💡
The exception that proves the rule: Linux does expose network interfaces as /sys/class/net/eth0/ for configuration, but that's a sysfs interface, not the device I/O path. Actual packet I/O goes through sockets.
📖 The /dev Filesystem — Device Nodes

Hardware exposed as files in a directory

What /dev is

In Unix-like systems, all three device categories are exposed to user space inside the /dev device filesystem layout. Each hardware peripheral appears as a special file — a "device node" — inside this directory.

What a device node contains

Permissions — same chmod bits as regular files
Type flag — b for block, c for character
Major number — which driver owns it
Minor number — which device within that driver

The devtmpfs

Modern Linux uses devtmpfs — a virtual filesystem mounted at /dev that the kernel populates automatically as hardware is detected. You don't create device nodes by hand; the kernel does it.

♿
Micro-Accessibility Context: if you've ever run ls -l /dev and seen crw-rw-rw- and brw-rw---- — that leading c or b is the device type flag.

The two integers that identify the driver

Major number

The major number identifies which device driver owns this device. Major number 8 is the SATA driver, major 4 is the serial driver, major 1 is the memory device driver. The kernel maintains a table of major-number → driver mappings.

Minor number

The minor number distinguishes individual devices within the same driver. The SATA driver might have major 8 with minors 0, 1, 16, 17 — representing /dev/sda, /dev/sdb, /dev/sda1, /dev/sda2.

The mknod legacy

Historically, admins created device nodes by hand with mknod. Modern Linux auto-creates them via devtmpfs as the kernel detects hardware. You almost never run mknod by hand anymore.

💡
The two numbers in ls -l: when you see crw-rw-rw- 1 root root 1, 3, the "1, 3" is major=1, minor=3. That's /dev/null.

What it is

The File Operations Struct (file_operations) is a definitive kernel data registry containing function pointers that route standard system calls (open, read, write, close) directly to their matching hardware driver backend functions.

How it works

When a user calls read(fd, buf, n) on a device node, the VFS looks up that node's file_operations table and indirectly calls the .read function pointer. The pointer points to the driver's custom implementation — which knows how to talk to the actual hardware.

The optimization

Every syscall on that device goes through the same table lookup. That's why the kernel doesn't need to know about the device — it just needs the table's address. Polymorphism in C, one dispatch per call.

♿
Micro-Accessibility Context: NULL entries in file_operations mean that operation isn't supported. If .read is NULL and the user calls read(), the kernel returns -EINVAL. This is how the driver declares "I don't do this."
📖 The Complete Routing Path

From write() to hardware — one full walkthrough

The example

User code calls write(fd, "Hello", 5) on a file descriptor that points to /dev/ttyS0. Here's every step between the syscall and the physical serial port.

The steps

1. user → write() syscall (L03)
2. kernel → VFS lookup by fd
3. VFS → get inode → get device node
4. VFS → read major/minor from the node
5. VFS → look up driver by major number
6. VFS → call driver's file_operations.write
7. driver → write to hardware registers

The payoff

The user program never knows it's talking to a serial port. The VFS never knows what hardware is behind the driver. Only the driver knows the specific hardware — and the same program works on any machine with any serial chip.

What to look for

The first character of each permissions string tells you the device type:

b — block device (HDD, SSD)
c — character device (kbd, serial)
l — symlink (device aliases)
d — directory (subdirs like /dev/input)

The two numbers

After the group name and size, you'll see major, minor. Those are the driver ID and device ID. For /dev/sda it's typically 8, 0.

The permission check

Notice the permissions: crw-rw-rw- for /dev/null (world accessible), brw-rw---- for /dev/sda (root-only). The same chmod that protects files protects hardware — that's the Module 7 hook.

💻 Code — A Minimal Character Driver

The file_operations table

my_driver.c
#include <linux/fs.h>#include <linux/module.h>// Custom driver function that runs when a user writes to our devicestatic ssize_t custom_driver_write(struct file *file,                                          const char __user *buf,                                          size_t count,                                          loff_t *ppos) {    printk("Driver captured write request!\n");    // [Custom low-level inline assembly to blink the LED goes here]    return count;}// The Master File Operations registry table// Maps standard syscalls to our custom functionsstatic struct file_operations my_dev_fops = {    .owner = THIS_MODULE,    .write = custom_driver_write,  // ← the key mapping};
The key line

.write = custom_driver_write — this is the entire contract. Any user write to this device node will invoke this exact function.

The __user annotation

The __user macro on buf tells sparse (Linux's static checker) that this pointer comes from user space. Direct dereference is a bug — the driver must use copy_from_user().

The missing pieces

In a real driver you'd also need:
· register_chrdev() to claim a major number
· class_create() to make the /dev node appear
· module_init/exit for load/unload

💻 Code — Inside the Write Handler

What the driver actually does with the bytes

write_handler.c
static ssize_t custom_driver_write(struct file *file,                                          const char __user *user_buf,                                          size_t count,                                          loff_t *ppos) {    char kernel_buf[256];    // 1. Validate the count    if (count > sizeof(kernel_buf))        return -EINVAL;    // 2. Copy from user space (mandatory!)    if (copy_from_user(kernel_buf, user_buf, count))        return -EFAULT;    // 3. Now talk to the actual hardware    write_to_hardware_register(kernel_buf, count);    return count;}
The mandatory copy

copy_from_user() is not optional. The driver runs in kernel space; the user buffer is in user space. Direct dereference would either crash (page fault) or — worse — read arbitrary kernel memory through a crafted pointer.

The security reason

Without copy_from_user, a malicious user could pass a pointer into kernel memory and the driver would happily write it. copy_from_user checks that the source address is actually in the user's address space.

The return contract

On success, return count (bytes written). On failure, return a negative error code like -EINVAL or -EFAULT. Never return 0 for "success" — that confuses the VFS into thinking the write was short.

💡
The layering: the driver sees only raw bytes and kernel-space buffers. It has no idea that the user called printf or write or cat. Everything above it is opaque.
🧪 Live Demo — Writing Raw Data to /dev/tty

Bypass all layers. Talk to hardware directly.

Live · The echo command bypasses normal output
user@box — echo to /dev/tty
$ echo "Hello hardware" > /dev/tty
What this does

echo "Hello" > /dev/tty opens the device node for the current terminal, writes the bytes to it, and closes. The bytes go directly to the terminal hardware — no shell involved, no line-buffered stdout, no libc.

The layering exposed

Normally: printf → libc → write() → VFS → driver
Here: echo → write(/dev/tty) → VFS → driver
The libc layer is skipped — echo calls write directly.

The proof

Redirect to a file instead and watch the difference. Writing to /dev/tty forces output to the terminal even when stdout is redirected. The device node is the only path to that specific hardware.

♿
Micro-Accessibility Context: this is why sudo sh -c 'echo ... > /dev/sda' is dangerous — it bypasses the filesystem entirely and writes raw bytes to the physical disk. You don't need a filesystem to corrupt a disk this way.
📖 Block Device Internals

Why block devices get their own subsystem

The block layer

Block devices are important enough to warrant their own subsystem. The block layer sits between the filesystem and the driver, providing:

Page cache — recently-read blocks
Buffer cache — merged write buffers
I/O scheduler — merge + reorder requests (L16's SCAN)
Request queues — batch operations
Plugging — temporary request merge windows

The two-layer design

Filesystems don't talk to block devices directly. They submit bio (block I/O) requests to the block layer, which schedules and merges them, then hands batches to the driver. This is why two sequential 4 KB writes might become one 8 KB write at the driver level.

The result

The block layer transforms random I/O from the filesystem into sequential I/O for the hardware — recovering most of the performance L16 described as lost to seeks. That's the entire reason the block subsystem exists.

📖 Network Device Internals

Why network devices don't use the file API

The socket layer

Network interfaces are accessed through the socket subsystem, not files. A socket is a kernel object that represents a network connection (TCP, UDP, raw) — with its own buffering, its own lifecycle, and its own API (bind, connect, listen, send, recv).

The sk_buff

The kernel's internal representation of a packet is a struct sk_buff — a complex structure with headroom for headers, tailroom for padding, and a pointer to the actual data. Every network driver reads and writes sk_buffs.

The net_device_ops

Just like char/block devices have file_operations, network devices have net_device_ops — a struct of function pointers like ndo_start_xmit (send a packet). Same polymorphism pattern.

💡
The consistency: all three device categories use the same design pattern — a struct of function pointers for polymorphic dispatch. The difference is which struct: file_operations for block/char, net_device_ops for network.

🛑 Three Student Pitfalls

What beginners get wrong about device drivers

PITFALL 01
"Network devices also live in /dev"
No. Block and character devices appear as nodes in /dev. Network devices do not — they're accessed through sockets. If you look for /dev/eth0 you won't find it. Network interfaces are exposed via /sys/class/net/ for configuration, but the actual data path is sockets.
PITFALL 02
"The driver runs for every byte"
Not necessarily. The kernel buffers aggressively — the page cache, socket buffers, and TTY line discipline all sit between the app and the driver. A read(fd, buf, 1000) that hits the page cache never invokes the driver. The driver only runs when the kernel actually needs to talk to hardware.
PITFALL 03
"The driver trusts user pointers"
It must not. Any pointer passed from user space (__user-annotated) must go through copy_from_user / copy_to_user. Directly dereferencing a user pointer is a privilege escalation vulnerability — a malicious user could pass a kernel address and the driver would happily read or write it in Ring 0. This is one of the most common kernel vulnerabilities.

🏆 Grand Summary — L21 Key Takeaways

Four things to walk out with

01

The kernel abstracts all hardware into three categories: block devices (HDD/SSD, seekable blocks), character devices (keyboard/serial, byte streams), and network devices (packets, sockets). Each gets a dedicated subsystem.

02

Device drivers bridge the gap between the VFS file API and specific hardware. Each device appears as a node in /dev for block/char, or as a network interface for net.

03

Major/minor numbers identify the driver and device instance. The file_operations struct is the driver's polymorphic vtable — function pointers the VFS dispatches through.

04

This architecture is why "everything is a file" works: the same open/read/write API that handles regular files also handles hardware — because the driver hides the hardware behind that API.
