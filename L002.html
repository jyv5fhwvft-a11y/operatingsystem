🚧 The Gate Problem — Why Syscalls Exist

Software cannot "just" touch the hardware

What the CPU physically forbids in Ring 3

Reading or writing memory-mapped device registers · issuing device commands · altering page tables · disabling interrupts · altering the CPU mode bit itself. Any attempt fires a hardware exception, not a polite refusal.

What that means for real code

Your program cannot open a file, read a keystroke, or draw a pixel by itself. Every single one of those operations must be requested through the kernel.

So we need one legal doorway

A controlled, auditable, single entrypoint from Ring 3 into Ring 0 — where the kernel can inspect the request, verify arguments, and only then perform the privileged action on the caller's behalf.

💡
That doorway is the system call interface. Everything above it (libraries, shells, GUIs) is built on top of this single primitive.

The key is the number in rax. The value is the address of the compiled kernel function.

Software API routing via hash map function lookups

What the kernel actually does

A system call behaves identically to a secure hash map router. The index key is a positive numeric ID (e.g., syscall #1 for write). The value paired with that key is a strict pointer to a verified, compiled inner kernel function array location.

Why this design works

Adding a new syscall means adding one entry to the array — no dispatch chain, no if/else tree, no branch mispredictions. O(1) lookup, bounded by array access speed.

The security aspect

The array lives in kernel memory. A user process cannot edit it or force the kernel to call an arbitrary address — it can only supply a legal index. Out-of-range = invalid syscall = EINVAL.

📖 Core Breakdown — The Syscall Contract

Four registers hold the entire request

The register contract (x86_64 Linux)

rax — syscall number (the key)
rdi — argument 1
rsi — argument 2
rdx — argument 3
(r10, r8, r9 hold args 4–6 when needed)

What the user code does

Loads the four registers, then fires a specific assembly trap instruction (syscall or int 0x80).

What the CPU does in response

Flips the mode bit to Ring 0, saves the return address, and jumps to the kernel's pre-registered trap entry point. No other ring transition is permitted.

Live · Registers loading for a write() call
rax 1 syscall #
rdi 1 arg 1 (fd)
rsi 0x7FF… arg 2 (buf)
rdx 37 arg 3 (len)

Sequential load order matters: values must all be in place before the trap fires — otherwise the handler reads garbage.

📖 Core Breakdown — The Trap Instruction

The one instruction that changes the CPU's mode bit

Live · Mode bit flip at the boundary
Ring 3 · User your code is executing here syscall
⚡ MODE BIT → RING 0
Ring 0 · Kernel handler code now executes
CPL = 3 → flipping
What the instruction physically does

When the CPU decodes syscall, it loads the LSTAR MSR (a hardware register holding the trap entry address), saves the return address in RCX, saves flags in R11, and sets the current privilege level to Ring 0.

The two variants

syscall — modern x86_64 fast path, ~100–300 cycles.
int 0x80 — legacy software interrupt, slower, still used on 32-bit.

Why this can't be forged

The user cannot choose where to jump. The trap entry address is set once by the kernel at boot, in a register the user cannot write. The destination is immutable from Ring 3.

📖 Core Breakdown — The Interrupt Vector Table

The kernel's master handler address book

What the IVT actually is

A memory array holding code pointers to specialized driver and kernel function routines. On x86_64, the analog is the IDT (Interrupt Descriptor Table) — but the mechanism is the same: index in, handler address out.

What the CPU does with it

After the trap fires, the CPU uses the trap type as an index into this table, reads the stored handler address, and jumps there — into Ring 0 code, with the caller's context saved.

For syscalls specifically

The syscall instruction lands at a single fixed entry point (entry_SYSCALL_64 in Linux). That entry stub then uses the number in rax to index a second table — the syscall table — to find the specific handler.

📖 Core Breakdown — The Full Round Trip

Four stages, one user request

Live · Request packet travelling through the pipeline
01User app fills registers
02syscall trap fires
03IVT lookup → handler
04return value in rax
Stage 01 · Preparation

The user code loads rax = syscall number, rdi/rsi/rdx = arguments. No privilege change yet. The data is just sitting in registers.

Stage 02 · The trap

The syscall instruction executes. The CPU flips the mode bit, saves the return address, and jumps to the kernel's trap entry point. Hardware transition.

Stage 03 · Dispatch

The kernel entry stub reads rax, validates the number, indexes the syscall table, and jumps to the specific handler. Software dispatch.

Stage 04 · Return

The handler performs the privileged action, writes its result into rax, and executes sysret — the CPU flips the mode bit back to Ring 3.

Hardware Trap
Term 02 of 04
Formal Definition

An exceptional condition generated by software that shifts control back to the operating system.

Plain Translation

( The electronic "ding" that tells the CPU to stop what it's doing and go ask the kernel. )

Why "trap"

The CPU treats the transition as an exceptional event — meaning the mode bit flip is guaranteed by hardware, not cooperatively by software.

💻 Code Dissection — A Raw x86_64 write()

Bypassing libc, calling the kernel directly

raw_write_syscall.c
// Bypassing the standard printf library wrapper to invoke a raw x86_64 write syscall#include <unistd.h>int main() {    char* msg = "Hello from a raw x86_64 system call\n";    __asm__ volatile (        "movq $1, %%rax\n"      // Syscall number 1 = write        "movq $1, %%rdi\n"      // arg 1: fd = stdout        "movq %0, %%rsi\n"      // arg 2: buffer pointer        "movq $37, %%rdx\n"     // arg 3: message length        "syscall\n"              // fire hardware trap → Ring 0        : /* no outputs */        : "r"(msg)        : "rax", "rdi", "rsi", "rdx"    );    return 0;}
What you're seeing

The four movq instructions load the register contract. Then one syscall instruction performs the entire gate crossing.

Why no printf?

printf is a libc wrapper that formats text into a buffer and then calls write. We're skipping the formatting and calling the syscall directly.

The clobber list

Listing "rax", "rdi", "rsi", "rdx" tells the compiler those registers will be modified — so it doesn't keep live values in them across the trap.

💻 Code Walkthrough — Line by Line

Reading the raw asm like a register choreography

What each line does to the CPU

Three things that matter here

Order matters

All four register writes must complete before line 5. If the trap fires with rax still uninitialized, the kernel will dispatch to whatever number happens to be in there — often producing an EINVAL or, worse, a nonsensical syscall.

The trap is the entire crossing

Lines 1–4 are ordinary user-space instructions. Line 5 is the only line that cannot be emulated in user space. That single instruction is the Gatekeeper.

Return value

After sysret, rax holds either the number of bytes written (success) or a negative error code (failure). The caller reads rax — end of story.

What strace shows you

strace runs a process under a tracer and logs every single syscall — its number, its arguments, and its return value. It's the fastest way to see the Gatekeeper in action.

The line you're looking for

write(1, "Hello from a raw x86_64 system call\n", 37) = 37
That's syscall #1, fd = 1, 37 bytes, returning 37. Same contract we just loaded into registers by hand.

Why this matters as a debugging tool

When a program "hangs", "fails silently", or "can't find a file", strace usually reveals the exact syscall that went wrong — and what error code it returned.

⏱️ The Cost of Crossing the Gate

Not free — but often cheaper than you think

The three costs of a syscall

1. Mode bit flip — hardware transition Ring 3 → Ring 0 → Ring 3
2. Register save / restore — the kernel must preserve the caller's context
3. Handler dispatch — entry stub → validate → table lookup → target function

Typical numbers on modern hardware

A simple getpid syscall costs about 100–300 nanoseconds. A read or write costs more because it touches devices.

Where this hurts

A loop that calls read one byte at a time pays the crossing cost once per byte. That's why buffered I/O exists.

Live · Relative costs (log scale)
Direct function call~5 ns
Simple syscall (getpid)~250 ns
Full syscall + device I/O~10 µs

Each step costs ~50× the last. That's the price of safety — and why every kernel designer obsesses over reducing syscall count.

🛡️ Why This Is a Security Boundary

The gate is also the guard post

What the gate guarantees

Every privileged action passes through one auditable interface. The kernel can inspect every argument, validate pointers, check permissions, and reject anything malicious — before the operation happens.

What the kernel checks on every call

✓ Is the syscall number in range?
✓ Does the caller have permission to touch that fd?
✓ Is the pointer inside the caller's own address space?
✓ Is the length field consistent with the buffer?

What happens if a check fails

The kernel returns an error code (like EFAULT, EINVAL, EPERM) without performing the operation. No exception to the user — just a negative return value in rax.

The gate as a checkpoint
🛑 Student Pitfalls — The Three Big Ones

Three misconceptions to kill early

Pitfall 01 — "printf is a syscall"

It isn't. printf is a libc formatting function. It builds a buffer in user space, then calls write once. One printf("hello %d\n", x) can cost zero or one syscalls depending on buffering. Never confuse a library function with a kernel entry.

Pitfall 02 — "I can call the kernel function by address"

No. The kernel's address space is not mapped in your process. Even if you knew the address of sys_write, you couldn't call it — the page isn't there. The only path in is through the trap.

Pitfall 03 — "syscalls are slow, so avoid them"

They're cheap relative to I/O. The reason to avoid them is redundancy — calling read(fd, buf, 1) in a loop is slow not because the trap is slow, but because you're paying it a thousand times. Buffer at the library level, and 1000 reads become one read of 4096 bytes.

🌍 Real-World — Where You've Already Seen This

Every "operation not permitted" you've ever seen

"Permission denied" on a file

You called open(). The kernel's sys_open handler checked your UID/GID against the file's permission bits, saw a mismatch, and returned -EACCES without opening anything.

"Segmentation fault" from a bad pointer

You passed a pointer to write() that pointed outside your address space. The handler tried to read it, the MMU raised a fault, and the kernel terminated your process rather than leak a kernel memory address.

Docker / container boundaries

Containers use seccomp filters — a whitelist of which syscall numbers are allowed. A blocked syscall returns EPERM immediately, without ever reaching the real handler.

The strace output you've probably seen
user@box — strace -e trace=open ./app
$ strace -e trace=open ./app open("/etc/passwd", O_RDONLY) = 3 open("/etc/shadow", O_RDONLY) = -1 EACCES — process exits with code 1 — app: error: cannot open /etc/shadow

The first open succeeded; the second was rejected. Same program, different permission bits on the target file.

📌 The 4-Step Syscall Journey — Recap

If you remember nothing else, remember this

STAGE 01
Fill the registers
rax = syscall number · rdi/rsi/rdx = arguments. Order matters.
STAGE 02
Fire the trap
The syscall instruction flips the mode bit to Ring 0 and jumps to the kernel entry point.
STAGE 03
Look up the handler
The kernel reads rax, validates it, and indexes the syscall table to find the target function.
STAGE 04
Return through rax
The handler runs, writes the result into rax, and sysret flips back to Ring 3.
The big idea

Every interaction with hardware — file I/O, keyboard, network, display — is a syscall. There is no other legal path from Ring 3 to Ring 0.

Why it matters

This is the foundation for the next 25 lectures. Every module (processes, memory, files, drivers, security) is built on top of this single mechanism.

🏆 Grand Summary — L03 Key Takeaways

Three things to walk out with

01

The system call is the only legal interface between user space and kernel space. It is small, well-defined, and impossible to bypass from Ring 3.

02

The mechanism is register-driven and trap-based: rax/rdi/rsi/rdx hold the request, syscall fires the trap, the CPU flips the mode bit, and the kernel dispatches via a lookup table.

03

The gate is also the security checkpoint — the kernel validates every argument before acting. Failures return negative error codes; successes return results in rax.
