🎯 Program vs. Process — The Critical Distinction

A program is a file. A process is that file alive.

A program is

A static binary file sitting on disk. It occupies no RAM, has no program counter, no register values, no PID. It's just bytes on a storage block.

A process is

An active instance of a running software application containing its own dedicated execution context and address boundaries. It owns memory. It has a current instruction. It can be scheduled.

The relationship

One program file → many processes. Open Chrome three times and you have three independent Chrome processes, each with its own memory, PID, and program counter — all running the same binary from disk.

💡
Analogy: A recipe book is a program. Actually cooking the recipe in your kitchen is a process. Two cooks can be following the same recipe simultaneously — that's two processes sharing one program file.
Static file vs. live process
📒 Analogy 1 · The Corporate Building Accountant

A building manager keeps a ledger folder for every tenant

The Setup

Imagine a massive corporate office building where multiple completely different businesses (user processes) share the same workspace. Each business thinks it is the only company there.

The Ledger

To keep them organized, the building manager has a dedicated filing cabinet containing a thick ledger folder for every single business. This folder is the Process Control Block (PCB).

What's inside the folder

PID — the tenant's unique identity badge
State — currently working / on break
Program Counter — which line of their contract they're reading
Registers — their running tally of calculations
File descriptors — which doors they have keys to

💡
The key insight: if a business leaves the room (gets context-switched out), the accountant reads their ledger to restore their exact state when they return. Without the ledger, work would have to restart from scratch.

📒 Analogy 1 · Why the Ledger Matters — Context Switch

Every pause, the ledger is updated and read back

Step 1 · Save on exit

Tenant A is running. The OS decides to switch away. The kernel saves all of A's register values, PC, and CPU state into A's PCB folder. Tenant A is now "ready" but paused.

Step 2 · Load on resume

Later, the OS picks Tenant A again. It reads the PCB folder back, restores every register and the PC, and Tenant A continues from exactly where it stopped — as if nothing happened.

The magic

The tenant never notices. From their perspective, time just moved forward. Only the accountant's ledger makes this possible. This is the context switch — the topic of L06.

💡
Cost of a bad ledger: if any register isn't saved correctly, the process resumes with a corrupted value and crashes or produces wrong results — a nondeterministic bug that's nearly impossible to debug.
The save-restore cycle

A resumes from the saved PC — as if no time had passed.

💾 Analogy 2 · VM Config File + Saved-State Snapshot

A PCB is basically a saved machine snapshot for one program

What a VM snapshot contains

Memory image, all CPU registers, disk state, device attachments. You can power off a VM, come back a week later, and resume it exactly where it left off.

What a PCB contains

Saved register state, program counter, memory management boundaries, open file descriptor table, and lifecycle flags. The kernel uses it to pause and resume processes the same way a hypervisor snapshots a VM.

The structural match

A process layout matches a sandboxed virtual container, where the underlying host kernel preserves a structured C struct (struct task_struct in Linux) to cache metadata boundaries that hardware registers must shift into during a context switch.

♿
Micro-Accessibility Context: On Linux, the PCB is literally a C struct called task_struct. It's roughly 1.7 KB per process. With 500 processes, that's under 1 MB of kernel memory — a very efficient way to track a lot of state.
The snapshot metaphor
📖 Core Breakdown — What a Process Actually Contains

Two things: an address space and a ledger entry

Part 1 · The Address Space

The physical and virtual memory the process can see and touch:
Text segment — compiled machine instructions
Data segment — global and static variables
Heap — dynamically allocated memory (malloc)
Stack — local variables and function call frames

Part 2 · The PCB (kernel-side)

The kernel's tracking ledger for that process:
PID — unique identifier
State — running / ready / waiting
Program counter — next instruction
CPU registers — saved at last switch
File descriptors — open files/sockets
Memory map — page table pointer

💡
Two different perspectives on the same thing: the address space is what the process sees; the PCB is what the kernel sees. Both describe the same running program.
🧱 Memory Layout — Text Segment

The compiled machine instructions

What lives here

The CPU's native machine instructions, produced by the compiler from your source code. When you run gcc program.c, this is where the resulting main, printf, and every other function ends up.

Characteristics

Read-only — you can't modify executing code (that would be self-modifying code, which is disabled by default). Shared across processes running the same binary. Executable — this is the only segment the CPU will fetch instructions from.

Why read-only matters

If the text segment were writable, a buggy pointer could accidentally overwrite the running code. Marking it read-only means the MMU catches such writes as faults. It also lets the kernel share one physical copy of Chrome's code across 30 Chrome processes.

Text segment · read-only · executable
.text
read-only · executable · shared
0x4004d0: push %rbp
0x4004d1: mov %rsp,%rbp
0x4004d4: mov $0x1,%eax
0x4004d9: callq 0x4003e0 <printf@plt>
0x4004de: pop %rbp
0x4004df: retq

Instructions are fetched from this segment by the CPU's instruction decoder. Every other segment is data.

🧱 Memory Layout — Data Segment

Global and static variables — allocated at load time

Data segment · read/write · fixed size
.data / .bss
read/write · fixed size · per-process
int global_counter = 0; // .bss
int global_cfg = 42; // .data
char banner[] = "Hi"; // .data
static int cache; // .bss
Live memory cells · highlighted as globals are accessed
What lives here

Global variables and static local variables. Anything declared outside a function body, or declared with the static keyword inside a function.

The .bss / .data split

.data holds globals with non-zero initial values. .bss holds globals initialized to zero — they don't need to be stored in the binary because the kernel just zero-fills them at load time. It's a size optimization.

Fixed size at load

Unlike the heap, the data segment's size is set once at program load. It cannot grow during execution. If you run out of globals, you don't "grow" them — you allocate on the heap instead.

🧱 Memory Layout — Heap

Dynamically allocated memory — grows as needed

What lives here

Memory allocated explicitly at runtime via malloc, calloc, realloc, or new in C++. Data structures whose size isn't known until runtime — strings, dynamic arrays, trees, hash tables.

How it grows

The heap starts small and grows upward (toward higher addresses) as allocations happen. The kernel extends the heap via the brk syscall when the current heap space runs out.

The classic problems

Memory leaks — forgetting to free allocations means the heap grows forever. Use-after-free — accessing memory after freeing it corrupts whatever gets allocated there next.

Heap · read/write · grows upward
heap
read/write · grows up · per-process
char *s = malloc(256); // allocate
strcpy(s, "hello world"); // use
char *t = malloc(64); // another block
free(s); // release
free(t); // release

Allocations are tracked by the malloc bookkeeping — the process "owns" them until freed.

🧱 Memory Layout — Stack

Local variables and call frames — grows downward

Stack · read/write · grows down · LIFO
stack
read/write · grows down · per-thread
[ main() frame ]
  int x = 5
  int y = 10
  ...
[ foo() frame ] ← current top
  int result
  char buf[32]
  return address

Each function call pushes a new frame. Returning pops it. Very fast — just move the stack pointer.

What lives here

Local variables, function parameters, return addresses, saved registers — everything needed to resume a function call. Managed entirely by the call/return instructions.

Grows downward

The stack grows toward lower addresses (opposite of the heap). This is intentional — the stack and heap grow toward each other from opposite ends of the address space, maximizing the room for both.

The classic bug

If the stack grows into the heap, you get a stack overflow. If a function recurses infinitely, the call frames pile up until they collide with the heap. The kernel detects this as a fault and terminates the process.

📊 The Full Memory Map — All Four Segments Together

One process, four regions, one address space

The canonical process memory layout
stack▼ grows down
Local variables · function call frames · return addresses
heap▲ grows up
malloc/calloc allocations · dynamic data structures
.data / .bssfixed
Global variables · static variables · initialized + zeroed
.textread-only
Compiled machine instructions · shared across processes
The layout at a glance

Stack — top of address space, grows down
Heap — grows up toward the stack
Data — fixed-size, set at program load
Text — bottom of address space, read-only

What happens as the program runs

The heap and stack each grow independently. If they ever meet, the process is out of memory and will crash (or the kernel's brk/stack growth will fail). This is why unbounded recursion or runaway allocation eventually crashes the process.

Why this specific layout

Text at the bottom (never changes). Data just above (fixed at load). Heap grows up. Stack grows down from the top. The middle is a no-man's-land that neither segment can enter unless the other shrinks — a natural guard against unbounded growth.

📋 The Process Control Block — Introduction

One kernel data structure per process

Definition

The Process Control Block (PCB) is the definitive kernel data structure used to track, schedule, and preserve a process's metadata. Every running process has exactly one PCB, allocated from kernel memory when the process is created.

Where it lives

In kernel memory (Ring 0), not user space. The process cannot read or modify its own PCB — only the kernel can. This is what makes the ledger trustworthy.

The Linux name

On Linux, the PCB is implemented as struct task_struct. On macOS/BSD it's called struct proc. Windows calls it EPROCESS. Same concept, different name.

💡
One PCB per process, not per program. Open Chrome 5 times → 5 processes → 5 PCBs. Same binary, separate tracking.
The kernel's process table
🔢 PCB Field 1 — PID (Process ID)

The unique identity badge of every process

pid_t pid
process identifier · integer · 32-bit
What it is A unique integer assigned by the kernel at process creation. No two live processes on the same machine share a PID.
How it's used Every signal, every scheduling decision, every permission check identifies the process by its PID. Users interact with PIDs constantly — kill 4821, ps aux | grep 4821.
Range Default 1 to 32768 on Linux. Reused when a process exits and its slot is freed. PID 1 is always init / systemd.
Every process has one

🚦 PCB Field 2 — Process State

The lifecycle flag — where in its journey the process is

enum state
process lifecycle flag · one of five values
Definition The operational lifecycle flag of a task: New, Ready, Running, Waiting/Blocked, Terminated.
Why it matters The scheduler only picks from the Ready queue. A process in Waiting cannot run, even if the CPU is idle — it's waiting for I/O, a lock, or a signal.
Where it's used Every context switch, every scheduler decision, every ps output reads this field.

🚦 The 5-State Process Diagram — All Transitions

Which states connect to which, and what triggers each transition

The transitions

NEW → READY — admitted by scheduler
READY → RUNNING — dispatcher picks it
RUNNING → READY — time slice expires (preempted)
RUNNING → WAITING — I/O request / lock wait
WAITING → READY — I/O completes / lock released
RUNNING → TERMINATED — exits or is killed

What makes this a "state machine"

Every transition is caused by an event the kernel detects: a syscall, an interrupt, a timer tick, or an exit. The scheduler's job (Module 2, L07–L08) is to decide which READY process becomes RUNNING next.

The waiting state matters most

Most of a process's time is spent WAITING. A browser tab waiting for a network packet, or a program waiting on a disk read, is not consuming CPU — it's sitting in the WAITING state until the kernel wakes it.

🎯 PCB Field 3 — Program Counter (PC)

The address of the next instruction to execute

void *program_counter
address · 64-bit · x86 called RIP · ARM called PC
Definition A specialized physical CPU register that stores the memory address of the next instruction waiting to be executed.
Why the PCB saves it When a context switch happens, the current PC value is written into the outgoing process's PCB. When the process resumes, the PC is loaded back — so execution continues at the exact same instruction.
On x86_64 The register is called RIP. On ARM, it's called PC. Both are 64-bit on 64-bit systems.

What's saved Every general-purpose register: rax, rbx, rcx, rdx, rsi, rdi, rsp, rbp, r8–r15, plus the instruction pointer RIP and the flags register.
Why it matters A register is a "scratchpad" holding values the program is working on right now. If the kernel doesn't save them, another process would clobber them and the original process would resume with garbage in its variables.
💡
This is the whole trick of multitasking: save all registers to PCB, load another process's registers from its PCB, and the CPU is now running the other process — even though it's the same physical hardware.
🗺️ PCB Field 5 — Memory Management Boundaries

The address space boundaries for this process

mm_struct *mm
memory descriptor · pointer · per-process
What it holds The process's base and bound registers (conceptually), the page table base address, and pointers to the VMA (virtual memory area) descriptors that define each segment of the address space.
The boundary values Base address of the process's address space, end address, and the location of each of text/data/heap/stack — so the kernel can validate every memory access the process attempts.
Used for Setting up the MMU on context switch (loading the page table base into the CR3 register on x86), validating syscall pointer arguments, and enforcing the boundary that turns stray writes into SIGSEGV instead of corruption.
Each process gets its own memory map
📁 PCB Field 6 — Open File Descriptor Tables

Every open file or socket the process holds

Live · The per-process file descriptor table
fd 0 📖 stdin /dev/pts/0
fd 1 📝 stdout /dev/pts/0
fd 2 ⚠️ stderr /dev/pts/0
fd 3 📄 data.txt /home/user/data.txt
fd 4 🌐 socket TCP :443 → 142.250.x.x
struct files_struct *files
open file descriptor table · pointer
What it holds An array where each slot points to an open file description. Slot numbers are the file descriptors you see as integers in C code.
The three universal FDs Every process starts with 0 = stdin, 1 = stdout, 2 = stderr — inherited from the parent process that created it.
Why the PCB tracks them When a process exits, the kernel must close every FD in the table. Otherwise the underlying file handles leak. This is why the OS cleans up leaked file handles at process termination — but only if the process exits, not if it stays alive and keeps opening files.

🔍 Real World — Reading PCBs via /proc on Linux

The kernel exposes PCB data through a virtual filesystem

Live · Looking at a real process's PCB data
user@box — inspect /proc/4821
$ cat /proc/4821/status | head -6 Name: chrome State: S (sleeping) Tgid: 4821 Pid: 4821 PPid: 1 ... $ ls -l /proc/4821/fd lrwx---- 1 user user 64 ... 0 -> /dev/pts/0 lrwx---- 1 user user 64 ... 1 -> /dev/pts/0 lrwx---- 1 user user 64 ... 2 -> /dev/pts/0 lrwx---- 1 user user 64 ... 3 -> /home/user/data.txt $ cat /proc/4821/maps | head -4 00400000-00452000 r-xp /usr/bin/chrome 00651000-00653000 r--p /usr/bin/chrome 01f2a000-01f4b000 rw-p [heap] 7ffd4c000000-7ffd4c021000 rw-p [stack]
What just happened

The kernel exposes a process's PCB data through a virtual filesystem at /proc/[pid]/. Reading those files doesn't read from disk — it asks the kernel to format and print the live data from that process's PCB.

Field mapping

/proc/PID/status → PID, State, PPid
/proc/PID/fd → open file descriptors
/proc/PID/maps → memory layout
/proc/PID/stat → PC, registers, state (raw)

Try it yourself

On any Linux machine (or WSL), run ps aux | head -5 to see all PIDs, then cat /proc/[pid]/status to inspect any one of them.

🧭 System Cohesion — Where L05 Sits

The bridge from Module 1 → Module 2

Relies On · L02 (Dual-Mode Barrier)

Relies on Ring 0 privileges to protect the PCB arrays from being altered by unprivileged user application code. The PCB lives in kernel memory — user space cannot even read it directly.

Feeds Into · L06 (Execution Mechanics)

Modifying, cloning, or discarding a process lifecycle requires allocating or freeing a physical PCB block struct inside the kernel slab allocator. Without a PCB, fork() cannot exist.

Downstream impact

Module 2 (L06–L09): every process creation, scheduling decision, and context switch reads and writes the PCB.
Module 3 (Memory): the PCB's mm pointer is where page tables live.
Module 4 (Sync): kernel locks protect the PCB during concurrent updates.
Module 5 (Files): the PCB's file descriptor table is the file system entry point per process.

🏆 Grand Summary — L05 Key Takeaways

Four things to walk out with

01

A process is not a program. A program is a static file; a process is that file alive in RAM, with its own PID, memory, program counter, and lifecycle state.

02

Every process has four memory segments: Text (read-only code), Data (globals), Heap (dynamic allocations, grows up), Stack (function frames, grows down).

03

The Process Control Block (PCB) is the kernel's ledger for one process — PID, state, PC, saved registers, memory boundaries, file descriptor table.

04

The PCB is what makes context switching possible. Save state → run another process → restore state. Without it, multitasking doesn't exist.
