🎯 The Core Problem — Fixed-Size Metadata, Unbounded Data

An inode is fixed size. A file can be huge.

The design constraint

Every inode on a Unix filesystem is the same size — typically 128 or 256 bytes. This is essential: the filesystem pre-allocates a fixed-size region for all inodes, so they can be located by a simple formula (inode_table + n * sizeof(inode)).

The tension

But a file can be 4 GB, requiring ~1 million block pointers. At 4 bytes each, that's 4 MB of pointer data. Where does it live if the inode is only 128 bytes?

The clever solution

Indirection. The inode doesn't point directly at all the data blocks — it points at pointer blocks, which point at more pointer blocks, which eventually point at data. A tiny fixed-size structure can address an arbitrarily large file by chaining levels of indirection.

💡
The whole lecture in one sentence: the inode uses a small number of direct pointers plus a chain of indirect pointers to address a range of file sizes spanning six orders of magnitude — from 4 KB to 4 TB — within a 128-byte structure.
The size problem

📚 Analogy 1 · When the Card Runs Out of Space

The card points to another ledger box

The overflow

The index card has exactly 15 pointer slots (12 direct + 3 indirect). When the book grows past 12 pages, the first indirect slot activates. It points at a whole new ledger box — a pointer block — which holds up to 1024 additional shelf coordinates.

The chain

12 direct → 12 books on nearby shelves
1 single indirect → 1 box of 1024 shelf coords → 1024 books
1 double indirect → 1 box → 1024 boxes → 1024² books
1 triple indirect → 1 box → 1024 boxes → 1024 boxes → 1024³ books

The beauty

The card stays 128 bytes forever. But the actual reachable capacity is terabytes, because each level of indirection is another box that itself holds pointers. It's a branching tree, not a flat list.

The tree of pointer blocks
🔗 Analogy 2 · Index Allocation Array with Indirect Node Chains

A multi-tiered array indexing system

The array analogy
// the inode · 15 pointers
int direct[12]; // → data blocks
int* single_indirect; // → int[1024] → data
int** double_indirect; // → int*[1024] → data
int*** triple_indirect; // → int**[1024] → data
// resolving a data block at index n
if (n < 12) return direct[n];
if (n < 12+1024) return single[n-12];
if (n < 12+1024+1024²) return double[n-...];
else return triple[n-...];
// the cost
direct access: 1 disk read
single indirect: 2 disk reads
double indirect: 3 disk reads
triple indirect: 4 disk reads
The structural match

The inode layout is exactly a multi-tiered array indexing system. Static top-level row keys (12 direct pointers) reference raw data blocks, while overflow indices point to sub-arrays of secondary pointers (indirect blocks).

Why it's elegant

The lookup is a simple range check + array access. No hashing, no tree walk — just arithmetic to pick the right level and index. O(1) in the best case, O(levels) in the worst, with levels capped at 4.

The cost

Each level of indirection is an extra disk read. Accessing a byte in the last 4 GB of a 4 GB file requires: inode (already read) → triple-indirect block → double-indirect block → single-indirect block → data block. 4 reads instead of 1.

💡
The tradeoff: small files are fast (direct pointers). Large files are slower per-access but possible at all. This is why database designers and video editors historically preferred filesystems with extents (ext4, XFS) instead of indirect pointers.

📖 Core Breakdown — What Is an Inode?

A fixed-size structure per file

Formal definition

An Inode (Index Node) is a fixed-size kernel data structure dedicated to a single file instance. It stores metadata metrics: File Type, Size, Owner, Access Permissions, Timestamps, and a critical index tracking array called Block Pointers.

Where it lives

Inodes are stored in a dedicated region of the filesystem called the inode table. The table is pre-allocated at filesystem creation, with a fixed number of inodes. This is why you can run out of inodes before running out of disk space (on ext4, that's the "df -i" column).

What an inode does NOT contain

✗ The file's name (that lives in the directory)
✗ The file's contents (that lives in data blocks)
✗ The file's full path (paths are not stored in the file)

♿
Micro-Accessibility Context: this is why rename is nearly instant — the inode never changes. Only the directory entry (name → inode mapping) is updated.

📖 Core Breakdown — Direct Pointers

The first 12 blocks: one pointer, one block

The mechanism

Each direct pointer is a single disk block number. Twelve of them live directly in the inode. Each points at one data block. Resolving a direct block requires zero extra disk reads — the address is already in the inode you just read.

The capacity

12 pointers × 4 KB per block
= 48 KB of file data
covers most small config files, scripts, symlinks

The design choice

Why exactly 12? Because the inode has 15 pointer slots and the designers needed to reserve 3 for the indirect levels. 12 direct is enough for 99% of real files (config files, small scripts, HTML, PDFs) to be accessed with maximum speed.

📖 Core Breakdown — Single Indirect Pointer

One hop to 1024 more blocks

The single indirect chain
The mechanism

Inode slot #12 points at a pointer block — a full block filled with 1024 pointer values. Each of those 1024 pointers points at a data block. So this one slot covers 1024 additional data blocks.

The capacity

1024 pointers × 4 KB per block
= 4 MB of file data
+ 48 KB from direct = ~4.05 MB so far

The tradeoff

Accessing any block in this range costs 2 disk reads: the inode is already read, but the pointer block must be read to find the address of the data block. Doubling the reads for the medium file range is the price of extending reach.

💡
Why 1024? A 4 KB block ÷ 4-byte pointer = 1024 pointers per block. If pointers were 8 bytes (larger disk addresses), it'd be 512. That's why filesystem block size and pointer width matter for the capacity math.
📖 Core Breakdown — Double Indirect Pointer

Two hops to over a million blocks

The mechanism

Inode slot #13 points at a pointer block whose entries point at more pointer blocks, which finally point at data blocks. It's a two-level tree: 1024 branches per level.

The capacity

1024 × 1024 pointers × 4 KB
= 4 GB of file data
+ 4.05 MB from direct + single

The cost

Accessing a block in this range costs 3 disk reads: inode → top pointer block → mid pointer block → data block. Doubling has a price.

♿
Micro-Accessibility Context: on a 4 GB file (the maximum for double indirect coverage), the last few MB are what make it 4 GB, but the last byte still requires 3 reads. This is why video editors historically used extent-based filesystems (a single extent can cover a whole contiguous file).
The double indirect chain
📖 Core Breakdown — Triple Indirect Pointer

Three hops to 4 TB

The triple indirect chain
THE STRUCTURE
inode[14] → top block (1024 ptrs)
    ↓ each of 1024
mid block (1024 ptrs)
    ↓ each of 1024²
low block (1024 ptrs)
    ↓ each of 1024³
data block (4 KB each)
THE MATH
1024³ = 1,073,741,824 pointers
× 4 KB per block
= 4 TB of file data
THE COST
4 disk reads per data access
only reached by huge files (4 GB–4 TB)
The mechanism

Inode slot #14 points at three levels of pointer blocks. Each level has 1024 entries. The leaves of this tree are 1 billion data blocks, covering 4 TB of file data.

The size class

Only files larger than 4 GB reach this level. A movie, a virtual machine disk, a database file. The access cost is 4 reads, but for such files — where a single read is 4 KB and the file is many GB — the extra reads are amortized.

The historical note

In the original Unix filesystem (1970s), disk capacity was measured in megabytes. A 4 TB triple-indirect ceiling was unimaginably huge. Modern filesystems (ext4, XFS, Btrfs) use extents instead — a single descriptor covers a whole contiguous run, so the pointer hierarchy is much shallower.

📖 Core Breakdown — The Full Pointer Tree

One inode · four reach tiers

Tier 1 · direct

Slots 0–11 · 12 data blocks · 48 KB · 1 disk read

Tier 2 · single indirect

Slot 12 · 1 pointer block → 1024 data blocks · 4 MB · 2 disk reads

Tier 3 · double indirect

Slot 13 · 1 top → 1024 mid → 1024² data blocks · 4 GB · 3 disk reads

Tier 4 · triple indirect

Slot 14 · 1 → 1024 → 1024² → 1024³ data blocks · 4 TB · 4 disk reads

💡
The pattern: each tier multiplies the capacity by 1024× but adds one disk read to the access cost. Filesystem designers tuned the number of direct pointers (12) to balance "small files fast" against "large files reachable".

📖 Core Breakdown — The Capacity Formula

The generalized capacity equation

The variables

B = block size (e.g., 4096 bytes)
P = pointer size (e.g., 4 bytes)
N = pointers per block = B / P
D = number of direct pointers
S = 1 (single indirect slot)
X = 1 (double indirect slot)
T = 1 (triple indirect slot)

The formula

max_file_size =
  (D + N + N² + N³) × B

Plugging in the numbers

N = 4096 / 4 = 1024
= (12 + 1024 + 1024² + 1024³) × 4096
= (12 + 1024 + 1,048,576 + 1,073,741,824) × 4096
= ≈ 4.004 TB

The dominant term
direct: 12 × 4 KB = 48 KB
0.0000011% of total
single: 1024 × 4 KB = 4 MB
0.0001% of total
double: 1024² × 4 KB = 4 GB
0.1% of total
triple: 1024³ × 4 KB = 4 TB
99.9% of total
Insight: the total capacity is dominated by the largest tier. That's why removing the triple indirect pointer (as some lightweight filesystems do) cuts capacity to ~4 GB — the double indirect tier's ceiling.
🧮 Worked Example — The Canonical Calculation

12 direct + 1 single + 1 double · 4 KB blocks · 4 B pointers

The four-step calculation
Step 1 · Direct block capacity
12 blocks × 4 KB = 48 KB
Step 2 · Single indirect capacity
1 block of pointers can hold 4096 ÷ 4 = 1024 pointer addresses
1024 pointers × 4 KB blocks = 4 MB
Step 3 · Double indirect capacity
1024 × 1024 = 1,048,576 pointer addresses
1,048,576 × 4 KB = 4 GB
Step 4 · Sum all branches
48 KB + 4 MB + 4 GB
= ≈ 4.004 GB maximum file size
The canonical numbers

direct: 48 KB
single: 4 MB
double: 4 GB
total: 4.004 GB

The exam trick

Note that the answer is 4.004 GB, not exactly 4 GB. The direct and single tiers add a tiny bit on top of the 4 GB double tier — about 4 MB extra. In practice, you can round to "4 GB" for a quick answer, but the precise calculation is 4.004 GB (or 4 GB + 4 MB + 48 KB).

Unit conversion

4096 B = 4 KB
1024 × 4 KB = 4096 KB = 4 MB
1024² × 4 KB = 4,194,304 KB = 4 GB
1024³ × 4 KB = 4,294,967,296 KB = 4 TB

💻 Code — The Inode Struct in C

A simplified ext2-style inode

inode.h · conceptual
// Simplified ext2-style inode — real inode is 128 bytesstruct inode {    uint16_t mode;         // permissions + type    uint16_t uid;          // owner user id    uint32_t size;         // file size in bytes    uint32_t atime;        // access time    uint32_t mtime;        // modify time    uint32_t ctime;        // change time    uint16_t gid;          // owner group id    uint16_t nlink;        // hard link count    uint32_t blocks;       // # of 512B blocks    uint32_t i_block[15];   // ← pointer array!};
The critical field

i_block[15] — an array of 15 integers. Slots 0–11 are direct pointers. Slot 12 is the single indirect pointer. Slot 13 is the double indirect. Slot 14 is the triple indirect.

The size math

2 + 2 + 4 + 4 + 4 + 4 + 2 + 2 + 4 + (15 × 4)
= 28 bytes of metadata
+ 60 bytes of pointers
= 88 bytes used, padded to 128

The padding

Real ext2 inodes have extra fields: i_blocks, i_flags, generation, file ACL, etc. The whole thing pads to 128 bytes — the filesystem's fixed inode size. All inodes on one ext2/3/4 filesystem are the same size.

💻 Code — Resolving a Block Address

The tier-routing logic

block_lookup.c
// Given an inode and a block index, return the disk blockuint32_t inode_get_block(struct inode* ino, uint32_t logical) {    uint32_t block_size = 4096;    uint32_t ptrs_per_block = block_size / sizeof(uint32_t); // 1024    // Tier 1 — direct    if (logical < 12) return ino->i_block[logical];    // Tier 2 — single indirect    logical -= 12;    if (logical < ptrs_per_block) {        uint32_t* p = read_block(ino->i_block[12]);        return p[logical];    }    // Tier 3 — double indirect    logical -= ptrs_per_block;    if (logical < ptrs_per_block * ptrs_per_block) {        uint32_t* top = read_block(ino->i_block[13]);        uint32_t* mid = read_block(top[logical / ptrs_per_block]);        return mid[logical % ptrs_per_block];    }    // Tier 4 — triple indirect    logical -= ptrs_per_block * ptrs_per_block;    uint32_t* t1 = read_block(ino -> i_block[14]);    uint32_t* t2 = read_block(t1[logical / (ptrs_per_block*ptrs_per_block)]);    uint32_t* t3 = read_block(t2[(logical / ptrs_per_block) % ptrs_per_block]);    return t3[logical % ptrs_per_block];}
The simple part

The direct tier (first branch) is trivial — direct array access. Most file accesses hit this: small files, header reads, config files.

The work

Each read_block() call is a real disk read (or a cache hit if the block is in the page cache). For a double-indirect access, that's 2 reads just to find the data block address.

The optimization

Real kernels don't call read_block() fresh each time — the block device cache (page cache) stores recently-read pointer blocks. Walking a file sequentially touches each pointer block once, then reuses the cached contents for 1024 data block lookups.

🌍 Real World — Modern Filesystems: Extents

The indirect pointer tree was replaced by extents

The ext2/ext3 approach

Every block of a file has its own pointer in the inode's block array (via direct or indirect). This works but requires one pointer per block — a 4 GB file consumes ~4 MB of pointer data, scattered across pointer blocks.

The ext4 approach: extents

An extent is a triple: (start_block, length, physical_block). A single extent can describe a contiguous run of up to 128 MB in one record. A 4 GB contiguous file needs ~32 extents, not millions of pointers.

The tradeoff

Extents are incredibly efficient for sequential files. For highly fragmented files, they degrade back to something like the old scheme. In practice, extents are a huge win — so much so that ext4, XFS, Btrfs, and ZFS all use them.

💡
Historical context: the indirect pointer tree is what Linux used for ~20 years (ext2, ext3). Ext4 (2008) replaced it with extents. Modern filesystems (Btrfs, ZFS) go further — Btrfs stores blocks in a copy-on-write B-tree, allowing O(log n) access to any block without a fixed inode size.

🏷️ System Lexicon — Direct & Indirect Pointers
Direct Pointer
Term 03 of 04
Formal Definition

An internal inode array address slot that points directly to a real physical block holding file data bytes.

Plain Translation

( A pointer in the inode that just says "block N is this file's next block". No intermediates. )

Typical count

12 slots. Covers the first 48 KB (with 4 KB blocks). One disk read to reach the data.

Indirect Pointer
Term 04 of 04
Formal Definition

An array slot inside an inode that points to a sector block allocated exclusively to hold additional address tracking pointers.

Plain Translation

( A pointer that points to a block full of pointers. The tree grows. )

Variants

Single indirect — one hop, 1024 pointers
Double indirect — two hops, 1024² pointers
Triple indirect — three hops, 1024³ pointers

🛑 Three Student Pitfalls

What beginners get wrong about inodes

PITFALL 01
"The filename is stored in the inode"
No — the inode has no name field. Names live in directory entries (parent_dir_entry → inode_number). This is why one inode can have multiple names (hard links) and why renaming a file doesn't touch the inode at all. It's also why /proc/PID/fd/3 shows the resolved path — the kernel reconstructed it by walking backwards through directories.
PITFALL 02
"Deleting a file frees the inode immediately"
Not always. When you rm a file, nlink decreases by 1. The inode is only freed when nlink reaches 0 AND no process has the file open. So deleting a large file that's still being read by another process doesn't actually reclaim disk space until that process exits.
PITFALL 03
"More disk space = more files"
Not on ext2/ext3/ext4. Each filesystem is created with a fixed number of inodes. If you create millions of empty files (e.g., a mail server with tiny message files), you can run out of inodes before running out of disk space. That's what df -i shows — the inode usage column. Once inodes are exhausted, open(O_CREAT) fails with ENOSPC even though there's free space.

The lesson from L18

The filesystem is a complex data structure built from fixed-size units (inodes, blocks, directory entries) held together by pointers. Every operation — create, write, delete, rename — is a manipulation of these pointers and metadata.

What comes next

L19 is about what happens when a pointer update is interrupted by a crash. If the inode says "file has 5 blocks" but only 4 block pointers are updated, the file is corrupt. Journaling (write-ahead logging) solves this by recording the intended update in a safe region before executing it.

💡
The system view: every file write goes through: page cache → block layer → disk driver → platter. The inode is the bookkeeping that keeps this multilevel pipeline coherent. L19 covers how to keep it coherent even when power fails at the worst moment.

🏆 Grand Summary — L18 Key Takeaways

Four things to walk out with

01

An inode is a fixed-size structure (typically 128 or 256 B) holding one file's metadata: type, permissions, owner, size, timestamps, and a block pointer array.

02

The block pointer array has 15 slots: 12 direct, 1 single indirect, 1 double indirect, 1 triple indirect. This scales capacity from 48 KB (direct) to 4 TB (triple indirect).

03

Capacity calculation: (D + N + N² + N³) × B where N = block_size / pointer_size. With 4 KB blocks and 4 B pointers, max = 4.004 GB for a 12+1+1 layout.

04

Modern filesystems use extents instead of pointer arrays — a single record covers a contiguous run of blocks. This reduces metadata by 4–5 orders of magnitude for large sequential files.
