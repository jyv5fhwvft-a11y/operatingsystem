🎯 The Core Problem — Names vs. Blocks

The disk doesn't know about names

What the disk understands

A block device knows only about fixed-size blocks — typically 4 KB — numbered sequentially. Block 0, block 1, block 2, etc. That's the entire vocabulary.

What users understand

People work with names: /home/user/resume.pdf, /etc/passwd, readme.txt. Strings. Human-readable. Hierarchical.

The translation layer

The filesystem is the subsystem that translates name → data location. It's the abstraction layer between the messy reality of blocks and the clean interface applications expect.

💡
The specific question of this lecture: when you type cat /var/log/sys.log, what does the kernel actually do? It has to walk down the directory tree, look up names in directories, and eventually find the inode that points to the data blocks.
Two views of the same storage
📦 Analogy 1 · The Nested Treasure Boxes

A path is a set of instructions, not a single location

The setup

Imagine a set of wooden boxes nested inside each other. A file path like /home/user/resume.pdf is not a single location — it is a set of instructions.

The walk

1. The root / is the master chest on the floor
2. Open it, find an index pointing to a box labeled home
3. Open home, scan its index, find user
4. Open user, find resume.pdf
5. Its index card gives the final coordinate

The key insight

A directory is not magic. It's a special kind of file whose contents are a list of names mapped to other locations. Walking a path is just opening a series of these lookup tables.

📦 Analogy 1 · What's Actually in a Directory

A list of name → inode pairs

What a directory stores

At its core, a directory is a file whose content is a simple table. Each row is one entry. Each entry maps a human-readable name to a numeric inode number. That's it.

Why not store the data directly

Separating names from metadata has huge advantages: rename is O(1) (just edit one entry), hard links are trivial (two entries pointing to the same inode), permissions live in one place (the inode) rather than being duplicated in every directory entry.

The type field

file — regular data file
dir — another directory (recursive)
link — symbolic link (points to a path string)
dev — device node (e.g., /dev/sda)
pipe — named pipe (FIFO)

🔗 Analogy 2 · Linked List Traversing a Graph Tree

A path is a property lookup chain

The JSON analogy
{
"home": {
"user": {
"resume.pdf": "<PDF bytes>"
}
}
}
lookup("home").lookup("user").lookup("resume.pdf")
The structural match

A path resolution is exactly a nested property lookup in a JSON object — except the data lives on disk rather than in memory. Each directory is a hash table (or a small linear list) mapping names to child inodes.

Why the analogy is precise

JSON key lookup → directory entry lookup
JSON nested object → subdirectory
JSON leaf value → file inode
JSON path (a.b.c) → filesystem path (a/b/c)

Where the analogy breaks

JSON is fully in memory. Filesystem lookups can require disk reads — that's why the directory cache (dentry cache) exists in the kernel. Walking a fresh path is fast after the first time, because the kernel remembers the mapping.

📖 Core Breakdown — What a File Actually Is

A file is a linear array of bytes

The formal definition

A file is a linear array of bytes that can be created, read, written, and deleted. It has a name (via the directory entry), a size, and a position — but to the application it's just a stream of bytes accessed by offset.

The critical abstraction

The application doesn't know — or care — that the bytes are stored as blocks on a magnetic platter or in NAND cells. It just calls read(fd, buf, n) and gets n bytes back. The filesystem does the rest.

What the FS hides

Block boundaries — files can span many blocks
Block fragmentation — the FS decides layout
Physical location — platter cylinders, NAND pages
Metadata structure — inodes, directories, permissions

💡
The UNIX philosophy: "Everything is a file." Devices, sockets, pipes — all exposed through the same file API (open/read/write/close). This uniformity is one of the most powerful abstractions in systems design.

📖 Core Breakdown — A Directory Is Just a File

Whose content is a list of entries

The insight

A directory is not a special magical thing. It's a file just like any other — with a special structure. Its bytes encode a list of (name, type, inode) tuples.

What "reading" a directory means

readdir() — returns the next entry's name
lookup() — find a specific name's inode
create() — add a new name → inode entry
unlink() — remove a name entry (decrements inode's link count)

The two special entries

. is a self-reference (this directory's own inode)
.. is the parent (the containing directory's inode)
These allow relative path resolution (./file, ../other).

📖 Core Breakdown — Path Resolution

One component at a time

The algorithm
START Current dir = process's CWD
Path = "/var/log/sys.log"
STEP 1 Leading "/" means: start from root
Current dir = inode 2 (root)
STEP 2 Component = "var"
Look up "var" in root's entries → inode 45
STEP 3 Component = "log"
Look up "log" in var's entries → inode 812
STEP 4 Component = "sys.log"
Look up "sys.log" in log's entries → inode 9042
FINAL No more components
Return inode 9042 to caller
The key rules

/ — absolute path, start at root
no / — relative path, start at CWD
. — current directory
.. — parent directory
component — one name between slashes

Performance

Each component lookup is a directory scan — either a linear list, a hash table, or a tree (depending on the FS). On a fresh path with cold cache, each lookup may require a disk read. That's why the dentry cache exists in the kernel: it remembers recently-resolved paths.

The cost

For a path with N components, you need N directory lookups. Deep paths are slower. This is why web servers with very deep document roots can be slow, and why keeping the dentry cache warm is important.

📖 Core Breakdown — File Descriptors

The handle returned by open()

The formal definition

A file descriptor is a small, non-negative integer returned to user space that acts as a secure session key to access a process's open file lookup array.

Why not return the inode

Security — the process can't spoof an inode number it doesn't have permission to access
Isolation — each process has its own FD table; two processes can have fd 3 pointing to different files
State — the FD tracks the current file position (offset) per open file

The indirection

When you call read(fd, buf, n), the kernel looks up fd 3 in the current process's FD table, gets a file struct, which points to the inode, which points to the blocks. Two layers of indirection between the integer and the bytes.

📖 Core Breakdown — The Three Standard File Descriptors

Every process starts with 0, 1, 2

The convention

0 — stdin · default input stream
1 — stdout · default output stream
2 — stderr · default error stream

How they're set up

When a shell launches a program, it opens the three standard streams for the new process — usually inheriting from the shell itself (which inherited from the terminal). That's why printf works without any explicit open.

Redirection

program > out.txt works by having the shell open out.txt and dup its FD onto fd 1 before exec'ing the program. The program never knows its stdout is now a file, not a terminal.

💡
This is why the UNIX pipe works: a | b connects a's stdout to b's stdin. Same file API, different backing object. The programs don't know or care.

📖 Core Breakdown — Hard Links

Two names, one inode

The definition

A hard link is a directory entry that links an additional human file name string directly to an existing, shared historical inode number block.

What this means

Both names point to the same inode. Same data blocks. Same size. Same owner. Same permissions. Editing through one name changes the file seen through both names. Deleting one just decrements the inode's link count.

The link count

The inode has a nlink field — the number of directory entries pointing to it. The file's data blocks are only freed when nlink reaches 0 (and no process has the file open).

The limitation

Hard links cannot cross filesystems. The link and its target must be on the same physical filesystem — because the link points to an inode number, which is only meaningful within one filesystem.

Two names → one inode

Both names point to inode 9042. Deleting one only reduces nlink to 1.

📖 Core Breakdown — Soft (Symbolic) Links

A file that points to another path

Symlink → path string → target inode

The symlink stores a path string. To follow it, the kernel re-walks that path.

The definition

A soft link (also called a symbolic link, symlink, or shortcut) is a standalone file containing a text string layout representing an absolute path to a completely separate file entry destination.

What's stored

Not an inode number — a string. That's why symlinks can cross filesystems and even point to nonexistent targets ("dangling" or "broken" symlinks).

The classic danger

If you delete the target, the symlink still exists but points to nothing. Reading through it returns ENOENT. This can be used maliciously — a symlink pointing to a sensitive file, opened by a privileged process, could leak data.

♿
Micro-Accessibility Context: file managers show symlinks with a small arrow overlay. On the command line, ls -l shows the symlink name, an arrow, and the target path.

💻 Code — Opening a File in C

The four-step lifecycle

open_read.c
#include <fcntl.h>#include <unistd.h>#include <stdio.h>int main() {    // 1. Open the file — kernel walks the path, returns fd    int fd = open("/home/user/resume.pdf", O_RDONLY);    if (fd < 0) {        perror("open");        return 1;    }    // 2. Read from the fd — bytes are copied into buf    char buf[4096];    ssize_t n = read(fd, buf, sizeof(buf));    if (n < 0) {        perror("read");        close(fd);        return 1;    }    printf("Read %zd bytes\n", n);    // 3. Close — releases the fd slot for reuse    close(fd);    return 0;}
The four steps

1. open() — path → fd number
2. read() — fd → bytes into buffer
3. (process the bytes)
4. close() — fd slot freed

What open() actually does

Walks the path (L17's whole subject), checks permissions on each component, finds the final inode, creates a struct file, inserts it into the FD table, and returns the smallest free index.

What read() actually does

Reads from the file's current offset, uses the inode's block pointers to find data blocks, copies bytes into the user buffer, and advances the offset. The offset lives in the FD, not the inode — each open gets its own position.

💻 Code — The Path Resolution Algorithm

A conceptual path walk

path_walk.c · conceptual
// Conceptual path resolution — kernel does this in Cinode_t* resolve_path(const char* path) {    inode_t* cur;    // Absolute path starts at root; relative at CWD    if (path[0] == '/') {        cur = get_root_inode();       // inode 2        path++;  // skip leading '/'    } else {        cur = current()->cwd;    }    // Split into components and look up each one    char component[256];    while (next_component(&path, component)) {        // Look up this name in the current directory        inode_t* next = dir_lookup(cur, component);        if (!next) return NULL;  // ENOENT        if (!has_exec_permission(next)) return NULL; // EACCES        cur = next;    }    return cur;  // the final inode}
The three key operations

get_root_inode() — always inode 2 on standard Unix
next_component() — peels off one name between slashes
dir_lookup() — scans the directory for the matching name

The permission check

Note the has_exec_permission check. To traverse a directory (not read it, just pass through), you need execute (x) permission on the directory. That's why you can sometimes cd into a directory but can't ls its contents.

The caching shortcut

This is the conceptual algorithm. Real kernels (Linux specifically) use the dentry cache — a hash table mapping (parent_inode, name) → child_inode. If the lookup is cached, the whole "walk the directory" step is skipped entirely.

Version-independent soname. Programs link against libc.so.6, and the actual library file has the precise version number.

🛑 Three Student Pitfalls

What beginners get wrong about files and paths

PITFALL 01
"Deleting a file frees its blocks immediately"
Not always. When you rm a file, the kernel removes its directory entry (decrements nlink). The data blocks are only freed when nlink reaches 0 and no process has the file open. This is why rm on a huge file doesn't always free space instantly — if a process still has it open, the space stays allocated until that process closes it.
PITFALL 02
"Symlinks are the same as shortcuts on Windows"
Similar idea, very different mechanics. Windows "shortcuts" (.lnk files) are consumed by the Windows shell — the filesystem doesn't understand them. Unix symlinks are a first-class filesystem object — the kernel follows them transparently, and every program sees the target as if it were the original file. That's why symlinks "just work" with tools that never knew shortcuts existed.
PITFALL 03
"The path to a file is stored in the file"
Files don't know their own names. An inode has no "name" field — only metadata and block pointers. The name lives in the parent directory entry, not the file. That's why a single file can have multiple names (hard links) and why renaming a file is just editing a directory entry — the inode doesn't change at all.
🎭 Interactive Activity — The Human Path Traversal Relay

Four students, four directories, one path

The setup

Assign four students to act as directories: root, home, user, docs. Hand each a small index card listing their directory's entries — e.g., "root contains home→45, etc→30, var→60".

The task

Have a fifth student (the "application") ask: "Locate /home/user/docs/lab.c".

1. Root student looks at their card, finds "home" → announces "go to inode 45"
2. Home student looks at their card, finds "user" → "go to inode 812"
3. User student finds "docs" → "go to inode 9201"
4. Docs student finds "lab.c" → "go to inode 9042"

The observation

Every student made exactly one lookup. The path was resolved one component at a time, in sequence, from root to leaf. If any lookup failed, the whole path would fail. That's path resolution in one sentence.

💡
Debrief: ask "what if the same path were requested again?" Answer: the lookups would be cached in the students' short-term memory (dentry cache), so the second traversal would skip the "look at my card" step entirely.

The VFS is the layer that makes everything else pluggable. Ext4, XFS, Btrfs, NFS, FAT32 — all present the same interface (open, read, write, stat, mkdir) to applications. The VFS handles path resolution uniformly. Applications never care which filesystem is underneath.

🏆 Grand Summary — L17 Key Takeaways

Four things to walk out with

01

A file is a linear byte array. A directory is a file whose contents are a table of (name, type, inode) entries. Walking a path means opening one directory at a time.

02

Path resolution splits the path on "/" and looks up each component in sequence, starting from root (absolute) or CWD (relative). The dentry cache makes repeated lookups nearly free.

03

File descriptors are small integer handles into a per-process FD table. Every process starts with 0=stdin, 1=stdout, 2=stderr, and open() returns the lowest free fd.

04

Hard links share an inode (two names, one file). Soft links store a path string (a shortcut that must be re-walked). They differ in cross-filesystem support, target-deletion behavior, and inode count.
