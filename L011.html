The Core Question of L11

L10's base-and-bound model required each process to occupy a single contiguous physical region. That caused fragmentation and made sharing impossible. What if we chop memory into fixed-size pages and let any page live anywhere?

🎯 The Problem Paging Solves

Contiguous allocation fails as memory fragments

What base-and-bound required

Each process needed a single contiguous region of physical memory. Its base register pointed at the start, its bound register capped the size.

What went wrong

After processes come and go, memory fills with gaps — small free regions between allocated ones. A new process needing 200 MB might fail to load even though 300 MB is free, because it's split across multiple gaps.

Paging's radical answer

Give up on contiguity entirely. Split both virtual and physical memory into fixed-size pages. A program's pages can live anywhere in physical memory — no gaps, no fragmentation, no contiguous requirement.

💡
The trade: you swap the nightmare of external fragmentation for a much smaller, bounded internal fragmentation — and in return you get sharing, dynamic growth, and the entire modern memory management stack.

📖 Analogy 1 · The Phonebook Indexed Ledger

The book is torn into loose pages and scattered

The setup

Imagine trying to read a giant encyclopedic novel that has been completely ripped apart, separated into single loose pages, and scattered randomly across different drawers in a room.

The problem

You want to read Chapter 1, then Chapter 2, then Chapter 3 — in order. But each chapter's physical location is somewhere in a drawer, and you have no idea which drawer holds which page.

The solution

A single index card — the page table. It says: "Logical page 0 is in drawer 3, page 1 is in drawer 7, page 2 is in drawer 1." With that card, you can find any page instantly, even though the physical pages are scattered.

💡
The book is written in logical order (page 0, 1, 2, …). The index card maps logical order to physical location. That's exactly what a page table does for memory.

The structure

Each entry is a single number. For a small system with 5 pages, the page table has 5 entries. For a 32-bit system with 4 KB pages, it has ~1 million entries — which is why real page tables are multi-level.

What each entry contains

Frame number — where the page lives
Present bit — is it currently in RAM?
Permission bits — read/write/execute?
Dirty bit — has it been modified?
Accessed bit — recently used?

Where it lives

The page table lives in kernel memory — specifically in physical memory, with a pointer stored in the PCB. The MMU reads it during translation. The program never sees it.

🧭 System Cohesion — Where L11 Sits

The modern memory mechanism replaces base-and-bound

Relies On · L05 (Process Anatomy)

Every independent process PCB structure must preserve a pointer to its own unique isolated physical Page Table location. Without the PCB's mm_struct, the kernel has nowhere to store where this process's page table lives.

Relies On · L10 (Base-Bound)

The vocabulary (logical, physical, translation) and the motivation (isolation) come from L10. Paging is a different mechanism for the same goal.

Feeds Into · L12 (TLB Acceleration)

Address translation requires a nested memory access path — the MMU must read the page table before it can do the actual access. This doubles the cost of every memory reference, necessitating a specialized hardware cache (TLB) to maintain high-speed throughput.

Feeds Into · L13 (Virtual Memory)

Once memory is paged, pages can be swapped to disk and loaded on demand. That's the foundation of virtual memory, demand paging, and page replacement.

💡
The trajectory: L10 (contiguous) → L11 (paged) → L12 (fast paging via TLB) → L13 (pages on disk via virtual memory). Each step removes a limitation of the previous one.

📖 Core Breakdown — The Paging Insight

Split memory into fixed-size chunks on both sides

Virtual side

A process's virtual address space is chopped into fixed-size chunks called pages. Every page is the same size (typically 4 KB). Page 0 is the first 4 KB, page 1 is the next 4 KB, and so on.

Physical side

Physical RAM is chopped into the exact same size chunks called frames. Frame 0 is the first 4 KB of RAM, frame 1 is the next 4 KB, and so on.

The mapping

A page table entry says: "virtual page 3 lives in physical frame 7." Since pages and frames are the same size, this mapping is one-to-one at page granularity — no offsets in the table.

The magic

Virtual page 0 can live in frame 5, virtual page 1 in frame 2, virtual page 2 in frame 7. Pages are scattered — but the page table remembers where each one is.

💡
Why same-size matters: because pages and frames are equal size, a page's offset within itself is preserved in the physical address. That's the trick that makes translation cheap — see slide 11.

Page

A fixed-size contiguous block of virtual address space allocated by the compiler and operating system kernel. Numbered 0, 1, 2, … within the process's address space.

Frame

A physical, hardware-wired block of real RAM storage matching the exact byte dimensions of a system page slot. Numbered 0, 1, 2, … globally across all of RAM.

The size

Typically 4 KB on x86-64, ARM, and RISC-V. Some systems use 16 KB or 64 KB. The page size is fixed at boot and never changes — that's what makes frame allocation trivial.

📖 Core Breakdown — The Address Split

A virtual address is just two numbers glued together

The split

A virtual address is divided into two components: a Page Number (p) and an Offset (d). The offset identifies the byte within the page; the page number identifies which page.

Why this split matters

The page number is used as an index into the page table (lookup). The offset is used unchanged in the final physical address. So translation only modifies the page-number portion of the address.

The bit math

If pages are 4 KB = 212 bytes, the offset needs 12 bits. The remaining bits (32 − 12 = 20 on a 32-bit system) are the page number. 220 pages × 4 KB = 4 GB virtual space — full 32-bit addressability.

💡
The pattern: split the address, look up the high bits in a table, keep the low bits as-is. This is exactly what base-and-bound did (add base, keep offset) — but the "base" is now a per-page value from a table instead of one global register.

📖 Core Breakdown — The Translation Step

Look up the frame. Keep the offset.

Step 1

MMU extracts the page number p from the virtual address.

Step 2

MMU reads page_table[p] to get the corresponding frame number f.

Step 3

MMU constructs the physical address by concatenating f (frame number) and d (the original unchanged offset).

The critical detail

The offset d is not translated. It's copied byte-for-byte from the virtual address into the physical address. Because pages and frames are the same size, the byte-within-page position is preserved.

♿
Micro-Accessibility Context: if you know the byte is 100 bytes into virtual page 3, it'll be 100 bytes into whatever physical frame page 3 maps to. The offset is invariant.

Why it works

Pages and frames are the same size. If a byte is at position 100 within virtual page 3, it's at position 100 within whatever physical frame page 3 maps to. The position within the page is preserved.

What this saves

If the offset needed translation too, the page table would need an entry per byte instead of per page. For a 4 GB address space with 4 KB pages, that's 4 billion entries instead of 1 million. The invariance is what makes paging feasible.

The hardware

The MMU literally copies bits [0..11] from the virtual address into the physical address without modification. Only bits [12..31] are replaced with the frame number from the page table. This is done in one clock cycle.

💡
Internal fragmentation lives here: if a program only needs 100 bytes of its last 4 KB page, 3996 bytes are wasted inside the page. That's the trade — but it's bounded to one page per allocation, not the whole memory.
📖 Core Breakdown — Eliminating External Fragmentation

Why paging makes external fragmentation impossible

The key claim

Every free frame is interchangeable with every other free frame. A 4 KB page can go into any 4 KB free slot — no contiguous requirement, no fitting problem.

Why it eliminates fragmentation

External fragmentation exists when free memory is split into gaps that are too small individually to be useful. With paging, every gap is a frame. If a frame is free, it can hold one page. There is no "too small to use" — the gap itself is the unit.

The allocation algorithm

When a process needs a new page: pick any free frame, insert the page, record the mapping in the page table. That's it. O(1) if you keep a free-frame list.

💡
External fragmentation is gone forever. That's the entire reason paging won. Every modern OS uses it — no exceptions.

📖 Core Breakdown — The New Cost: Internal Fragmentation

External is gone. Internal takes its place.

What internal fragmentation is

When a process requests a buffer that doesn't completely fill its final allocated fixed-size page block, the unused bytes are wasted inside the last page. Nothing else can use that leftover space.

The magnitude

On average, a process wastes half a page at the end of its last page. With 4 KB pages, that's 2 KB per process. With 500 processes, 1 MB total — negligible.

Why it's acceptable

Compare to external fragmentation: 30–50% of memory wasted versus <1% with paging (typically). This is why paging won — the cost is bounded, predictable, and small.

♿
Micro-Accessibility Context: a 3 KB file stored in 4 KB pages wastes 1 KB (25% of the last page). A 1 KB file wastes 3 KB (75%). The average is 50% of one page per allocation.

📖 Multi-Level Page Tables — Why One Level Isn't Enough

The size problem with single-level tables

The math for a 32-bit system

32-bit address space · 4 KB pages
= 232 / 212 = 220 = 1,048,576 pages
× 4 bytes per page table entry
= 4 MB per process

Why this is unacceptable

With 500 processes, that's 2 GB just for page tables — before any actual program data. On a system with 4 GB of RAM, half the memory would be page tables.

The solution: multi-level

Split the page number into multiple pieces. Use one level for the first chunk, another for the next, and so on. Most entries are unused, so most sub-tables never need to exist.

💡
The insight: a process's virtual address space is sparse — most of the 4 GB is empty. A single-level table wastes space because it has an entry for every possible page, even unused ones. Multi-level lets unused sub-trees be allocated lazily or not at all.

📖 Multi-Level Page Walk — The 3-Step Lookup

Two or three memory reads before the actual data access

The bit split on 32-bit x86

VA[31..22] → page directory index (10 bits)
VA[21..12] → page table index (10 bits)
VA[11..0] → offset (12 bits)

The walk

1. Read PD entry (memory access #1)
2. Read PT entry (memory access #2)
3. Combine frame + offset → actual access (memory access #3)

The cost

Every memory access now costs 3 memory reads instead of 1. On a modern 64-bit system with 4-level paging, it's 4–5 reads per access. That's a 3–5× slowdown — unacceptable without caching.

💡
This is exactly why the TLB exists (L12). It caches the final translation result, so most accesses skip the walk entirely.

💻 Code — Address Translation in C

The exact bit math the MMU performs

translate.c · paging logic
#define PAGE_SIZE  4096
#define PAGE_SHIFT 12       // log2(PAGE_SIZE)#define OFFSET_MASK 0xFFF    // low 12 bits#define PAGE_MASK   (~0xFFF) // high bits// Basic translation: virtual → physicaluint64_t translate(uint64_t va, uint64_t* page_table) {    // Step 1: extract the page number and offset    uint64_t page_num = va >> PAGE_SHIFT;    uint64_t offset   = va & OFFSET_MASK;    // Step 2: look up the frame number    uint64_t pte = page_table[page_num];    // Step 3: check present bit    if (!(pte & PRESENT)) return -1;  // page fault    // Step 4: extract frame + build physical address    uint64_t frame = pte & PAGE_MASK;    return frame | offset;}
The two bit operations

>> 12 extracts the page number (shifts out the offset).
& 0xFFF extracts the offset (masks out the page number).

The final combination

frame | offset — a bitwise OR, because frame and offset don't overlap. Frame is in the high bits, offset is in the low bits.

The real hardware

This exact math runs in the MMU, in hardware, at wire speed. A real CPU does this in one clock cycle for the offset, and the page table lookup in parallel with the memory access. The C code shown is a conceptual model — real hardware is faster but does the same thing.

💡
Why multi-level in the code? The code above is single-level for clarity. Real implementations do the multi-level walk — but the bit math for extracting page number and offset is identical.
📖 Page Table Entry — What Each Entry Stores

More than just a frame number

A typical x86 page table entry
FRAME NUMBERbits 12-31 · physical address
Ppresent
R/Wread/write
U/Suser/supervisor
FRAME NUMBER — where the page lives in physical RAM. This is the value the MMU appends with the offset.
PRESENT (P) — is the page currently in RAM? If 0, the access triggers a page fault and the kernel loads it from disk.
READ/WRITE (R/W) — is the page writable? If 0 and the process tries to write, the MMU raises a protection fault.
USER/SUPERVISOR (U/S) — can user-mode code access this page? If 0, only kernel code can.
Other bits worth knowing

Accessed (A) — set by hardware when the page is read/written. Used by page replacement algorithms.
Dirty (D) — set by hardware when the page is written. Tells the kernel it must write back to disk on eviction.
NX/XD — no-execute. Prevents code execution from this page (security).
Cache-disable — bypass cache for this page (memory-mapped I/O).

Why so many bits

The page table is the entire security enforcement for memory access. Every permission check, every access control, every "you can't write there" comes from one of these bits. It's the most consequential data structure in the system.

Where PTE checks meet the barrier

The U/S bit is what makes Ring 3 unable to access kernel memory. Combined with the Ring 0/Ring 3 hardware barrier from L02, this creates two-layer protection: the CPU privilege ring and the per-page permission.

( The directory that says "virtual page X is in physical frame Y." One per process. )

In kernel memory (physical RAM). The CR3 register holds the base address of the current process's page table.

🧭 System Cohesion — Full Module 3 View

L11 is the pivot point of memory management

Relies On · L05 (Process Anatomy)

Each PCB's mm_struct points to that process's page table. Without per-process page tables, every process would share the same mapping — no isolation.

Relies On · L10 (Base-Bound)

Provides the vocabulary (logical, physical, translation) and the isolation goal. Paging is a replacement mechanism, not a different goal.

Feeds Into · L12 (TLB)

Every access now requires a page table walk (extra memory reads). The TLB is a hardware cache that skips the walk for recently-used translations.

Feeds Into · L13 (Virtual Memory)

Once memory is paged, pages can be evicted to disk. That's the foundation of virtual memory, demand paging, and page replacement algorithms.

The compounding effect

L10 → gave you translation + isolation
L11 → added fragmentation elimination + sharing
L12 → added speed via caching
L13 → added the disk (huge virtual address spaces)
Each layer makes the previous layer's limitations disappear.

🏆 Grand Summary — L11 Key Takeaways

Four things to walk out with

01

Paging splits virtual and physical memory into fixed-size units. Any virtual page can live in any free physical frame. No contiguity requirement.

02

A virtual address is split into page number + offset. The page number indexes the page table to find a frame. The offset is copied unchanged.

03

Paging eliminates external fragmentation entirely. It introduces a much smaller internal fragmentation — bounded to at most one page per allocation.

04

Real systems use multi-level page tables to avoid the size cost of single-level tables. That adds memory reads per access, which is why the TLB (L12) exists.
