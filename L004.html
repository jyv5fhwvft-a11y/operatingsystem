🔰 🏛️ L04 · The Boot Process

Four stages between pressing power and reaching the login prompt

Chronologically sequence the four structural stages that occur between a user pressing a computer's physical power-on switch and the arrival of a user-space login prompt.

The Core Question of L04

At the instant power hits the CPU, no operating system exists in RAM. There is no file system reader, no driver, no scheduler. How does the machine bootstrap itself from cold silicon into a fully running multi-process system?

🎯 The Boot Paradox — Why Booting Is Not Trivial

The CPU cannot read a file system. That's the whole problem.

What the CPU can do the instant power hits

Fetch the next instruction from a fixed physical memory address. That's it. No file reading, no disk I/O, no device initialization — nothing but "read the next instruction."

What it needs to do

Load the kernel binary from disk, initialize the memory manager, mount a root file system, and hand off to user space. But all of that requires code that isn't loaded yet.

The resolution — a bootstrap chain

Each stage is a small, simple program whose only job is to load the next, more complex stage. Stage 1 doesn't need to understand file systems — it just needs to know how to read the boot sector of a disk. Stage 2 doesn't need to understand memory paging — it just needs to load the kernel image and jump to its entry point.

💡
This is why it's called "bootstrapping" — literally "pulling yourself up by your bootstraps". Each stage has just enough capability to load the next stage, no more.
Cold-start capability

CPU CAN DO

  • Fetch instruction from a fixed ROM address
  • Execute simple machine code
  • Jump to a hardcoded memory address
  • Read/write specific I/O ports

CPU CANNOT DO (yet)

  • Read files from disk
  • Understand a file system
  • Initialize device drivers
  • Set up virtual memory

Every stage in the boot chain adds capability the CPU didn't have the instant before. Stage 1 → knows disk sectors. Stage 3 → knows file systems. Stage 4 → knows user-space.

🏃 Analogy 1 · The Multi-Stage Relay Race

Four runners, four very different athletic builds

Runner 1 · UEFI/BIOS

Tiny and fast. Only job: check the track is clear and pass the baton. Physically very small amount of code — a few KB in motherboard flash.

Runner 2 · Bootloader

Grabs the baton, sprints out to find the heavyweight champion sleeping in the locker room (the kernel) and wakes them up. Can read file systems — unlike Runner 1.

Runner 3 · Kernel Core

Takes over the track, sets up the entire stadium infrastructure — memory, drivers, devices. The biggest and slowest runner.

Runner 4 · User Space / Init

Finally opens the stadium doors for the spectators (the users). Draws the login prompt, spawns services.

💡
Crucial detail: Each runner drops out completely once their handoff finishes. UEFI code doesn't keep running after the bootloader takes over — its memory gets reclaimed. Same for the bootloader after the kernel starts.

⚙️ Analogy 2 · The Compiler Toolchain Pipeline

Deterministic sequence. Each stage hands off a more capable artifact.

The structural match

The boot process is a deterministic sequence of bootstrap execution transitions where each loader routine has just enough hardcoded primitives to read, verify, map, and jump into the entry-point memory address of the next, more complex software layer.

The compiler comparison

Just like gcc pipes source → preprocessor → compiler → assembler → linker → executable, the boot process pipes ROM → UEFI → bootloader → kernel → user space.

What both share

Each stage's output is more usable than its input. Each stage is a complete, standalone program. Each transition involves verifying the input (checksum, magic number, signature) before proceeding.

📖 Core Breakdown — The Four Stages, One Overview

Each stage hands the baton to a more capable successor

Stage 1 · UEFI / BIOS

Code executes from a read-only flash chip on the motherboard. Runs a Power-On Self-Test (POST) to verify physical RAM and hardware integrity.

Stage 2 · Bootloader

UEFI locates a designated boot sector on a storage drive and loads a small program (like GRUB) into RAM. This bootloader's sole job is to locate the compiled kernel binary image on the disk.

Stage 3 · Kernel Initialization

The bootloader loads the kernel into memory and jumps to its entry address. The kernel initializes device drivers, constructs virtual memory page tables, and mounts the root file system.

Stage 4 · Init System

The kernel launches the very first user-space process (/sbin/init or systemd), which spins up background services and draws the login prompt.

🔬 Stage 1 — UEFI/BIOS · The Power-On Self-Test

Verify the hardware before trusting anything to run on it

What POST actually does

Before it hands control to the bootloader, UEFI/BIOS runs a hardware diagnostic on the machine. It walks through the CPU, RAM, storage controllers, and input devices in order, verifying each one is present and functional.

The interesting part — RAM verification

POST writes test patterns to every RAM cell, reads them back, and compares. If a cell doesn't match, the machine beeps (the classic "memory error beep code") rather than proceeding to load the OS.

If POST fails

The machine halts before any OS code runs. The famous beep sequences are the failure codes — long/short patterns that indicate which hardware failed. Modern UEFI shows a graphical error screen instead.

💡
The misconception: POST does not initialize drivers or load files. It only checks hardware presence and basic health. The OS hasn't started yet.

📖 Stage 1 — Where the Code Physically Lives

Firmware is permanent, unprivileged by the OS

The physical substrate

UEFI/BIOS lives in a flash memory chip on the motherboard — a small chip that retains its contents even when the machine is fully powered off. On modern systems it holds roughly 16–32 MB of code.

Why it must be non-volatile

Because on the first power-on there is no OS, no loaded driver, no file system — the only code the CPU can run is what's already physically wired into the address space via that flash chip.

Where the CPU looks

On x86, the CPU's reset vector points to physical address 0xFFFFFFF0 at power-on. That address is mapped to the firmware chip. The first instruction always comes from firmware — no exceptions.

♿
Micro-Accessibility Context: "UEFI" (modern) vs. "BIOS" (legacy) — the mechanism is the same, but UEFI supports larger disks (GPT), Secure Boot, and a much richer pre-boot environment.
The reset vector → firmware entry
🔬 Stage 2 — The Bootloader (GRUB)

The disk-seek stage — finding the kernel on storage

What the bootloader does

UEFI locates a designated boot sector on a storage drive and loads a small program (like GRUB) into RAM. This bootloader's sole job is to locate the compiled kernel binary image on the disk.

Why it can do more than UEFI

GRUB is a real program with filesystem drivers built in. It can read /boot/vmlinuz-linux — a file on an ext4 partition. UEFI cannot. That's the entire capability jump.

The choreography

GRUB parses its config file (/boot/grub/grub.cfg), presents a boot menu, reads the selected kernel image and initramfs into memory, and jumps to the kernel's entry point.

💡
On modern UEFI systems: the bootloader is itself loaded from an EFI System Partition (ESP) as an .efi executable. On legacy BIOS, it comes from the first 512-byte sector of the disk (the MBR).
Live · The arm seeking the kernel on disk
seeking /boot/vmlinuz-linux…

GRUB physically reads disk sectors — something UEFI/BIOS is incapable of doing.

📖 Stage 2 — What GRUB Actually Loads

Two files enter memory. One starts running.

The two-file handoff
Why two files, not one?

The initramfs is a tiny in-memory file system that contains just enough drivers to mount the real root filesystem. Chicken-and-egg: to load the ext4 driver from disk, you need a filesystem reader — but the filesystem reader lives on that same disk.

The chicken-and-egg resolution

The kernel ships with the initramfs already in RAM. It uses it as a temporary root, loads the real drivers, mounts the actual root filesystem, and then "switches root" (pivot_root) to the real one.

The kernel command line

GRUB also passes command-line arguments to the kernel — things like root=/dev/sda2 that tell it which partition to mount as the real root.

🔬 Stage 3 — Kernel Initialization

The biggest stage — turning the machine into a real OS

What the kernel does on entry

The bootloader has jumped to the kernel's entry point. The CPU is now executing kernel code with full privilege. The kernel does an enormous amount of work here — this is the longest boot stage on most systems.

The work list (roughly ordered)

1. Set up protected-mode / long-mode segments
2. Initialize the memory manager · build page tables
3. Unpack the initramfs
4. Probe and initialize device drivers
5. Mount the real root filesystem
6. Launch the init process

The observable proof

Every line printed on your screen during boot (the "wall of text") is a printk() call from within this stage. When you see "kernel panic", it happened here.

📖 Stage 3 — The Ring 0 → Ring 3 Handoff

This is the one moment the boundary gets crossed downward

The transition, precisely

The kernel calls execve("/sbin/init", ...). Because init is a normal ELF binary, the kernel must drop out of Ring 0 to run it. The CPU's CPL bits flip to 3, and user-space execution begins.

Why this is unusual

Every syscall in L03 involved Ring 3 → Ring 0. Boot's final act is the reverse — Ring 0 → Ring 3, taking user-space code into existence for the first time on this machine.

The state at this moment

✓ Virtual memory mapped
✓ Device drivers ready
✓ Real filesystem mounted
✓ Kernel scheduler running
✓ Exactly one user process — PID 1

💡
Notice what's missing: there are no other user processes, no shell, no login prompt, no desktop. Those come from PID 1 in Stage 4.
The one downward transition
🔬 Stage 4 — The Init System (PID 1)

The genetic ancestor of every process that will ever exist

What PID 1 is

The kernel launches the very first user-space process — /sbin/init or its modern replacement systemd. This process gets PID 1 by definition — the first PID ever assigned on this boot.

Its responsibilities

Spawn all other system services, handle orphaned child processes, and present the login interface. Every other process on the system is either a direct or indirect descendant of PID 1.

Why "systemd" replaced "init"

Traditional SysV init ran services strictly sequentially. systemd runs them in parallel with dependency tracking — a huge reduction in boot time (from minutes to seconds).

💡
If PID 1 dies, the kernel panics. That is the only process whose death is guaranteed to halt the entire machine — a direct consequence of the "no process above it to adopt children" rule.

📖 Stage 4 — The Full Service Cascade

From "PID 1 exists" to "you can log in"

The service dependency graph
The dependency order

Notice the order matters: udev must be up before it can create device nodes; networkd must be up before SSH can listen on a socket. systemd tracks these dependencies as a graph and starts independent services in parallel.

What you actually see

On a modern Linux desktop, this all happens in about 2–8 seconds after Stage 3 completes. Traditional SysV-init took 30–60 seconds for the same work because it ran everything sequentially.

Targets, not runlevels

systemd uses "targets" (multi-user.target, graphical.target) instead of SysV runlevels. Each target is a set of services that must be active for it to be considered "reached".

🔗 The Handoff Chain — Every Stage Drops Out

Only the last stage survives its handoff

Live · Stage exits as successor takes over
01UEFI / BIOSdrops out
02Bootloaderdrops out
03Kerneldrops out
04init / systemdruns forever
What "drops out" actually means

After UEFI hands off to the bootloader, UEFI code is no longer executing. Its memory may still be reserved (some firmware tables live on for ACPI), but its job is complete. Same for the bootloader once the kernel starts.

Why this pattern is elegant

Each stage's design can be perfectly minimal. UEFI doesn't need filesystem drivers because it never has to read a file. The bootloader doesn't need to manage processes because it never has to schedule anything. Each stage does exactly one thing.

🏷️ System Lexicon — Firmware & Loader
UEFI
Term 01 of 04
Formal Definition

Unified Extensible Firmware Interface — modern motherboard software that initializes hardware and bootstraps the operating system bootloader.

Plain Translation

( The permanent code burned into the motherboard that wakes up the hardware and points the way to the OS loader. )

Replaces

Legacy BIOS — same role, but supports GPT disks, Secure Boot, and a richer pre-boot environment.

Bootloader
Term 02 of 04
Formal Definition

A lightweight intermediate utility (e.g., GRUB) responsible for loading the core operating system kernel into memory.

Plain Translation

( The middleman whose entire job is: find the kernel file on disk, load it into RAM, and jump to it. )

Examples

GRUB (Linux) · systemd-boot · Windows Boot Manager · rEFInd

🏷️ System Lexicon — Process & Diagnostics
systemd / init
Term 03 of 04
Formal Definition

The primordial user-space process (PID 1) responsible for spawning and managing all system daemons and shell interfaces.

Plain Translation

( The very first user-space program to run. Everything else on the machine is its child, grandchild, or further descendant. )

Why "PID 1" is special

If PID 1 dies, the kernel panics — there's no higher process to adopt orphans. This is why systemd restarting itself is a critical operation.

POST
Term 04 of 04
Formal Definition

Power-On Self-Test — the initial hardware diagnostic routine run by motherboard firmware to verify system readiness.

Plain Translation

( The "is everything plugged in?" check the firmware does before it trusts the machine to run an OS. )

If it fails

Beep codes (legacy BIOS) or on-screen error (UEFI). The machine halts before any OS code executes.

🧪 Practical Example — The GRUB Config Walkthrough

What the bootloader actually reads

Live · /boot/grub/grub.cfg parsing
cat /boot/grub/grub.cfg
# Auto-generated by grub-mkconfig menuentry 'Arch Linux' { linux /boot/vmlinuz-linux root=/dev/sda2 rw initrd /boot/initramfs-linux.img } # ... other boot options ...

Four lines of config. Two files loaded. One jump. That's Stage 2.

Line 1 · menuentry

Declares a boot option. On a multi-boot machine, this shows up in the GRUB menu as a selectable entry.

Line 2 · linux

Points to the compiled kernel image (vmlinuz-linux) and passes the kernel command line: root=/dev/sda2 rw.

Line 3 · initrd

Points to the initial RAM disk (initramfs-linux.img). GRUB loads both files into memory before jumping.

💡
Reality check: On a modern UEFI system with systemd-boot, this config is much simpler — just a text file listing kernel + initrd paths, with no scripting language at all.
⏱️ Real Numbers — Where the Time Actually Goes

The boot time is dominated by stage 4

The distribution is not what you'd expect

Most people assume the kernel is the slow part. It isn't. On modern systems, the vast majority of boot time is spent in user space, waiting for services to spawn and be ready.

Why systemd shortened it

Traditional init ran services sequentially: "wait for network, then start SSH, then start the desktop". systemd runs them in parallel and tracks dependencies as a graph — an order-of-magnitude improvement.

What you can optimize

Disabling unused services (Bluetooth on a desktop, print services on a laptop) is often the single biggest boot-time win available to a user.

Live · Typical boot time distribution
Stage 1 · UEFI/BIOS POST~2.0 s
Stage 2 · Bootloader~1.0 s
Stage 3 · Kernel init~3.5 s
Stage 4 · systemd services~9.5 s

Rough numbers for a typical modern laptop. Exact figures vary enormously by hardware and enabled services.

🛑 Where Boots Actually Fail

Four failure modes, four different error signatures

Stage 1 Failure

Firmware / POST failure

Machine beeps (or shows a firmware error screen) before any OS code runs. Causes: bad RAM, disconnected boot disk, dead CMOS battery. The OS never even begins to load.

Stage 2 Failure

Bootloader error

"GRUB rescue>" prompt or "no such device" message. Causes: kernel image deleted, grub.cfg corrupted, disk ID changed. The bootloader can't find the kernel.

Stage 3 Failure

Kernel panic

Wall of kernel messages ending in "Kernel panic - not syncing". Causes: missing initramfs, incompatible driver, corrupted root filesystem. The kernel initialized but couldn't proceed.

Stage 4 Failure

Degraded boot

Machine boots but services fail to start. "Failed to start X service" in journalctl. Causes: missing binaries, config errors, permission issues. The OS runs but incompletely.

💡
Diagnostic rule of thumb: if the screen is black and the machine beeps, it's Stage 1. If you see "GRUB" text, Stage 2. If you see kernel messages, Stage 3. If you get a login prompt but services fail, Stage 4.
🛡️ Secure Boot — The Modern Chain-of-Trust Extension

Every stage now cryptographically verifies the next

The chain of trust

UEFI Secure Boot adds a verification step at each handoff. Before Stage 2 is allowed to execute, UEFI checks its cryptographic signature against a list of trusted public keys stored in firmware. If the signature doesn't match, the boot is refused.

What this blocks

Bootkits and rootkits — malware that tries to insert itself into the boot chain before the OS runs. Without Secure Boot, a compromised bootloader can hide from every antivirus on the running system.

The Linux complication

Most Linux distributions ship a signed shim — a tiny signed bootloader that then loads the (potentially unsigned) main kernel. This lets Linux boot on Secure Boot machines without every kernel being signed by Microsoft.

♿

🎭 Interactive Activity — The Boot Time Synchronization Challenge

Every student reboots. All timers start together.

The setup

Have every student close their laptop and shut it down completely. Prepare a stopwatch app on their mobile phones. On the count of three, everyone presses their power button simultaneously.

The measurement

Instruct them to stop the timer the exact millisecond their graphical login screen or desktop draws. Record each student's total time on the board.

The analysis

Compare the times. Ask: "Where did the time go?" Look for correlations — SSD vs. HDD, few enabled services vs. many, minimal desktop environment vs. heavy GUI. The variance is enormous.

💡
Debrief: Ask which stage dominated each student's time. The answer is almost always Stage 4. This is the whole reason systemd was invented.

🏆 Grand Summary — L04 Key Takeaways

Four things to walk out with

01

Booting is a bootstrap chain: each stage has just enough capability to load the next. No single stage understands the whole picture — that's the design.

02

The four stages are: UEFI/BIOS POST → Bootloader (GRUB) → Kernel Init → Init System (systemd). Each hands off control and drops out except the last.

03

Boot failures are diagnosable by stage: beeps = Stage 1, GRUB errors = Stage 2, kernel panic = Stage 3, service failures = Stage 4.

04

PID 1 is the genetic ancestor of every user process. The boot process concludes with its launch; everything in Module 2 onwards branches from that moment.

Timestamps on the left are seconds since kernel started.

Reading dmesg

The first few lines are the kernel greeting (Stage 3 entry). "ACPI" lines are driver init. "EXT4-fs mounted" is the root filesystem mount. "systemd[1]" is the moment Stage 4 begins.

The timestamps

Seconds since kernel start. If you see gaps (e.g., [ 5.2 ] then [ 12.8 ]), something took 7.6 seconds — that's your bottleneck.

Where to look first

If boot is slow, systemd-analyze blame tells you which services took longest. It's almost always the GUI or network services.
