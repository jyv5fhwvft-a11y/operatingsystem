The Core Question of L09

Processes are heavy — separate memory, separate address spaces, costly to create and switch. What if you need two execution streams in the same program? That's a thread, and it changes every rule we've seen so far.

🎯 Processes vs. Threads — The Tradeoff

Processes are heavyweight. Threads are lightweight.

Process cost (from L05-L06)

Each process has its own address space (page tables, memory, files). Creating one requires fork() — expensive.

Switching between processes requires a full context switch — save/load 16 registers, flush TLB, swap page tables (CR3).

Inter-process communication requires explicit IPC — pipes, sockets, shared memory, semaphores.

Thread cost

Each thread shares its process's address space — same memory, same files, same globals. Creating one is much cheaper than fork().

Switching between threads is cheaper — same page tables, no TLB flush, just register swap.

Communication is automatic — threads share memory by default. But that's also why threads are dangerous.

When to use processes

When you need strong isolation — separate crash domains, separate permissions. Chrome tabs, per-user services, anything where one bug shouldn't kill the other.

When to use threads

When you need performance — parallel computation, overlapping I/O with CPU work, responsive UI. When the tasks are naturally cooperative and share data.

🎭 Analogy 1 · Stage Actors Sharing a Single Props Table

Four actors. One stage. One props table.

The setup

A theatrical play runs in an auditorium. Multiple actors (threads) step onto the same stage inside the same building. Each actor has their own script folder (thread stack) and performs independently — but they all share the exact same props table, background scenery, and storage crates (the shared heap and data).

The shared assets

The props table is where the risk lives. If one actor rearranges the props while another actor is about to pick up a specific item, they collide. The shared memory is a shared resource — and shared resources need coordination.

The danger

If one actor knocks over the shared props table, every single actor is impacted immediately. There's no isolation between threads — a crash in one is a crash in all (usually — unless the kernel catches it).

💡
The whole tradeoff in one image: shared memory gives you fast coordination and no serialization overhead — but it also means the memory is a battlefield unless you add locks.

The rule of thumb

Anything a function can reach through a shared pointer is shared between threads. Anything declared static outside a function, anything on the heap, anything in a global — all visible to every thread.

What's private and why

Each thread needs its own program counter (which instruction am I executing?) and its own stack (what function am I inside, with what locals?). Without these, two threads couldn't run different code paths simultaneously.

The dangerous middle ground

Heap-allocated memory is technically "shared" — but only if threads have a pointer to it. That's why malloc is thread-safe by default in modern libcs: the allocator itself uses internal locks.

🌐 Analogy 2 · Independent Windows vs. Isolated Tabs

Processes are separate windows. Threads are tabs in one window.

Multiple processes

Running a standalone text editor alongside a standalone video game. Each has its own window, its own memory, its own resources. If the game crashes, the text editor keeps running.

Multiple threads

Multiple tabs within one web engine. They share the same browser process, the same session cookies, the same cache — but each tab has its own DOM and JavaScript context. If one tab hangs, the others usually stall too (in older browsers) — but a modern Chrome isolates each tab as a separate process, which is why one crashing tab doesn't kill your entire session.

📖 Core Breakdown — What a Thread Actually Is

A lightweight unit of CPU utilization inside a process

Formal definition

A thread is a lightweight concurrent sequence of instructions executing within the shared ecosystem context of a parent process. The OS schedules threads, not processes — processes are just the container.

What each thread gets

Unique Thread ID — to distinguish it from siblings
Program Counter — its current instruction
Register state — saved on context switch
Isolated Stack frame — its own local variables

What threads share

Code segment, data segment, heap, file descriptors, signal handlers, environment. Everything that isn't on the private list.

💡
The famous tradeoff: shared state makes threads fast to coordinate but hard to get right. Every thread-safety bug you'll ever see traces back to this exact design choice.

✦ Why Use Threads — The Benefits

Four things threads make cheaper or possible

⚡ Fast creation

Creating a thread is much cheaper than fork(). No address-space copy, no page tables — just a new stack and a new TCB. Microseconds, not milliseconds.

🔄 Fast switching

Thread switch: save/load registers only. No TLB flush, no CR3 swap. This makes thread switches 5–10× cheaper than process switches.

🤝 Zero-cost communication

Threads share memory — any thread can read/write any global or heap variable. No pipes, no sockets, no marshalling. Just pointer dereferences.

🔀 True parallelism

On a multi-core CPU, multiple threads of one process can genuinely run simultaneously on different cores. Processes can too, but threads share the cache — better locality.

✦ Why Threads Are Dangerous — The Costs

Four things that make threads hard to use correctly

💥 No crash isolation

A segmentation fault in one thread takes down the entire process — and all sibling threads with it. Compare to processes, where a crash affects only that process.

⚔️ Race conditions

Two threads writing to the same variable at the same time produce nondeterministic results. This is the entire subject of Module 4 (Process Synchronization).

🔒 Deadlock risk

Introducing locks to fix race conditions introduces a new failure mode — two threads waiting on each other's locks, neither making progress. Also Module 4.

🔍 Debugging is terrible

Thread bugs are often timing-dependent — they appear once in 10,000 runs, then disappear when you attach a debugger. This is why "it works on my machine" is a cliché.

The structure

Multiple user-level threads map to a single kernel thread context. The user library handles creation and switching. The kernel knows only one thread — from its perspective, one thing is running.

The upside

Thread switching is incredibly fast — no kernel involvement at all. Purely a userspace operation: save registers, load registers, jump. Hundreds of nanoseconds.

The fatal flaw

If one user thread blocks on I/O, the entire kernel thread blocks — and all sibling threads freeze with it. The kernel can't context-switch to a sibling because it doesn't know the siblings exist.

💡
Historical example: old versions of Java "green threads" used this model. It worked well for CPU-bound computation but fell apart for I/O-heavy applications.
1️⃣ One-to-One — Each user thread gets its own kernel thread

Full kernel awareness of every thread

The structure

Every user thread maps directly to its own scheduled kernel thread. The kernel knows about every thread, schedules each independently, and can run them in true parallel on different cores.

The upside

No blocking cascade. If one thread blocks on I/O, the kernel just schedules the others — they keep running on other cores or the same core. True parallelism across multi-core CPUs.

The cost

Each thread creation requires a syscall (or kernel-aware allocation). Thread switches go through the kernel — slightly more expensive than pure userspace switches, but still much cheaper than full process switches.

The scaling concern

Thousands of threads means thousands of kernel threads, which means thousands of task_structs, which means the scheduler has a lot of work. Modern kernels handle this well (Linux handles 100k+ threads), but it's not free.

💡
Linux and Windows both use 1:1. POSIX pthreads on Linux is implemented via clone() with CLONE_VM — each pthread is a real kernel-scheduled task.

The structure

Multiple user threads are multiplexed onto a smaller number of kernel threads. The user library schedules user threads onto kernel threads. The kernel schedules kernel threads onto CPUs.

The upside

Best of both worlds: if one user thread blocks, the user library can schedule a sibling on the same kernel thread. And you can still get true parallelism up to N cores.

The complexity

Two-level scheduling is genuinely hard to implement correctly. The user library must coordinate with the kernel about when to add/remove kernel threads, handle blocking syscalls, and not starve user threads. Very few production systems use this.

💡
Solaris used this for years. The old Sun Solaris "M:N" thread library was famous for its complexity — and famously replaced by 1:1 in later versions.

💻 Code — POSIX pthreads

The canonical thread example

pthreads_demo.c
#include <pthread.h>#include <stdio.h>// Function that each thread will runvoid* thread_runner_routine(void* arg) {    printf("Hello from Thread ID: %ld\n",           (long) pthread_self());    return NULL;}int main() {    pthread_t worker_thread_id;    // Create a thread · runs thread_runner_routine in parallel    pthread_create(&worker_thread_id, NULL,                   thread_runner_routine, NULL);    // Wait for the worker thread to finish    pthread_join(worker_thread_id, NULL);    printf("Worker finished. Main thread exits.\n");    return 0;}
The three key calls

pthread_create — spins up a new thread running the given function
pthread_join — waits for the thread to complete
pthread_self — returns the current thread's ID

What pthread_create actually does

On Linux, this calls clone() with flags that say "share memory but create a new stack and new task." The kernel creates a new task_struct (that's the "1:1" model we saw) — the user library just wraps it in the pthread abstraction.

The compile step

You must link with -pthread: gcc -pthread threads.c -o threads. Without it, pthread_create returns an error and the program behaves unexpectedly.

💻 Code — Sharing Data Between Threads (and Why It's Dangerous)

The same variable, two threads, one result you didn't expect

shared_counter.c
#include <pthread.h>#include <stdio.h>// SHARED — both threads will see and modify thisint shared_counter = 0;void* bump_counter(void* arg) {    for (int i = 0; i < 100000; i++) {        shared_counter++;  // NOT atomic — race condition!    }    return NULL;}int main() {    pthread_t t1, t2;    pthread_create(&t1, NULL, bump_counter, NULL);    pthread_create(&t2, NULL, bump_counter, NULL);    pthread_join(t1, NULL);    pthread_join(t2, NULL);    // Expect 200000. Often get something like 143287.    printf("Final counter: %d\n", shared_counter);    return 0;}
What's actually happening

shared_counter++ is not one instruction. It's three: load counter into a register, add 1, write back. If both threads run those three steps interleaved, one increment can overwrite the other.

Why this is the whole point of Module 4

Sharing memory by default is fast but unsafe. The whole subject of process synchronization is: how do we get the speed of shared memory without the data races? That's L14 and L15.

The preview fix

Wrap the increment in a mutex lock: pthread_mutex_lock(&m); counter++; pthread_mutex_unlock(&m);. The result becomes deterministic (200000, every time) — but the mutex itself is expensive.

What you're watching

Each "run" is the same binary with the same two threads doing 100,000 increments each. Because of the race condition, the final result is nondeterministic.

The observation that scares people

Every run is different. Sometimes it's 189,204. Sometimes 156,782. Sometimes 199,999. Rarely (if you're unlucky with timing) it's actually 200,000 — but you can't rely on it.

Why this is a "heisenbug"

Adding print statements changes the timing, which can make the bug appear or disappear. Attaching a debugger changes timing. The compiler's optimization level changes timing. Threads are the original "it works on my machine" generator.

🌍 Real World — How Linux Actually Implements Threads

Linux has no separate thread concept

The key insight

Linux doesn't have a distinct "thread" abstraction. Both processes and threads are implemented via the same clone() syscall — with different flags controlling what gets shared.

The flags that matter

CLONE_VM — share address space
CLONE_FILES — share file descriptor table
CLONE_FS — share filesystem info
CLONE_THREAD — share signal handlers, put in same thread group

The result

fork() = clone(SIGCHLD). pthread_create() = clone(CLONE_VM | CLONE_FILES | CLONE_FS | CLONE_THREAD | ...). Same syscall, different flags.

💡
Why this is elegant: the kernel scheduler doesn't care whether a "task" is a process or a thread — it just schedules task_structs. The distinction lives entirely in userspace (via the pthread library).
One syscall, two behaviors
📋 The Full Tradeoff — When to Use Which

A practical decision guide

Use THREADS when

✓ Tasks share substantial data (image convolution, matrix math)
✓ You need true CPU parallelism on multi-core
✓ You want responsive UI while background work continues
✓ You have short-lived tasks (thread creation is cheap)
✓ All tasks are cooperative and well-tested

Use PROCESSES when

✓ Tasks have separate security domains (browser tabs, per-user services)
✓ You need crash isolation (one bad plugin shouldn't kill everything)
✓ Tasks are truly independent (microservices)
✓ You're running untrusted code
✓ Debug time is more valuable than switch time

💡
The pragmatic middle: modern systems use process pools with threads inside each process. Chrome does this — each tab is a process (isolation), and inside each tab multiple threads render and execute JavaScript (performance). Best of both.
🏷️ System Lexicon — Thread Fundamentals
Thread
Term 01 of 04
Formal Definition

A lightweight concurrent sequence of instructions executing within the shared ecosystem context of a parent process.

Plain Translation

( An independent execution stream that shares its parent's memory. )

Key property

Shares code, data, heap, file descriptors with sibling threads. Has its own stack, PC, and registers.

User-Level Thread
Term 02 of 04
Formal Definition

A thread managed completely in user space by an application library without the underlying kernel core being aware of its boundaries.

Plain Translation

( A thread the OS doesn't know exists — it's just a data structure the app manages. )

Trade-off

Faster to create and switch (userspace only), but the kernel can't schedule them independently — one blocked thread blocks all siblings.

🏷️ System Lexicon — Kernel Threads & Concurrency
Kernel-Level Thread
Term 03 of 04
Formal Definition

A thread maintained, tracked, and scheduled natively by the operating system core within Ring 0.

Plain Translation

( A thread the kernel knows about and schedules itself. )

Trade-off

Slower to create (syscall), but the kernel can schedule each thread independently — true parallelism, no blocking cascades.

Concurrency
Term 04 of 04
Formal Definition

Enabling multiple execution paths to make progress over overlapping blocks of time (via fast time-slicing or true parallel cores).

Plain Translation

( Multiple threads of work making progress — not necessarily simultaneously, but overlapping in time. )

vs. parallelism

Concurrency = managing multiple tasks (can be on one core via time-slicing). Parallelism = actually running them simultaneously (needs multiple cores).

🛑 Three Student Pitfalls

What beginners get wrong about threads

PITFALL 01
"Threads are just lightweight processes"
They share the address space — that's not a lightweight version of anything. It's a fundamentally different model. A process has its own memory; a thread shares its parent's. That single difference cascades into every other property: crash isolation, IPC, debugging, everything.
PITFALL 02
"More threads = more performance"
False. On an 8-core machine, 8 threads can run in parallel. 800 threads still run 8 at a time — plus you pay scheduler overhead, cache thrashing, and lock contention. Optimal thread count is usually near the number of cores for CPU-bound work, or higher for I/O-bound work (so other threads run while waiting).
PITFALL 03
"Threads are automatically faster than processes"
Only if the workload benefits from shared state. If two tasks don't share any data, running them as threads vs processes has near-identical throughput — but processes give you crash isolation for free. Threads only win when the shared state saves real work (e.g., no serialization, no IPC round-trips).
🎭 Interactive Activity — The Task Manager Thread Inspection Hunt

Find one process with many threads. Explain why.

The setup

Have all students pull up their laptops. Instruct Windows users to open Task Manager and turn on the "Threads" column. Mac/Linux users run htop or Activity Monitor.

The hunt

Have them locate a heavy app instance — a web browser, communication client, or IDE. Ask them to note: how many core processes it shows, and how many threads are running inside that single process.

The expected observation

Most heavy apps show 1–3 processes but 30–100 threads per process. Chrome shows multiple processes (one per tab, plus a browser process). VS Code shows one process with 40+ threads. Slack shows one process with 20+ threads.

💡
The debrief: "Why so many threads in one process?" Answer: rendering, network I/O, disk I/O, UI events, JavaScript execution, garbage collection — all need to run concurrently without blocking each other. Threads are the natural model for this.

🔬 Advanced — Things You'll Learn to Hate About Threads

Three traps that will bite you in real code

Trap 1 · Thread-unsafe library functions

Not every libc function is thread-safe. strtok, ctime, and localtime all use static internal buffers — call them from two threads simultaneously and they'll corrupt each other's return values. The _r suffix (strtok_r, localtime_r) denotes the thread-safe version.

Trap 2 · Fork + threads don't mix

If you call fork() from a multithreaded program, only the calling thread survives in the child. Any locks held by other threads stay held — forever — because their owners don't exist in the child. This is a real source of deadlocks in production.

Trap 3 · Thread cancellation is hard

Cancelling a thread mid-execution can leave shared state inconsistent. If a thread is cancelled while holding a mutex, the mutex stays locked forever. This is why most guidelines say never use pthread_cancel — use a cooperative shutdown flag instead.

🏆 Grand Summary — L09 Key Takeaways

Four things to walk out with

01

Threads are execution streams inside a process. They share the code segment, data segment, heap, and file descriptors — but each has its own stack, program counter, and registers.

02

Threads are cheaper than processes — faster to create, faster to switch, and they share memory so no explicit IPC is needed. That's why they're the foundation of all concurrent programming.

03

There are three concurrency models: Many-to-One (fast but blocking cascades), One-to-One (full kernel awareness, what Linux/Windows/macOS use), and Many-to-Many (hybrid, historically complex, mostly abandoned).

04

Shared memory makes threads fast but makes them dangerous. Race conditions and deadlocks are the price of admission — and that's exactly what Module 4 is about.
