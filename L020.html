🎯 The Core Problem — CPUs Are Faster Than Devices

CPU: 3 GHz. Disk: 100 IOPS. The gap is enormous.

The asymmetry

A modern CPU executes roughly 3 billion instructions per second. A spinning HDD can complete roughly 100 I/O operations per second. The CPU is 30 million× faster than the device it needs to talk to.

The naive approach — wait in place

If the CPU just spins, asking "are you done yet?" repeatedly, it spends nearly all its time doing nothing productive. On a busy server, this would be catastrophic — most of the machine's compute capacity would be wasted on busy-waiting.

The insight

The OS needs a way for the CPU to do useful work while devices transfer data — and to only get involved when there's actual work to do. Three strategies have evolved: polling, interrupts, and DMA. Each has a place.

💡
The design axis: who waits? With polling, the CPU waits. With interrupts, the device notifies. With DMA, a third chip takes the transfer. Each shifts work off the CPU at the cost of complexity.
The CPU vs. device speed gap
📬 Analogy 1 · Mailbox, Doorbell, Desk Assistant

Three ways to receive a package

📬
POLLING · "check the mailbox every 5 minutes"
You stop working every 5 minutes, walk downstairs, and check the mailbox. It's usually empty. You waste 99% of your trips doing nothing.
🔔
INTERRUPT · "the mail carrier rings the doorbell"
You sit at your desk working smoothly until the mail carrier physically rings the doorbell. You pause your work only when you hear the chime, handle the package, and immediately go back to work.
🤝
DMA · "hire a private assistant with a key"
You tell them: "Wait for a truck carrying 100 heavy boxes, stack them all directly on my shelf, and only tap me on the shoulder when the entire shelf is full." You're completely out of the lifting process.
💡
The tradeoff: polling is simple but wastes time; interrupts are efficient but add per-event overhead; DMA is best for bulk transfers but requires an extra hardware chip.

📬 Analogy 1 · When Each Approach Wins

Match the strategy to the delivery profile

Polling wins when...

Deliveries are predictable and frequent. If you know mail arrives every morning at 9:00, walking down at 9:01 is efficient — no doorbell needed. Polling is also cheap when the check itself is nearly free (a memory-mapped status register read).

Interrupts win when...

Deliveries are unpredictable but infrequent. A letter from a friend arrives whenever it arrives; being alerted is better than constant checks. The doorbell pays for itself many times over by keeping you at your desk.

DMA wins when...

Deliveries are bulk shipments. If a truck arrives with 100 heavy boxes, you don't want to lift them yourself — you delegate. The cost of setting up the assistant is amortized over the massive transfer.

💡
The unifying principle: choose the strategy whose overhead is smallest relative to the actual transfer work. That's why modern hardware uses all three at different scales.

📖 Core Breakdown — The I/O Controller Registers

Every device exposes three registers

Command register

The CPU writes here to tell the device what to do. Common values: READ, WRITE, RESET, SEEK. This is the "start" button.

Status register

The CPU reads here to learn what the device is doing. Common bits: BUSY, READY, ERROR, DONE. Polling reads this register in a tight loop.

Data register

The actual data flows through here. On a PIO (programmed I/O) transfer, the CPU copies bytes between the register and memory one at a time. On DMA, the DMA chip handles this directly.

💡
The consistency: every device — keyboard, disk, network card, GPU — presents these same three logical registers. The OS only needs to know how to write commands and read statuses; it doesn't care what the device physically does.

📖 Core Breakdown — Strategy 1: Polling

The CPU continuously checks

The mechanism

The CPU executes a tight loop: write the command, then repeatedly read the status register until it says "ready." Only then does it read the data. Polling forces the CPU to continuously read the Status register in a tight loop until the device finishes its work.

When it's the right choice

When the device is predictable and fast relative to the poll cost. Temperature sensors, GPIO pins, and simple ADCs are the classic examples. If the loop runs only once per event, there's nothing to waste.

When it's the wrong choice

When the device is slow or unpredictable. A disk transfer can take milliseconds; polling that would spin the CPU billions of times doing nothing. Fast, unpredictable devices (keyboard) also break polling — the CPU would either miss events or waste cycles checking.

♿
Micro-Accessibility Context: polling is sometimes called "busy-waiting" or "spinlocking." It's considered a bug in most user-space code — but in the kernel, spinlocks are correct for very short critical sections because the alternative (sleep/wake) costs more than the spin.

📖 Core Breakdown — The Cost of Polling

How much CPU is wasted on the loop?

Live · Polling a slow device
CPU UTILIZATION
polling · 100% busy

The CPU reports 100% utilization — but only a tiny fraction of that is productive work.

The math

Device latency: 1 ms
Poll read cost: 10 ns
Polls per transfer: 100,000
Wasted work per transfer: ~1 ms of CPU

At scale

If the system does 1,000 such transfers per second, polling consumes 100% of one CPU core doing nothing. On a multi-core machine, that's one core fully wasted on busy-waiting.

When it's fine

If the poll cost is comparable to the device latency — e.g., reading a memory-mapped register in nanoseconds — the overhead is small. On modern CPUs, mmio reads are ~100 cycles; if the device responds in ~1000 cycles, polling is genuinely efficient.

💡
The exception that proves the rule: firmware and bootloaders often poll because they run before interrupts are set up. It's the correct choice for that specific phase — not for steady-state operation.
📖 Core Breakdown — Strategy 2: Interrupts

The device notifies, the CPU resumes

The mechanism

Interrupts free the CPU: the device controller fires an electronic signal down a physical wire line when it is ready. The CPU catches this, pauses its current instruction loop, handles the data transfer via an Interrupt Service Routine (ISR), and resumes work.

The IVT lookup

When the interrupt fires, the CPU uses the interrupt number as an index into the Interrupt Vector Table (IDT on x86_64) to find the right ISR address. That's the same mechanism from L03 — just triggered by a device instead of the syscall instruction.

The overhead

Every interrupt costs a register context save/restore — typically 100–1000 cycles. For occasional events (keystrokes, mouse moves) that's fine. For high-frequency events (1 million packets/second), it becomes prohibitive.

♿
Micro-Accessibility Context: interrupts aren't free. The interrupt latency is the delay between the device firing the signal and the CPU entering the ISR — typically 1–10 µs on modern hardware. That's 1000× the cost of a single memory access, which is why we still need DMA.

📖 Core Breakdown — Inside the ISR

The four phases of interrupt handling

Phase 1 · Hardware entry

The CPU stops the current instruction stream, saves the registers and program counter to the stack, and switches to Ring 0. This happens in silicon — no software involved.

Phase 2 · IVT dispatch

Read the interrupt number from the controller, index into the IVT/IDT, jump to the registered ISR address. The kernel pre-registered all these addresses at boot.

Phase 3 · Do the work

Read the data, acknowledge the interrupt (so the device stops signaling), schedule any deferred work, and write to a buffer that a sleeping process can wake up to read.

Phase 4 · Return

Restore the saved registers, execute the IRET instruction, and the CPU resumes the interrupted program exactly where it left off. The program never knew it was paused.

3 · ISR body Read data · acknowledge interrupt
Buffer it · wake any waiting process
4 · Return IRET · restore registers
Resume the interrupted instruction

The interrupted program has no idea this happened. From its perspective, time just moved forward.

📖 Core Breakdown — Strategy 3: DMA

Hand off the transfer to a dedicated chip

The mechanism

For high-speed, data-dense devices (hard drives, network cards, GPUs), interrupts still slow the system down due to excessive overhead. Direct Memory Access (DMA) resolves this by handing the data transfer off to a secondary hardware chip — the DMA controller.

How it works

The CPU tells the DMA controller the starting RAM address and total byte size. The DMA chip then copies the data directly between the device and RAM over the system bus, completely bypassing the CPU for the bulk transfer. It fires a single interrupt only when the entire transfer finishes.

The payoff

For a 4 GB file transfer, the CPU would otherwise handle 4 billion byte-by-byte copies. With DMA, it does one setup call and one completion interrupt. The CPU is entirely free during the transfer.

💡
The assistant analogy revisited: the CPU "hires" the DMA controller, gives it instructions ("copy 4 GB from disk address X to RAM address Y"), and then goes back to its desk. The DMA controller taps the CPU on the shoulder only when it's done.

The CPU sees only 2 phases (setup + completion). The DMA controller handles the middle.

The setup cost

DMA setup takes ~1000 cycles (write the descriptor, program the controller). For a 4 KB transfer, that's expensive — you wouldn't use DMA. For a 4 MB transfer, it's free (0.02% overhead).

The threshold

General rule: DMA pays off above ~1–4 KB per transfer. Below that, the setup cost dominates and interrupts are more efficient.

Modern variants

Standard DMA — classic PCI/ISA DMA
Bus-mastering DMA — device is the bus master (PCI, PCIe)
Scatter-gather DMA — one descriptor covers multiple non-contiguous buffers
IOMMU — address translation + isolation for DMA

♿
Micro-Accessibility Context: bus-mastering is the modern default — the device itself arbitrates for the bus and drives the transfer. This is why a modern NVMe SSD can saturate PCIe without the CPU writing a single byte to the data register.

Temperature sensor → Polling

Because data arrives on a slow, highly predictable timeline, the kernel can simply schedule a quick check once every 10 minutes, completely bypassing interrupt line allocation.

Keyboard → Interrupts

Keystrokes are completely unpredictable and infrequent on a microsecond scale. Polling would waste billions of CPU cycles; an interrupt lets the CPU ignore the keyboard until a key is physically tapped.

Gigabit Ethernet → DMA

Packets stream in at millions of bytes per second. Using standard interrupts for every single incoming byte would throw the CPU into an "Interrupt Storm," paralyzing the machine. The DMA controller streams packets directly to a RAM buffer, alerting the CPU only when a full frame array settles.

What you're seeing

Each "BUSY" line is a wasted read of the status register. The device isn't ready yet, so the CPU just loops and loops until the data finally arrives.

The waste

For a 10 ms device, the CPU executes ~100,000 poll iterations. Only the last one is productive. 99.999% of the work is thrown away.

When this is fine

If you're reading a GPIO pin that you know changes once per second — 1,000 polls per second is basically free on a 3 GHz CPU. The waste only matters when it's in the billions.

🧪 Live Demo — The Interrupt Storm

Too many interrupts is also bad

Live · Interrupt storm on a busy NIC
kernel — IRQ 42 (eth0)
Interrupt handler registering for eth0...
What you're seeing

A high-speed network card firing interrupts faster than the CPU can handle them. Each one triggers a context save, an ISR, and a context restore.

The problem

At 1 million interrupts per second, the CPU spends 100% of its time in ISR overhead — saving registers, jumping to the handler, restoring registers — and never gets to do useful application work.

The fix

NAPI (New API) — Linux's solution. It disables interrupts after the first one, then switches to polling the device in bulk. Best of both worlds: interrupt for the initial wake-up, polling for the throughput.

💡
This is the classic L20 lesson: every strategy has an upper bound where it breaks. The trick is to combine them — start with interrupts, escalate to polling under load, and delegate the bulk transfer to DMA.

💻 Code — The DMA Transfer in C

Two API calls. Billions of bytes.

dma_transfer.c
// Setup + start a DMA transferint read_device_dma(void* buf, size_t len) {    // 1. Allocate a DMA descriptor    struct dma_desc desc;    desc.src       = DEVICE_DMA_ADDR;    desc.dst       = virt_to_phys(buf);    desc.length    = len;    desc.direction = DMA_FROM_DEVICE;    // 2. Program the DMA controller    dma_submit(&desc);    // 3. Tell the device to start reading    write_reg(CMD, READ);    // 4. CPU is free — wait for completion IRQ    wait_for_dma_complete(&desc);    return len;}
The four steps

1. Build a descriptor (source, dest, length)
2. Give it to the DMA controller
3. Trigger the device
4. Sleep until the DMA completes

The heavy lifting

Between step 3 and step 4, the DMA controller takes over. It reads from the device, writes to RAM, and never bothers the CPU. When it finishes, the completion IRQ fires — and one interrupt handles an entire 4 GB transfer.

The caveat

The destination address must be a physical address, not virtual. That's why virt_to_phys() is in the code — the DMA controller doesn't go through the MMU.

♿
Micro-Accessibility Context: on systems with an IOMMU, the DMA controller does go through address translation — but via a separate IOMMU, not the CPU's MMU. This lets the OS pass virtual addresses (safe) while the IOMMU handles the translation for the DMA path.
🌍 Real World — Modern Hybrid Approaches

Real hardware uses all three at once

🌐
Linux NAPI — network driver
Interrupt fires once to wake the driver → driver disables interrupts → switches to polling with a batch budget. Under heavy load, NAPI polls; under light load, it sleeps until the next interrupt.
💾
NVMe SSD — DMA with queue-based polling
Modern NVMe uses DMA for bulk transfers, but also supports polling mode (no interrupts at all) for ultra-low-latency workloads. Databases running on NVMe often disable interrupts entirely.
🖥️
io_uring — polling from user space
Linux's io_uring can run in SQPOLL mode — a kernel thread polls the submission queue, so syscalls are eliminated. The kernel side of io_uring uses interrupts + DMA for the actual I/O, but the API is pure polling.
⚡
DPDK — pure polling for packet processing
Data Plane Development Kit bypasses interrupts entirely — user-space processes poll the NIC rings directly. Only viable when you dedicate CPU cores to the task, but produces the lowest latency.
💡
The pattern: modern systems let software choose the mode at runtime. Interrupts for the slow path, polling for the fast path, DMA for the bulk transfer. The old "one strategy per device" rule has been replaced by mode switching under load.
🏷️ System Lexicon — Polling & Interrupt
Polling
Term 01 of 04
Formal Definition

An I/O communication method where the CPU repeatedly inspects a hardware device register to check if an I/O operation has finished.

Plain Translation

( "Are you done yet?" — asked in a loop, forever. )

Also known as

Busy-waiting · spinlock (in kernel context). Best for slow, predictable devices.

Interrupt
Term 02 of 04
Formal Definition

An electronic signal sent by a hardware component that forces the processor to pause its current execution flow and jump to a specialized handler.

Plain Translation

( The device rings the doorbell. The CPU gets up to answer. )

The key property

Asynchronous — fires at any time. Requires context save/restore (~100–1000 cycles).

🏷️ System Lexicon — ISR & DMA
ISR
Term 03 of 04
Formal Definition

Interrupt Service Routine — the low-level kernel code function triggered inside Ring 0 to process and clear a specific hardware interrupt vector.

Plain Translation

( The code that runs when an interrupt fires. )

The discipline

ISRs must be short. Long ISRs delay other interrupts and stall the system. Defer heavy work to a bottom half / tasklet / workqueue.

DMA
Term 04 of 04
Formal Definition

Direct Memory Access — a specialized hardware feature allowing peripheral controllers to read or write data blocks straight to main system RAM completely independent of the CPU.

Plain Translation

( A helper chip that moves data without the CPU lifting a finger. )

The benefit

CPU is free during transfer. One interrupt on completion. Best for bulk transfers above ~4 KB.

🛑 Three Student Pitfalls

What beginners get wrong about I/O communication

PITFALL 01
"Interrupts are always better than polling"
Not true. For a very fast, very predictable device, the interrupt overhead (~1–10 µs) can dominate the actual data transfer. Modern NVMe SSDs and 100G NICs actually switch to polling mode under high load — because at 10 million packets per second, the interrupt overhead alone would peg every core. The right answer depends on the workload profile.
PITFALL 02
"DMA replaces the need for interrupts"
DMA and interrupts are complementary, not substitutes. DMA moves the bulk data without the CPU, but it still uses an interrupt to signal completion — otherwise the CPU would have to poll to know the transfer finished, defeating the purpose. Every DMA transfer ends with one interrupt.
PITFALL 03
"More interrupts = faster response"
False. Interrupts can queue up and delay each other. If the CPU is busy handling interrupt A, interrupt B waits. If interrupts come faster than the CPU can handle them, you get an interrupt storm — the CPU spends all its time entering and exiting ISRs and never gets to the actual work. This is why Linux has NAPI, threaded IRQs, and interrupt affinity tuning.

🏆 Grand Summary — L20 Key Takeaways

Four things to walk out with

01

I/O communication has three foundational strategies: polling (CPU checks), interrupts (device notifies), DMA (helper chip transfers). Each has a distinct profile of cost, latency, and complexity.

02

Polling wastes CPU cycles but is trivial to implement. Best for slow, predictable devices. Interrupts are efficient for occasional events, but add ~1–10 µs overhead per event. DMA bypasses the CPU entirely for bulk transfers above ~4 KB.

03

Every device exposes the same three registers: COMMAND (write what to do), STATUS (read what's happening), DATA (the payload). The three strategies differ in how the CPU interacts with these registers.

04

Modern systems combine all three — NAPI for NICs, polling mode for high-performance SSDs, io_uring for user-space polling. The old "one strategy per device" rule is gone.
