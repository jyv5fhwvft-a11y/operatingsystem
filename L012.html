The Core Question of L12

L11 gave us paging — but every memory access now requires two trips to RAM: one to read the page table entry, another to read the actual data. That's a 50% slowdown. How does the system recover that performance back?

🎯 The Problem — Paging Doubles Memory Latency

Every load. Two trips to RAM.

The paging penalty

Without a TLB, every memory access requires two separate RAM reads: one to fetch the page table entry (to find the frame number), and one to actually read the data at the translated physical address.

The cost

If DRAM access takes 100 ns, a naive paged access takes 200 ns. That's a 2× slowdown on every single load, store, and instruction fetch. The CPU, designed to run at ~0.3 ns per cycle, spends most of its time waiting on memory.

The multi-level worse case

On 32-bit x86 with 2-level paging, it's actually 3 accesses (directory → table → data). On 64-bit x86 with 4-level paging, it's 5 accesses without caching. That would be catastrophic.

💡
The obvious fix: cache the results of recent translations. If the same virtual page is accessed again soon, we already know its frame number — skip the page table walk entirely.

📝 Analogy 1 · The Sticky Note on the Monitor

You don't walk to the phonebook for every call

The setup

You work as a researcher who constantly needs to look up phone numbers in a massive 1,000-page directory book kept across the room (the page table in RAM). Every single time you want to make a call, walking across the room to check the book slows you down heavily.

The optimization

You stick a small piece of paper right next to your telephone (the TLB cache). When you look up a number for the first time, you write it on the sticky note. The next time you call that same person, you don't walk across the room — you glance at the sticky note instantly.

The miss case

You only walk to the heavy phonebook if the note is missing the name. That's a TLB miss — the translation wasn't cached, so you have to do the full page table walk.

💡
The win: the sticky note holds maybe 64 entries — tiny compared to the 1,000-page book. But 99% of your calls go to numbers already on the note, because you call the same people repeatedly. That's locality of reference.

📖 Core Breakdown — What the TLB Actually Is

A hardware cache inside the MMU

Formal definition

The Translation Lookaside Buffer (TLB) is a specialized hardware cache embedded inside the CPU MMU dedicated exclusively to accelerating virtual address mapping scans. It caches recent virtual-to-physical translations.

Where it lives

Inside the MMU, physically on the CPU die. Not in RAM. Not in the kernel. It's silicon — a few thousand flip-flops and comparators sitting between the load/store unit and the memory controller.

How it's searched

The TLB is an associative memory — the hardware compares the incoming virtual page number against all TLB entries simultaneously, in one clock cycle. There's no linear search; the comparison is done by dedicated comparator circuits.

💡
Typical sizes: L1 TLB has 32–128 entries per core. The L2 TLB (unified) has 512–2048 entries. Small, but thanks to locality, they catch 98–99.9% of translations.

📖 Core Breakdown — The TLB Hit Path

The translation resolves instantly

What happens on a hit

The virtual address is split into page number + offset. The page number is checked against every TLB entry in parallel. If a match is found with the valid bit set, the frame number is read directly from that entry.

The cost

The TLB check happens in parallel with the cache lookup — the CPU doesn't wait for the translation to finish before starting the L1 cache probe. Effectively, a TLB hit adds ~1 ns to the total. On modern hardware, often zero visible overhead.

The critical detail

The physical address is available in one clock cycle. The memory request then goes out immediately. From the program's perspective, there's no "paging slowdown" — the TLB has completely hidden it.

♿
Micro-Accessibility Context: TLB hits dominate real workloads. Typical hit rates are 98–99.9% — because programs spend most of their time in tight loops, and a loop's working set fits entirely inside a handful of pages.

📖 Core Breakdown — The TLB Miss Path

The full page table walk fires

What happens on a miss

If no TLB entry matches, the MMU must walk the page table in physical memory — read the page directory, then the page table, find the frame number. On 4-level paging, that's up to 4 memory reads just to translate.

The cost

A single miss costs an extra 100 ns (one DRAM trip) on 1-level paging, or up to 400 ns on 4-level paging. If the miss rate is 1%, the average cost is still only ~1–4 ns extra — manageable. If it's 20%, the system slows to a crawl.

The recovery

After the walk succeeds, the frame number is inserted into the TLB (evicting some LRU entry). Next access to the same page becomes a hit. The TLB "learns" the working set over time.

💡
Two flavors of miss: the page table walk succeeds (page is in RAM) → just slow. Or the page's present bit is 0 (page is on disk) → page fault, and the OS must load it from swap. That's L13.

📖 Core Breakdown — The TLB Structure

Small. Associative. Searched in parallel.

The size

A typical L1 TLB has 32–128 entries. The L2 TLB (unified, larger, slower) has 512–2048 entries. Both are tiny compared to the page table — because they rely on locality, not on holding everything.

The associative lookup

Unlike a normal cache (which uses an index), the TLB uses content-addressable memory — the incoming page number is compared against every entry simultaneously. Hardware comparators do all comparisons in one clock cycle.

The replacement policy

When the TLB fills up and a new translation must be inserted, an entry must be evicted. Most TLBs use pseudo-LRU — approximate least-recently-used. That's why the LRU field exists on each entry.

♿
Micro-Accessibility Context: because there are only ~64 entries, a program with a working set larger than 64 × 4 KB = 256 KB will thrash the TLB. That's why huge-pages (2 MB or 1 GB) exist — one entry covers a lot more memory.

📐 The EAT Formula

Effective Access Time — the weighted average

The formula
EFFECTIVE ACCESS TIME
EAT = HitRate × [TLB + Mem]
        + MissRate × [TLB + Mem + Mem]

where MissRate = 1 − HitRate
What each term means

HitRate — fraction of accesses that hit the TLB
TLB — time to check the TLB (typically ~1 ns)
Mem — time for one DRAM access (~100 ns)
MissRate — fraction that miss (1 − HitRate)

Why hit path is one Mem

On a hit, we get the frame from the TLB and go straight to DRAM for the data. That's 1 memory access (data). The page table read is skipped.

Why miss path is two Mem

On a miss, we have to read the page table first (memory access 1), get the frame, then read the data (memory access 2). That's the two access penalty.

💡
The insight: EAT is a probability-weighted average. Most of the time you take the fast path; sometimes you take the slow path. The formula tells you the average cost.
🧮 Worked Example — The Canonical EAT Calculation

90% hit rate. 100 ns RAM. 1 ns TLB.

Given TLB check latency = 1 ns
Memory access latency = 100 ns
TLB hit rate = 0.90 (90%)
TLB miss rate = 0.10 (10%)
STEP 1 · Hit path contribution 0.90 × (1 + 100) = 0.90 × 101 = 90.9 ns
STEP 2 · Miss path contribution 0.10 × (1 + 100 + 100) = 0.10 × 201 = 20.1 ns
STEP 3 · Total EAT 90.9 + 20.1 = 111 ns

📈 The Hit Rate Curve

EAT is nonlinear in the hit rate

Live · EAT vs. hit rate
Reading the curve

At 0% hit rate (no cache at all), EAT = 201 ns — the full two-access penalty. At 100% hit rate, EAT = 101 ns — nearly the no-paging cost. Everything in between is a smooth blend.

Why the curve is steep near 100%

Going from 90% to 99% hits shaves 9 ns off EAT — that's 8% improvement for 9 percentage points. Going from 0% to 50% saves 50 ns. Both are linear, but the relative improvement is huge at the top end.

The design implication

Schedulers, cache designers, and programmers all obsess over the last 1% of hit rate — that's where the wins are. Doubling TLB size or adding a 2-level TLB pushes 95% to 99%.

💻 Code — Computing EAT

The 30-line calculator

eat.c
#include <stdio.h>// Compute Effective Access Time for a TLBdouble compute_eat(double hit_rate,                   double tlb_ns,                   double mem_ns) {    double miss_rate = 1.0 - hit_rate;    double hit_cost  = tlb_ns + mem_ns;    double miss_cost = tlb_ns + mem_ns + mem_ns;    return hit_rate * hit_cost + miss_rate * miss_cost;}int main(void) {    double tlb = 1.0;    // 1 ns    double mem = 100.0;  // 100 ns    // Try several hit rates    double rates[] = {0.50, 0.90, 0.95, 0.99, 0.999};    for (int i = 0; i < 5; i++) {        double eat = compute_eat(rates[i], tlb, mem);        printf("hit %.1f%% → EAT %.1f ns\n",               rates[i] * 100, eat);    }    return 0;}
The core function

compute_eat() is a three-line calculation: hit_rate × hit_cost + miss_rate × miss_cost. That's the entire formula.

What the output shows

hit 50.0% → EAT 151.0 ns
hit 90.0% → EAT 111.0 ns
hit 95.0% → EAT 106.0 ns
hit 99.0% → EAT 102.0 ns
hit 99.9% → EAT 101.1 ns

The pattern

Every 1% increase in hit rate saves exactly 1 ns of EAT (since hit_cost − miss_cost = −100 ns, and 1% × 100 ns = 1 ns). Linear in the hit rate, until you approach 100% where the remaining 100 ns of DRAM is unavoidable.

📖 The Context Switch Cost — TLB Flushes

Every context switch invalidates the TLB

The problem

When the OS switches from process A to process B, process B has a different page table. Any TLB entry mapping A's virtual pages would give wrong results for B. The TLB must be invalidated — all entries marked invalid.

The cost

After a flush, the first access to any page becomes a TLB miss. The process runs slowly until the TLB refills with its hot entries. On a busy system, this happens hundreds of times per second.

The mitigation — ASIDs

Modern CPUs support Address Space Identifiers: each TLB entry is tagged with the process ID. On context switch, the OS just changes the current ASID — no flush needed. TLB entries for different processes coexist and match by ASID.

💡
Historical context: before ASIDs (pre-2010 on x86, still common on some ARM), full TLB flushes on every context switch were a big deal. Modern systems use PCIDs (x86) or ASIDs (ARM) to avoid this.

🏷️ System Lexicon — Miss & EAT
TLB Miss
Term 03 of 04
Formal Definition

A scenario where a virtual address is absent from the TLB, forcing the system to perform a slower, multi-step page table walk across main RAM.

Plain Translation

( The translation isn't in the cache — the CPU must walk the page table in memory. )

Cost

One extra memory access (1-level paging) or up to 4 (4-level paging). Handled in hardware or by a fast software TLB miss handler.

EAT
Term 04 of 04
Formal Definition

Effective Access Time — the calculated average operational time cost paid by a system to resolve a memory data request stream.

Plain Translation

( On average, how long does one memory access take with the TLB in place? )

The formula

EAT = h × (t + m) + (1−h) × (t + 2m)
where h = hit rate, t = TLB latency, m = memory latency.

🛑 Three Student Pitfalls

What beginners get wrong about the TLB

PITFALL 01
"The TLB is part of the page table"
No — the TLB is a cache of page table entries, not the page table itself. The page table lives in RAM. The TLB lives in the CPU. They serve different roles: the page table is authoritative, the TLB is a speed optimization.
PITFALL 02
"Hit rate = miss rate × 2"
Not quite. The correct relation is hit rate + miss rate = 1. If your hit rate is 0.90, your miss rate is 0.10 — not 0.20. The temptation to think of "hits and misses as separate counts" leads to doubling errors in the EAT formula.
PITFALL 03
"TLB miss means the page is on disk"
Not necessarily. A TLB miss just means the translation isn't cached. The page table walk then proceeds — if the page is in RAM (present bit = 1), it's just a slow translation. Only if the present bit is 0 does it become a page fault requiring disk I/O. That's L13.
🌍 Real World — Why Locality Makes This Work

Programs reuse the same pages over and over

Temporal locality

If you access page X, you're likely to access page X again soon. Tight loops — the bread and butter of all computation — touch the same handful of pages millions of times per second.

Spatial locality

If you access page X, you're likely to access page X+1 soon (because arrays are contiguous). A simple `for (i=0; i<N; i++) a[i]++` walks sequentially through pages, causing periodic TLB misses at page boundaries.

The practical result

Code loop: ~99.9% hit rate
Typical app: ~99% hit rate
Pathological (big working set): ~50% hit rate
Adversarial (deliberately thrashing): <10% hit rate

♿
Micro-Accessibility Context: this is why data layout matters. A cache-friendly loop that walks memory sequentially gets near-100% TLB hits. A linked list with nodes scattered across memory gets much worse — because it jumps between pages that don't fit in the TLB simultaneously.

🧭 Full Module 3 View — Where L12 Fits

The speed layer that makes paging feasible

The complete module

L10 · Base + Bound — translation and isolation (contiguous)
L11 · Paging — fragmentation-free, shareable
L12 · TLB — the speed layer (this lecture)
L13 · Virtual Memory — disk-backed pages, huge address spaces

What L12 enabled

Multi-level paging (which every 64-bit system uses) would be impossible without the TLB. The cost of 4–5 memory accesses per access would make the machine unusable. The TLB is what makes modern paging practical.

What comes next

L13 takes paging one step further. The page table gets a "present" bit. When it's 0, the page is on disk. The TLB miss then cascades down to a page fault — the kernel must load the page from swap before the access can proceed. That's the whole machinery of virtual memory.
