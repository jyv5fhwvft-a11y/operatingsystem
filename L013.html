🎯 The Core Problem — Programs Outgrow RAM

Paging gave us isolation. But not capacity.

The gap

A modern program's virtual address space is typically tens of GB (shared libraries, data files, mmap'd regions). Physical RAM is 8–32 GB on most machines. The virtual space exceeds physical memory by 2–10× on a normal desktop.

Why we can get away with it

Because most of that address space isn't actually touched at any moment. A 3 GB Photoshop file might only have 200 MB of it actively in use. A web browser reserves GBs of virtual space but only touches a fraction.

The insight

If we only load the pages that are actually accessed, and put the rest on disk (swap space), the process can have a huge virtual address space while consuming only the RAM it genuinely needs at any moment.

💡
Virtual memory is the mechanism that makes this work. Paging is the mechanism for isolation; virtual memory is the mechanism for capacity. Same page tables, same MMU — but with a "present" bit and swap space.

📚 Analogy 1 · The Limited Desk & Library Storage Stacks

Your desk holds 3 books. The library holds thousands.

The setup

You're studying in a massive university library. Your study desk can only fit exactly 3 books at a time (physical frame allocation). You're currently writing an essay that references 10 different books (virtual address space).

The page fault

You start working: you look for Book A on your desk. It isn't there! You must pause your work, wait for a runner to fetch Book A from the deep basement storage stacks (the hard disk / swap space), and drop it onto your desk.

The replacement

When your desk fills up completely and you need a 4th book, you must choose one current book to throw off your desk and send back to the basement (page replacement policy).

📚 Analogy 1 · The Replacement Decision

Which book gets thrown off the desk? Two strategies.

FIFO · First In First Out

Throw off whichever book has been on the desk the longest. Simple, easy to track with a timestamp. But a book you grabbed first and have been using continuously could get thrown off — even if it's the one you need most.

Advantage: trivial to implement

Disadvantage: ignores usage — can evict hot pages

LRU · Least Recently Used

Throw off whichever book you haven't touched in the longest time. Assumes that if you haven't looked at a book recently, you probably won't need it soon.

Advantage: better approximation of future use

Disadvantage: expensive to track precisely

The core insight

The choice of eviction policy determines how often you'll take a page fault. A good policy that keeps hot pages in RAM means fewer slow disk fetches. A bad policy thrashes — constantly fetching and evicting the same pages over and over.

🧭 System Cohesion — Where L13 Sits

The final layer of Module 3

Relies On · L11 (Paging)

Virtual memory is built on paging. Without page tables there's no "present bit" to check, no swap-in mechanism, no replacement policy. L11 is the substrate.

Relies On · L12 (TLB)

When the TLB misses, we walk the page table. If the entry says "not present," that walk becomes a page fault — and the kernel has to load the page from disk. So L13 extends L12's chain: TLB miss → page table walk → page fault → disk read.

Feeds Into · Module 4 (Process Synchronization)

Because virtual memory allows multiple concurrent threads to securely share specific page entries, it sets the stage for race condition contentions. Shared pages = shared state = synchronization needs.

Feeds Into · Module 5 (File & Storage Management)

Swapping unmapped dirty pages out of RAM requires directly orchestrating raw block writes to disk storage partitions. The page replacement algorithm must talk to the file system and block device drivers.

💡
Module 3 is complete: L10 (base + bound) → L11 (paging) → L12 (TLB) → L13 (virtual memory). Together they explain how a 64-bit address space can be presented to a process that only has 8 GB of physical RAM — the entire memory illusion.

📖 Core Breakdown — Demand Paging

Load a page only when needed

Formal definition

Demand Paging is an optimization mechanism where virtual pages are loaded into physical RAM strictly on-demand only when an active instruction requests them. No eager loading — pages appear in RAM the moment they're first touched.

What happens on process start

When a program launches, the OS sets up its page table but doesn't load any pages yet. Every page table entry is initially marked "absent." Execution begins — the first instruction fetch triggers a page fault, which loads the first page. The process then runs one page at a time.

The big win

Process startup is nearly instant. A 3 GB program can start in milliseconds — only its first few pages get loaded. The rest trickle in as execution reaches them. This is what makes huge applications feel instant.

💡
Compare to eager loading: without demand paging, launching Firefox would require reading 500 MB from disk into RAM before the first window appeared. With it, the window appears in ~2 seconds and pages load as needed.

📖 Core Breakdown — The Present / Absent Bit

One bit per page tells the MMU "is this in RAM?"

What the bit means

Every page table entry has a present bit (also called the "valid" or "P" bit). If it's 1, the page is currently in a physical frame — the MMU can complete the translation normally. If it's 0, the page is absent — currently on disk.

What happens when it's 0

The MMU doesn't just fail — it raises a specific hardware exception called a page fault. That traps into the kernel. The kernel recognizes it as "this page is on disk, not in RAM" and orchestrates the load.

The key insight

The present bit is what makes virtual memory transparent. The process has no idea a page is missing. It issues a load. The load might take 100 ns (page in RAM) or 10 ms (page on disk, needs swap-in). Either way, the process sees the load succeed. The MMU and kernel hide the difference.

♿
Micro-Accessibility Context: the present bit is why you can have a 64-bit program address space on a 8 GB machine. The page table has 2^52 entries, all but a tiny fraction marked "absent." When you access one, it becomes present after a fault.

📖 Core Breakdown — The Page Fault Sequence

Six steps from fault to resume

Live · What happens on a page fault
1
Hardware trap fires
MMU sees P=0 → raises page fault exception → CPU switches to Ring 0
2
Kernel identifies the page
Reads faulting address from CR2 register → determines which page is absent
3
Find a free frame
Pick a free physical frame, or evict one via replacement algorithm
4
Read page from disk
Issue block read to swap partition → wait ~10 ms for I/O
5
Update page table
Set P=1, fill in frame number → now the page is resident
6
Resume the instruction
Restart the load/store that faulted → now it succeeds from RAM
The trap-and-resume model

The fault isn't a failure. It's a transparent suspension and retry. The instruction that caused the fault runs again after the page is loaded, and this time it succeeds.

The cost per fault

Disk read of 4 KB typically takes 5–10 ms on SSD, 10–20 ms on HDD. That's 50,000–100,000× slower than a RAM access. One page fault dominates a million normal accesses.

Why page faults are catastrophic at scale

A process that faults once per second is fine. A process that faults once per 100 instructions spends 99% of its time waiting on disk. That's thrashing — next slide.

📖 Core Breakdown — FIFO Page Replacement

Evict the oldest page

The rule

Maintain a queue of pages in the order they were loaded. When a fault occurs and a frame must be freed, evict the page at the front of the queue — the one that has been in RAM the longest. Add the new page to the back.

Why it's attractive

Trivial to implement. No tracking needed beyond a queue. Each page just needs a timestamp (or a doubly-linked list position) at load time. O(1) eviction, O(1) insertion.

Why it's bad

FIFO ignores actual usage. A page loaded early but accessed constantly gets evicted just because it's old. FIFO has no idea whether a page is hot or cold. This can cause poor cache behavior and, famously, Belady's anomaly — adding more frames can increase faults.

FIFO queue
📖 Core Breakdown — LRU Page Replacement

Evict the least recently used page

LRU ordering
The rule

On every memory access, move the accessed page to the front of a recency list. When a fault occurs and a frame must be freed, evict the page at the back of the list — the one whose last access was longest ago.

Why it's better

LRU tracks actual usage, not load time. A page that's been in RAM for hours but is accessed constantly stays at the front and never gets evicted. A page that was loaded recently but never used sinks to the back and gets removed first.

The problem

Precise LRU is expensive in hardware. Every memory access would need to update a timestamp or reorder a list — that's a lot of bookkeeping for something that should be nearly free. Real systems use approximate LRU via a reference bit and clock algorithm.

💡
The intuition: LRU assumes the future looks like the past. If you haven't touched a page in a long time, you probably won't touch it soon. This assumption holds for most real workloads — which is why LRU is the gold standard for page replacement.

📊 FIFO vs. LRU — And Belady's Anomaly

Same result here. Different behavior elsewhere.

FIFO properties

✓ Trivial to implement (queue)
✓ O(1) eviction and insertion
✗ Ignores usage patterns
✗ Can exhibit Belady's anomaly

LRU properties

✓ Approximates future use well
✓ No Belady's anomaly (it's a "stack algorithm")
✗ Precise implementation is expensive
✗ Real systems approximate with reference bits

Belady's anomaly

For FIFO (and some other algorithms), increasing the number of frames can increase the number of page faults. This is deeply counterintuitive — more memory should mean fewer faults. LRU doesn't exhibit this because it's a stack algorithm — the set of pages in N frames is always a subset of the set in N+1 frames.

💡
Classic example of Belady's anomaly: reference string 1,2,3,4,1,2,5,1,2,3,4,5 with FIFO gives 9 faults at 3 frames but 10 faults at 4 frames. That's the textbook anomaly.

💀 Thrashing — The Worst Failure Mode

When the system spends more time swapping than working

Formal definition

Thrashing is a critical system failure state where a machine spends more time continuously swapping blocks back and forth to disk than executing actual instruction paths. CPU utilization collapses; throughput drops to near zero.

How it starts

1. Too many processes are running
2. Each process's working set doesn't fit
3. Processes steal frames from each other
4. Every access faults — pages get evicted before use
5. System enters a death spiral
6. CPU is 100% "busy" but does nothing useful

The Linux solution — the OOM killer

When thrashing reaches a critical point and no progress can be made, the Linux kernel invokes the OOM (Out-Of-Memory) killer. It selects the process consuming the most memory and kills it, freeing its pages for everyone else. Brutal, but it prevents the death spiral from taking down the entire system.

💡
Detecting thrashing: if vmstat shows the CPU idle time near 0% but disk I/O is pegged at 100%, and no useful work is completing — you're thrashing. It's the classic symptom on any system that's run out of RAM.
Live · Thrashing vs. healthy

CPU utilization rises with workload — then collapses once thrashing begins. Adding more load makes it worse.

📖 The Working Set Model — Preventing Thrashing

How much RAM does a process actually need?

The definition

The working set of a process at time t is the set of pages it has accessed in the last Δ time units. Δ is a tunable window (often 10,000–1,000,000 instructions). The working set approximates which pages must be in RAM for the process to make progress efficiently.

Why it matters

If the sum of all processes' working sets fits in physical RAM, no thrashing. If it exceeds RAM, thrashing. The OS uses this insight: admit a new process only if its working set fits. Otherwise, swap someone out or wait.

Why it's approximate

Precise working set tracking requires knowing every access. Real systems approximate with reference bits — the hardware sets a bit on each page access, and the OS samples those bits periodically. A page with the reference bit set recently is "in the working set."

📖 Swap Space — The Disk Side of Virtual Memory

Where absent pages actually live

What swap space is

A designated raw block sector layout on a hard drive or SSD used to cache evicted virtual page overflows. When the OS evicts a page from RAM, it writes it to swap — and when the process touches it again, it reads it back from swap.

Where it comes from

Swap partition: a dedicated disk partition (fastest)
Swap file: a regular file on an existing filesystem (flexible)
Zram: a compressed RAM-based swap area (compresses pages before "swapping")

Executable pages — the free lunch

If a page is clean (unmodified since loaded from the program's executable), it doesn't need to be written to swap — it can just be re-read from the original file later. Only dirty pages (modified in memory) need swap. This means program code pages are cheap to evict.

💡
Why SSDs changed the game: with HDDs, swap was painful — 10–20 ms per swap. With SSDs, it's 0.1–1 ms. This made heavier swap usage tolerable and shifted the tradeoffs of memory management significantly.

🌍 Real World — Linux Virtual Memory in Practice

What's actually in your kernel

The LRU approximation — clock algorithm

Linux doesn't do precise LRU (too expensive). It uses a two-list approach: an "active" list and an "inactive" list of pages. On each access, a page's reference bit is set by hardware. Periodically, the kernel scans pages, moving recently-referenced ones to active and demoting cold ones to inactive. Eviction happens from inactive.

The swappiness knob

/proc/sys/vm/swappiness (0–100) controls how aggressively the kernel swaps anonymous pages vs. dropping file-backed clean pages. Default is 60. Lower it to 10 for systems with lots of RAM that shouldn't swap heavily.

The OOM killer

When swap is full AND RAM is full, the kernel's last resort is the OOM killer. It scans all processes, scores them by memory usage (with adjustments for priority, root status, etc.), and SIGKILLs the highest-scoring process. Logs to dmesg with the process name and RSS size.

💡
What this means for you: if your process gets OOM-killed, it's not a bug — it's the kernel preventing system-wide failure. Reduce memory usage, add swap, or add RAM. The OOM killer doing its job is often the least-bad option.

💻 Code — The Page Fault Handler

The kernel's response to a P=0 trap

page_fault.c · conceptual
// Simplified page fault handler (educational)void handle_page_fault(uint64_t fault_addr) {    // 1. Which page faulted?    uint64_t page = fault_addr >> 12;    pte_t *pte = &current()->mm->page_table[page];    // 2. Is it a valid virtual address at all?    if (!is_mapped(page)) {        send_signal(current(), SIGSEGV);        return;    }    // 3. Find a physical frame (free or evicted)    frame_t frame = allocate_frame();    // 4. Read the page from swap / executable    read_page_from_disk(pte->disk_block, frame);    // 5. Update page table: present = 1, frame filled    pte->frame   = frame;    pte->present = 1;    invalidate_tlb_entry(page);    // 6. Return from trap → hardware retries the instruction}
The check that keeps it safe

Step 2 is crucial: not every fault is a valid demand page. If the virtual address was never mapped (a wild pointer), the fault can't be fixed — the process gets SIGSEGV and dies. Only legitimate accesses to swapped-out pages get swapped back in.

The retry semantics

After step 6, the CPU re-executes the faulting instruction. Now the page is present, so the load/store succeeds. From the process's perspective, nothing happened — just a slow memory access.

The cost of a wrong eviction

If step 3 chooses badly (evicts a hot page), the next access to that page will fault again — potentially right after. That's thrashing: the same pages faulting in a loop. This is why replacement policy matters so much.

💻 Code — The LRU Bookkeeping

What precise LRU would need

lru.c · conceptual
// Precise LRU implementation (educational — real systems approximate)struct lru_node {    uint64_t page;    struct lru_node *prev, *next;};// On every memory access — move page to headvoid lru_touch(uint64_t page) {    struct lru_node *n = lookup(page);    if (n) {        list_remove(n);        list_insert_head(n);    }}// On a fault — evict the tailuint64_t lru_evict(void) {    struct lru_node *victim = lru_tail;    uint64_t page = victim->page;    list_remove(victim);    free(victim);    return page;  // evict this from RAM}
The cost problem

lru_touch runs on every single memory access. That's a lookup, list remove, and list insert — three operations per load/store. On a modern CPU running at 3 GHz, that's impossible to do in a clock cycle.

Why real systems approximate

Linux's clock algorithm is the workaround. Each page has a reference bit set by hardware. The kernel periodically sweeps through pages: if the bit is 1, reset it and skip; if 0, evict. That's a "second chance" approximation of LRU — much cheaper, nearly as effective.

The lesson

Precise LRU is theoretically optimal for the given access pattern, but unimplementable at full speed. Real systems trade precision for speed. That tradeoff is a recurring theme in systems design.

🎭 Interactive Activity — The Human Reference String LRU Simulation

Three chairs = 3 frames. Students play the pages.

The setup

Line up three empty chairs at the front of the room to serve as a 3-frame RAM. Have a stack of cards numbered 1, 2, 3, 4, 5, 6, 7, 8. Shuffle them or use the syllabus string 1, 2, 3, 4, 1, 2.

The choreography

Call out numbers from the reference string. The student carrying that number's card rushes up and sits in an empty chair. If the number's chair is already occupied (the same student is up there), that's a hit — no change.

The LRU decision

When a new student arrives and all chairs are full, the class determines: which current sitter has been in their chair the longest without being "touched" (that is, whose number hasn't been re-called recently). That student vacates their seat back to the "disk lobby."

💡
Debrief: after the run, have the class count the misses (page faults) and hits. Ask: "What's the difference between a cold miss and an eviction miss?" Answer: cold misses are unavoidable (page never in RAM); eviction misses are the algorithm's fault (page was in RAM, got kicked out).

🏆 Grand Summary — L13 Key Takeaways

Four things to walk out with

01

Virtual memory lets a process have a virtual address space larger than physical RAM. Demand paging loads pages only when accessed — no eager loading, instant startup.

02

When a page is absent from RAM (P=0), accessing it triggers a page fault. The kernel loads the page from disk, updates the page table, and resumes the instruction. Transparent to the process, but ~10 ms per fault.

03

Page replacement decides which page to evict when RAM is full. FIFO evicts the oldest — simple but ignores usage. LRU evicts the least recently used — better, but expensive to track precisely. Real systems use approximations.

04

Thrashing is the failure state where the system spends all its time swapping. The Linux OOM killer terminates the worst offender to prevent total collapse. Working set tracking and swap tuning help avoid it.
