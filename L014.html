🎯 The Core Problem — Shared State = Shared Danger

Fast, but nondeterministic

What shared memory gives us

Threads can read and write any shared variable without going through the kernel — no syscalls, no marshalling, no copying. That's why threads are fast. It's also why they're hard.

The failure mode

When two threads read-modify-write the same variable at nearly the same time, the outcome depends on the exact instruction interleaving — which is controlled by the scheduler, which is nondeterministic. Same program, different runs, different results.

The fix

Introduce mutual exclusion: a mechanism that guarantees only one thread at a time can execute a critical region of code. Enforced by primitives like mutexes, semaphores, and atomic operations.

💡
This is the entire subject of Module 4: how do we preserve the speed of shared memory while making the results correct and predictable?

🐷 Analogy 1 · The Shared Digital Piggy Bank

Two siblings, one bank, one lost dollar

The setup

Two siblings share a digital piggy bank. It currently holds $100. Both want to deposit $1 at the exact same instant. Both hit the "deposit" button simultaneously.

The failure

Sibling A reads the balance ($100). Before A can write $101, Sibling B reads the balance — still $100. B writes $101. Then A finishes their turn and writes $101. Two dollars were deposited. The balance only went up by one.

The fix

Introduce a mutex — a single physical bathroom key taped to the bank. A sibling must grab the key, lock the room, change the balance in total isolation, and return the key. Only one sibling can be in the room at a time.

🐷 Analogy 1 · The Exact Interleaving

Read-modify-write is three steps, not one

Live · The interleaving that loses $1

Thread A · Sibling A

LOAD $100 → regA
ADD regA + 1 = $101
STORE regA → balance ($101)

Thread B · Sibling B

LOAD $100 → regB
ADD regB + 1 = $101
STORE regB → balance ($101)
What you're watching

Step-by-step, the two threads interleave. A reads first, then B reads, then A writes, then B writes. Each writes $101 — but two $1 deposits were made. The final balance is $101 instead of $102.

The key insight

Both threads did exactly what they were told. Both executed "add 1" correctly. The bug isn't in either thread — it's in the combination, which is exactly what synchronization has to prevent.

Different interleaving, different result

If A's write completed before B's read, both deposits land correctly and the balance is $102. So the same code produces different results depending on timing — that's what a race condition is.

🔒 Analogy 2 · The Transactional Database Table Row Lock

Same pattern, at database scale

The structural match

A software mutex lock behaves identically to a hardware-enforced write-reservation token that blocks out raw processor access lines to a specific memory array address index until a commit sequence resolves.

How a database does it

When a transaction wants to update row 42, it acquires a row-level lock. Other transactions that try to update row 42 block. When the first transaction commits, the lock is released and the next one proceeds — reading the updated value.

The mapping

Row → shared variable
Transaction → thread
BEGIN TRANSACTION → mutex_lock
COMMIT / ROLLBACK → mutex_unlock
Row lock wait → blocked on mutex

💡
Same concept, different layer. Databases learned to do this in the 1970s (OLTP systems); operating systems did it in the 1960s (the first mutex). The math is identical.

📖 Core Breakdown — The Non-Atomic Increment

x++ is three instructions, not one

Live · What the compiler actually emits
1
LOAD x into register R
2
ADD 1 to register R
3
STORE register R back to x
Why this is dangerous

Any one of those three steps can be interrupted by the scheduler. If the context switch happens between LOAD and STORE, the other thread sees stale data.

The requirement for correctness

All three steps must happen without interruption — as a single indivisible unit. That's the definition of an atomic operation.

The hardware solution

x86 has a LOCK INC instruction that does read-modify-write atomically at the hardware level. Other architectures have equivalents (ARM's LDREX/STREX pairs, RISC-V's AMO operations).

💡
What "atomic" means: indivisible. The entire operation completes or doesn't happen at all. There is no in-between state visible to other threads.
📖 Core Breakdown — The Bad Interleaving

Two threads, three instructions each, six possible interleavings

What can happen

Both threads execute the three instructions. If the scheduler interleaves them without any synchronization, one thread's STORE can overwrite the other's before the other reads it.

The specific sequence that fails

T1: LOAD x=5 → r1=5
T2: LOAD x=5 → r2=5
T1: ADD r1+1 = 6
T2: ADD r2+1 = 6
T1: STORE r1 → x=6
T2: STORE r2 → x=6 ← overwrites

The result

Both threads incremented. Final value is 6. Correct would be 7. One increment vanished. This is the classic lost-update problem.

📖 Core Breakdown — The Critical Section

The block of code that must not be interrupted

Formal definition

A Critical Section is a structural window of source code that reads or writes to a shared, mutable global or heap state resource. Only one thread may be inside the critical section at a time.

Identifying it

Any code that touches a shared variable is a critical section candidate.
Read-only access — usually fine (no modification).
Read-modify-write — always a critical section.
Multiple writes to related state — must all be in one section.

Why "section" and not "line"

An increment is three lines. The critical section must cover all three — otherwise another thread can slip in between them. The boundaries must contain the entire read-modify-write.

A critical section, marked
NON-CRITICAL
int y = compute();
printf("starting");
CRITICAL SECTION
shared_counter++;
shared_buffer[y] = x;
log_entry = y + 1;
NON-CRITICAL
return result;
printf("done");
📖 Core Breakdown — Mutual Exclusion

One thread in, all others wait

Formal definition

Mutual Exclusion (Mutex) is a synchronization primitive that locks out concurrent access, ensuring only one execution thread can claim a resource slot. Other threads that try to enter block until the holder releases.

The three guarantees

1. Exclusivity — at most one thread inside
2. Progress — if the section is free, some thread can enter
3. Bounded wait — a thread won't wait forever (assuming fair acquisition)

Cost

Locking and unlocking a mutex costs roughly 10–100 ns in the uncontended case, and much more under contention (because the waiting thread must be suspended and later woken). That's the price of correctness.

📖 Core Breakdown — The Atomic Operation

The hardware foundation under every mutex

Atomic vs. non-atomic
NON-ATOMIC
x++ → LOAD, ADD, STORE. Any of the three can be interrupted.
❌
ATOMIC
LOCK INC [x] → single hardware instruction, cannot be interrupted mid-way.
✅
ATOMIC
CMPXCHG (compare-and-swap) → atomically compare and replace — foundation of mutexes.
✅
ATOMIC
TEST-AND-SET → atomically set a flag and return the old value.
✅
Formal definition

An Atomic Operation is a low-level processor instruction sequence that executes completely to completion as a single indivisible unit without any possibility of preemption. No other thread can observe an intermediate state.

Why mutexes need this

A mutex's lock/unlock operation is itself built on an atomic instruction. Without atomics, no synchronization primitive could exist — because the lock acquisition itself would be a race condition.

The chicken-and-egg solution

Atomic instructions are guaranteed by the CPU hardware. Everything above — mutexes, semaphores, condition variables — is built on top of them. The CPU is the root of trust.

📖 The Mutex Solution — Serialize the Critical Section

Force the good interleaving every time

The mechanism

Wrap the critical section in pthread_mutex_lock() and pthread_mutex_unlock(). Between these, only one thread executes at a time.

What this restores

All three instructions (LOAD, ADD, STORE) run atomically with respect to other threads. No interleaving is possible — the scheduler can still switch threads, but the next thread to enter the section sees the updated value.

The result

The final counter value is always 40 — every run, every scheduler timing, every system. Deterministic. Correct. Predictable.

💡
The key trade: speed for correctness. With the mutex, threads spend some time waiting rather than computing. But the result is now correct — which is usually more important.
The same code, now protected
pthread_mutex_lock
(&lock); // enter
shared_counter++;
// critical
pthread_mutex_unlock
(&lock); // exit
final counter = 40 always ✓

💻 Code — The Broken Version

No mutex. Race condition guaranteed.

unsafe_counter.c
#include <pthread.h>#include <stdio.h>// SHARED — no mutex to protect itint shared_counter = 0;void* bump_counter(void* arg) {    for (int i = 0; i < 20; i++) {        shared_counter++;  // NOT atomic — 3 instructions    }    return NULL;}int main() {    pthread_t t1, t2;    pthread_create(&t1, NULL, bump_counter, NULL);    pthread_create(&t2, NULL, bump_counter, NULL);    pthread_join(t1, NULL);    pthread_join(t2, NULL);    // Expect 40. Often get 38, 35, 32...    printf("Final: %d\n", shared_counter);    return 0;}
The bug, line by line

shared_counter++ on line 10 is the entire problem. Both threads execute this line concurrently, and the compiler emits three instructions that can interleave badly.

Why it's not caught

Compilers don't warn about this. Static analyzers sometimes flag obvious races, but plain C has no threading semantics the compiler tracks. The bug is invisible until it manifests at runtime.

Why it's hard to debug

Attaching a debugger changes timing. Adding print statements changes timing. The bug often disappears under observation — the classic heisenbug. This is why race conditions are considered one of the hardest bug classes in software.

💻 Code — The Fixed Version

Wrap in a mutex. Correctness restored.

safe_counter.c
#include <pthread.h>#include <stdio.h>int shared_counter = 0;pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;void* bump_counter(void* arg) {    for (int i = 0; i < 20; i++) {        pthread_mutex_lock(&lock);   // ACQUIRE        shared_counter++;             // critical        pthread_mutex_unlock(&lock); // RELEASE    }    return NULL;}int main() {    pthread_t t1, t2;    pthread_create(&t1, NULL, bump_counter, NULL);    pthread_create(&t2, NULL, bump_counter, NULL);    pthread_join(t1, NULL);    pthread_join(t2, NULL);    // Always exactly 40    printf("Final: %d\n", shared_counter);    return 0;}
The three added lines

Line 5: declare the mutex
Line 10: acquire before the critical section
Line 12: release after

The discipline

Every lock must have a matching unlock on every path — including early returns, exceptions, and error branches. Missing one leaks the lock; everyone else waits forever (deadlock).

The scope

Keep the critical section as small as possible. Only the increment needs the lock — not the loop overhead, not the computation. Smaller critical sections mean less contention and faster execution.

What to notice

Same binary, same input, same machine. Different results every run. The nondeterminism comes from timing — where the scheduler decides to preempt.

Why this is a nightmare

Reproducing a bug that happens 1-in-10 runs is already hard. Reproducing one that depends on exact microsecond scheduling is nearly impossible. This is why "it works on my machine" is a real cliché for race condition bugs.

The fix is simple

With the mutex, all 8 runs print 40. Every time. The nondeterminism is entirely eliminated by the mutual exclusion.

📖 Race Conditions Beyond Simple Counters

Counters are just the simplest case

📝
Linked list insertion
Two threads insert at the head simultaneously. One insertion gets lost, or the list corrupts. Requires locking the head pointer (or using atomic pointers with careful design).
💾
Banking transactions
Check balance, if sufficient then withdraw. Two threads can both see $100, both withdraw $100, account goes to -$100. Classic TOCTOU — time-of-check-to-time-of-use.
🔍
Lazy initialization
Two threads both see `instance == NULL`, both allocate new instances, one leaks. Requires double-checked locking (with memory barriers) or `pthread_once`.
📊
Statistics aggregation
Threads atomically updating a shared count and sum. Two threads can update one but not the other, leaving them inconsistent. Requires protecting both, or using atomic operations on both.
💡
The general pattern: anytime you have check-then-act or read-modify-write on shared state, you have a potential race. The mutex prevents the interleaving; the critical question is always "what's the smallest region that must be protected?"
🌍 Real World — Famous Race Condition Bugs

Race conditions have caused real damage

🏥
Therac-25 · 1985–1987
A race condition in the radiation therapy machine's software allowed operators to administer massive overdose. Six patients injured, three died. The race involved editing parameters too fast for the UI to keep up.
💸
Knight Capital · 2012
A deployment race condition caused a trading firm to execute $3.5 billion of unintended trades in 45 minutes. The firm lost $440 million and was acquired two days later. The bug: an old server was still running old code and joined the cluster mid-deploy.
🚀
Mars Pathfinder · 1997
We covered this in L08 — priority inversion isn't exactly a race, but it's a related concurrency bug. A mutex-protected resource caused the high-priority task to miss deadlines, triggering watchdog reboots.
🔐
Therac-25 class of bugs · ongoing
Race conditions in security-sensitive code are especially dangerous — TOCTOU attacks (time-of-check-to-time-of-use) exploit the gap between "I verified you have permission" and "I perform the operation."
💡
The lesson: mutexes aren't theoretical — they're the difference between "the program works" and "the program causes a national financial incident." The next time you write concurrent code, take this lecture seriously.
🏷️ System Lexicon — Race & Critical Section
Race Condition
Term 01 of 04
Formal Definition

A concurrency bug where the system output shifts nondeterministically based on the precise timing and execution order of overlapping threads.

Plain Translation

( The same code produces different results because the threads happen to interleave differently. )

Classic symptom

Bug disappears under a debugger or when you add print statements. That's because the debugger slows execution and changes the interleaving.

Critical Section
Term 02 of 04
Formal Definition

A structural window of source code that reads or writes to a shared, mutable global or heap state resource.

Plain Translation

( The lines of code that must not run concurrently with another thread's version of the same lines. )

Rule of thumb

Any read-modify-write of a shared variable is a critical section. Any check-then-act on shared state is a critical section. If you can't decide, assume it is.

⚖️ The Cost of Synchronization

Mutexes aren't free — here's the actual price

✓ Correctness guarantees

Deterministic resultguaranteed
Lost updateseliminated
Data corruptionprevented
Debug time savedhours to days

⚠ Performance overhead

Uncontended lock~10–20 ns
Contended lock~100–1000 ns
Context switch (wait)~2–20 µs
Lost parallelismsignificant
The design rule

Use the smallest possible critical section. Lock only what you have to. If you have one shared counter, protect only the increment — not the surrounding loop, not the computation, not the print statement. Smaller section = shorter lock hold time = less contention = more parallelism.

💡
An anti-pattern: "coarse-grained locking." A single global mutex for everything is easy to reason about but kills parallelism — threads queue up on the lock and effectively run serially. Sometimes that's fine (e.g., Python's GIL). Often it isn't.
🛑 Three Student Pitfalls

What beginners get wrong about race conditions

PITFALL 01
"The race condition only happens sometimes, so it's not a real bug"
A race condition that "only happens sometimes" is a worse bug, not a lesser one. It hides in testing, ships to production, and causes catastrophic failures at 3 AM on a full moon. The correct response to "it works on my machine" for concurrent code is: "then test it on mine."
PITFALL 02
"Adding a mutex is always the right fix"
Sometimes it is. Sometimes the right fix is to not share state — restructure the code so each thread has its own copy, then merge at the end. Sometimes atomic operations are enough and cheaper. Sometimes a lock-free data structure is appropriate. The mutex is a hammer; not every shared-state problem is a nail.
PITFALL 03
"Locking everywhere makes the code safe"
Over-locking causes its own problems: deadlocks (L15), convoy effects, and priority inversion (L08). Fine-grained locking is safer if done carefully, but harder to get right. The real art is knowing what to lock and when, not just adding locks everywhere.
🎭 Interactive Activity — The Shared Whiteboard Disruption

Two markers. One number. Who wins?

The setup

Draw a large single number "0" on the center of the classroom whiteboard. Appoint two students to act as Threads.

The rule

Instruct them: their only loop is to read the board number, add 1 in their head, and write the new value over the old one. Have them both try to do this simultaneously, as fast as possible, with different colored markers.

The observation

Watch how their writing overrides each other. If Thread A writes "5" while Thread B is still reading "4", B will write "5" as well. The final number is less than it should be. That's the race in action — physically, visibly, in real time.

The fix

Introduce the "mutex" — a single physical object (say, a sticky note) that only one student can hold. To write on the board, a student must hold the sticky note. The other student waits until it's returned. Now the number is always correct.

💡
Debrief question: ask the class "Why doesn't the count come out right without the mutex?" The answer — interleaved read-modify-write — should now feel obvious and physical, not abstract.

🏆 Grand Summary — L14 Key Takeaways

Four things to walk out with

01

A race condition occurs when two threads read-modify-write shared state concurrently, and the result depends on the exact interleaving. Same code, different results, unpredictable timing.

02

x++ is three instructions (LOAD, ADD, STORE), not one atomic operation. The critical section must encompass all three to guarantee correctness.

03

Mutual exclusion — implemented via mutex — ensures only one thread enters the critical section at a time. It eliminates the race at the cost of some parallelism.

04

All synchronization primitives are built on atomic hardware instructions. Without CPU-level atomics, no software mutex could exist.
