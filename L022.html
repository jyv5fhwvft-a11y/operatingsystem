🎯 The Core Problem — The Trust Question

How do we ensure Alice cannot read Bob's files?

The exact problem

How do we ensure that user Alice cannot read user Bob's files, and that malware cannot exploit a bug to seize control of the entire supervisor Kernel?

Two failure modes to prevent

1. Horizontal attack: Alice reads or writes Bob's private documents, emails, or credentials.

2. Vertical attack: A bug in an unprivileged app lets it climb into Ring 0 and own the whole machine.

The resolution — both are access control

Every byte of memory, every device node, every file — needs a protection boundary that says: "who is this caller, and are they allowed to perform this operation on this object?" The kernel must answer this question billions of times per second without slowing the system down.

💡
The design tension: checking every access is expensive. The entire field of access control is about organizing who's allowed to do what — so the check is fast, unambiguous, and enforceable by Ring 0 alone.
The forbidden requests the kernel must deny
🏨 Analogy 1 · The Hotel Room Ledger vs. The Physical Room Key

Two ways to answer: "can this guest enter?"

The setup

Imagine a hotel security framework. One design approach checks an explicit sheet clipped right onto the door frame: "Who is allowed into Room 204?" — resource-centric.

Another design completely ignores the doors and hands you an electronic keycard token that simply works instantly on whichever lock it fits — user-centric.

The ledger approach — ACL

Each door (resource) carries its own access list. "Room 204: Alice ✓, Bob ✓, Charlie ✕." The decision lives with the resource.

The keycard approach — Capability

Alice carries a physical token. The token is checked by the lock — if she holds a valid key for this door, it opens. The decision lives with the user.

💡
The deep insight: both approaches encode the same information — "Alice can enter Room 204." One stores it at the door; the other stores it on Alice. Both are valid. The choice depends on which operation is more common: checking the door, or moving Alice between doors?

🏨 Analogy 1 · The Two Models Visualized

Where does the decision live?

Resource-centric · ACL

The decision lives at the object. Every resource maintains a list of subjects and their rights. To answer "can Alice read this?", we read this resource's list.

Pro: revoking access to one resource is trivial — just edit the list. Con: finding "everything Alice can read" requires scanning every resource.

User-centric · Capability

The decision lives at the subject. Every user holds a set of unforgeable tokens, each one granting specific rights to a specific object. To answer "can Alice read this?", we inspect Alice's tokens.

Pro: answering "what can Alice access?" is instant. Con: revoking one token requires tracking down where it's held (which is why true capabilities are often short-lived).

The unifying truth

Both decompose the same matrix. One prunes it by column. One prunes it by row. Neither invents new information — they just choose where to store the fact.

🔗 Analogy 2 · Pure Technical — NFS Mount Rules vs. JWT Bearer Tokens

The same polarity in real systems

Two real-world encodings
STATELESS NETWORK FS MOUNT RULES · ACL-style
/exports → 10.0.0.0/24 (rw, no_root_squash)
/backup → *.eng.example.com (ro)
/home/alice → host "laptop-a" (rw)
Decision stored ON the export (the resource)
CRYPTOGRAPHIC JWT BEARER TOKEN · Capability-style
header: {"alg":"RS256"}
payload: {"sub":"alice","scope":"read:/api/docs"}
sig: HW-bound, uncheangeable
Decision carried BY the user in an unforgeable token
ACL · Firewall-rule-like

An ACL acts like a firewall rule table mapped directly onto a disk block node. Every time the resource is touched, the list is consulted. The policy lives with the asset.

Capability · Kernel-signed descriptor

A capability behaves like an unforgeable, kernel-signed memory address descriptor held by a running thread. Presenting the token is the proof of access — no further lookup required.

Why both exist

Both encodings solve the same problem: describing who may do what. The engineering choice depends on distribution, revocation, and speed. Real systems often use both simultaneously.

💡
The dictionary lesson: an NFS export table says "this host may mount this share". A JWT says "whoever bears this signed token may access this API". The first checks at the door; the second is checked by bearing.

📖 Core Breakdown · Protection Domains

Every running thread has a protection domain

What a domain is

A protection domain is the bounded environment profile that determines which operations a thread is permitted to execute across various system objects. It's the "scope of authority" the thread carries with it as it runs.

How it's realized in Unix

In a Unix-like kernel, the domain is largely determined by the credentials attached to the process: effective UID, effective GID, supplementary groups, and any elevated capabilities. Every permission check is made against this domain — not against "the user" in some abstract sense.

When it changes

setuid binaries → temporarily adopt another domain
sudo → switch effective UID to 0
setgid → adopt a group domain
Linux capabilities → narrow or expand the set of privileged operations

💡
The key insight: access control is not just about "who you are" — it's about which domain the thread is currently running in. The same user, in different domains, may be allowed or denied the same operation.
A process and its protection domain
📖 Core Breakdown · The Access Control Matrix

A grid that maps every subject × every object

The formal definition

A conceptual grid mapping user domains (subjects) against system objects (resources) to define structural read, write, and execute permissions.

The axes

Rows — subjects (Alice, Bob, Charlie…)
Columns — objects (/etc/passwd, /dev/sda…)
Cell (i, j) — the rights subject i has on object j

What a cell can say

R — read
W — write
X — execute
— — no rights

💡
The whole point: the matrix is the model. Every implementation you'll see — ACLs, capabilities, Unix mode bits, POSIX ACLs — is a compact encoding of some part of this matrix.

Mallory — — — —

Every cell is a "can subject X do action on object Y?" question. The next slide asks: how do we actually implement this at scale?

📖 Core Breakdown · The Sparse Matrix Problem

A matrix with millions of blanks

The scale reality

A real system has tens of thousands of subjects and millions of objects. Multiplying those out gives a matrix with billions of cells — and the overwhelming majority are empty. That's called a sparse matrix.

Why we can't store it full

Even one bit per cell (say, "read: yes/no") would require gigabytes just to represent the grid — before storing any file content. That's absurd. Memory would be consumed entirely by access metadata.

The resolution — decompose

Production kernels don't store the full matrix. They store only the non-empty cells — and they choose to organize those non-empty cells either by column (ACL) or by row (capability). Both store the exact same information. Both are correct. The engineering tradeoffs determine which one is right for a given system.

💡
The two bookkeeping methodologies: ACLs decompose the matrix by columns, attaching a strict authorization list directly to the asset container. Capabilities decompose by rows, producing unforgeable tokens carried and presented by the active user process.
Decomposition of a sparse matrix
📖 Core Breakdown · ACL — Access Control List

A list attached to the resource

The formal definition

A column-oriented optimization where resource permissions are tracked directly on the asset container.

The intuition

Every file, every device node, every directory carries its own little list: "who may do what to me?" When Alice calls open() on a file, the kernel reads that file's list and asks: "is Alice on it, and does she have the right to read?"

Where you see it

Unix mode bits → 9 bits, one "ACL"
POSIX ACLs → per-user / per-group entries via setfacl
NFS exports → host- and netgroup-based lists
firewall rules → list of allowed senders per port

The tradeoff

Pro: revoking is cheap — just edit one file's ACL. Con: answering "what can Alice access?" requires walking every object's list. In a matrix with a billion objects, that's an expensive query.

Charlie —
Mallory —

The list travels with the file. Every access check reads the file's own ACL.

📖 Core Breakdown · Capability Tokens

A token carried by the user

The formal definition

A row-oriented security optimization where unforgeable access tokens are carried and presented by the active user process.

The intuition

Alice doesn't ask "does this file allow me?" She presents a token she already holds: { object: /home/bob/resume.pdf, rights: read }. If the kernel can verify the token is genuine, access is granted — no lookup on the resource required.

Unforgeability is the guarantee

A token must be impossible for user code to fabricate. In real systems this is achieved by keeping tokens in kernel memory (user code only holds an index into a kernel table) or cryptographically signing them (as in JWTs). The unforgeability is the whole point.

The tradeoff

Pro: "what can Alice access?" is instant — just look at her tokens. Con: revoking a token requires finding every holder. This is why real capabilities are often short-lived or confined to a process tree.

Live · One user, many tokens
SUBJECT · Alice
/home/alice/notes.txt READ · WRITE · EXECUTE
/dev/tty READ · WRITE
/tmp/alice.sock CONNECT

The tokens travel with Alice. Every access check just verifies the presented token.

📖 Core Breakdown · The Two Optimizations Side by Side

Same matrix. Opposite projections.

The comparison
ACL · COLUMN-ORIENTED
Stored on: the resource
Check speed: O(list length)
Revoke one: trivial — edit the list
Audit subject: expensive — scan all
Best when: resources are authoritative
Real world: Unix modes, POSIX ACLs, NFS exports
CAPABILITY · ROW-ORIENTED
Stored on: the subject
Check speed: O(1) token verify
Revoke one: hard — find every holder
Audit subject: instant — read tokens
Best when: distribution/delegation matters
Real world: JWT, Plan 9, seL4, Genode
Which one is "right"?

Neither. They are mathematically equivalent encodings of the same matrix. The choice is a systems engineering trade-off based on distribution, revocation, and workload patterns.

The blend in real Unix

Linux mixes both. File permissions are ACLs on inodes. But when a process opens a file, the kernel returns a file descriptor — and that fd is effectively a short-lived capability the process presents in every subsequent read/write call. The fd is the capability; the mode bits are the ACL. The two live side by side.

Takeaway

Access control isn't about picking a side. It's about understanding that a matrix can be decomposed two ways — and picking the decomposition that makes the common case fast.

💡
The file descriptor revelation: the fd is unforgeable (only the kernel can mint one), it identifies the object, and it carries the rights the process acquired at open time. That's a capability — hidden in plain sight.
📖 Practical Example · The Linux 9-Bit Permission Vector

The ACL, compressed to nine bits

The compression

Standard Unix file systems compact the entire ACL architecture down to nine simple permission bits grouped into three classes: Owner, Group, and Others.

The bit layout

bit 8 7 6 → owner (read, write, execute)
bit 5 4 3 → group (read, write, execute)
bit 2 1 0 → others (read, write, execute)

Why it works

Because on a Unix-like system, the vast majority of access checks are answered correctly by the user's primary owner ID or primary group ID. Nine bits cover 99% of the cases at almost zero storage cost.

Where it runs out

POSIX ACLs extend this when you need per-user or per-group entries beyond the nine bits. But the default 9-bit model remains the baseline every Unix-like system inherits.

📖 Practical Example · rwxr-xr-- Walkthrough

What rwxr-xr-- actually means

Live · Decoding the mode string
user@box — decoding a mode
$ stat -c "%A %U:%G %n" report.txt
The mode string

-rwxr-xr--

The leading - is the file type (regular file). Then three triplets:

Owner · rwx

Read, write, execute. The file's owner has full access — can read, modify, and run the file (if executable). In the practical example from the source: the owner has full read, write, and execute permissions.

Group · r-x

Read and execute, no write. Group members can read the file and run it, but cannot modify it. Group members can read and execute.

Others · r--

Read only. All external system callers can strictly read the asset contents without modifying them.

💡
The full sentence: "Owner may read, write, and execute. Group may read and execute. Everyone else may only read." That single short string — 10 characters — is the entire ACL for this file.
📖 The Access Check at open() Time

Where the kernel actually decides

The exact moment

The permission decision happens at open() time — not every read/write. Once open() succeeds, the returned file descriptor is already the "capability" — subsequent read()/write() calls don't re-check permissions.

The steps

1. user → open("/home/bob/resume.pdf", O_RDONLY)
2. VFS → resolve path → inode of resume.pdf
3. VFS → read inode's mode bits + ACL
4. kernel → build the requesting domain (euid, egid, groups)
5. inode_permission() → compare domain against bits
6. allow → return fd; deny → return -EACCES

Why this design

Doing the check once at open-time is dramatically cheaper than re-checking on every read — and it's what turns file descriptors into capabilities. That's the ACL side of the system handing out a row-oriented token in the same breath.

See the 9 bits in the wild

What to read first

The first column of ls -l output is the mode string. Look at the first character:

- → regular file
d → directory
l → symlink
b → block device (L21)
c → character device (L21)

Then read the triplets

The next nine characters are the owner triplet, the group triplet, and the others triplet — exactly the 9-bit ACL we covered.

Then read owner and group

Columns 3 and 4 are the owner name and group name. Together with the mode string, they fully identify the ACL: who owns this, and what may each class do?

🛑 Three Student Pitfalls

What beginners get wrong about access control

PITFALL 01
"ACL and capability are opposites"
They're not opposites — they're two projections of the same matrix. ACL is the column projection; capability is the row projection. You don't pick "the right one"; you pick the projection whose common case is fast. Modern systems blend both: Linux file permissions are an ACL, but an open file descriptor is a capability.
PITFALL 02
"The kernel re-checks permissions on every read()"
It doesn't. The permission decision happens at open() time. Once a valid file descriptor is returned, subsequent read() and write() calls rely on the fd — that's the whole point of the capability-style optimization. Changing a file's permissions while it's already open does not affect the open fd.
PITFALL 03
"rwxr-xr-- is the whole story"
The 9 bits are a compressed ACL, not the full matrix. They only cover owner, group, and others — three classes. For per-user or per-group entries beyond that, you need POSIX ACLs (setfacl, getfacl), Linux capabilities (for fine-grained privileged operations), or SELinux/AppArmor policies. The 9 bits are the baseline, not the ceiling.

⚠️ A naming trap worth knowing

Linux "capabilities" (as in cap_net_bind_service) are not the same as OS-theory "capabilities" (unforgeable access tokens à la Amoeba). The Linux word describes piecemeal root privileges — a way to grant one privileged operation without full root. It's a different concept that unfortunately shares the same name.

💡
Try this at home: run getfacl /etc/passwd to see the ACL. Then getcap /usr/bin/ping to see what Linux capabilities that binary carries — usually cap_net_raw, which is how ping sends ICMP packets without being setuid-root.

🌉 The Identity Question — A Bridge to L23

Access control assumes we already know who is asking

The unfinished sentence

Every ACL, every capability, every mode bit answers a question of the form: "Can subject S perform action A on object O?"

But look closely — the whole mechanism assumes we already know the subject. Every design in L22 relies on the kernel having a trustworthy answer to "who is S?"

The failure mode if identity is broken

If Alice can convince the kernel she is Bob, then every ACL protecting Bob's files becomes irrelevant. Access control is a lock; authentication is the key check at the door. A perfect lock with a broken key is useless.

The bridge

Access control lists only work if the system possesses an unshakeable mechanism to verify the identity of the user calling them. That mechanism is the subject of L23 — Authentication.

💡
The handoff: L22 defines what each subject is allowed to do. L23 defines how the kernel proves who the subject actually is. Together they form the two halves of any secure operating system.
The two halves of security
🏆 Grand Summary — L22 Key Takeaways

Four things to walk out with

01

The Access Control Matrix — subjects × objects — is the conceptual foundation of every access control scheme. It asks one question per cell: "may this subject do this action to this object?"

02

Because real matrices are massive and sparse, kernels store only the non-empty cells. ACLs decompose by column (list attached to the resource); capabilities decompose by row (token carried by the subject). Both encode the same information.

03

Every thread carries a protection domain — its effective UID, GID, supplementary groups, and capabilities. Permission checks are made against this domain, not some abstract "user" — which is why sudo can grant access: it changes the domain.

04

Linux compresses the entire ACL to 9 bits — owner / group / others × read / write / execute. That's the baseline Unix permission model, and it's what ls -l shows you at the start of every line. It's the ACL, compressed to the point of invisibility.
