🔰 🏛️ L06 · Process Execution Mechanics

How does a process duplicate itself, then replace itself — and how does the CPU swap between them?

Explain the exact operational lifecycle difference between cloning an address space (fork) and overriding an address space (exec), and trace register states during a context switch.

The Core Question of L06

We know what a process is. But how does Linux create a new one? How does ls become the program that runs? And how does the CPU swap from process A to B without either noticing?

🎯 Three Mechanisms, One Lifecycle

fork · exec · context switch — the trio that runs every program

fork()

Duplicates the current process into a new child process. The child is an identical copy — same memory, same registers, same open files, same instruction pointer. It gets a new PID.

pid_t fork(void)

exec()

Replaces the current process's address space with a new executable image. The PID stays the same, but everything else — code, data, heap, stack — gets wiped and reloaded.

int execv(path, argv)

Context Switch

The kernel pauses process A, saves its registers into A's PCB, loads B's registers from B's PCB, and resumes B. A happens many times per second — transparently.

The two-step pattern

Every new program launch in Unix is fork + exec. The shell forks itself, and the child calls exec to load the target program. Context switch is what makes multitasking possible in between.

🏃 Analogy 1 · Swapping Runners Mid-Relay

Three events, one track-and-field metaphor

fork() = duplicate the runner

The current runner magically duplicates themselves into a perfect clone standing right next to them. Both clones have the exact same muscle memory, are running at the exact same speed, and are looking at the exact same spot on the track.

exec() = new script, same body

That runner keeps their physical body but instantly receives an entirely new task script — throwing a javelin instead of running. Same athlete, completely different activity.

Context switch = the referee

The referee pauses the race, carefully writes down exactly where the current runner stood, makes them step aside, and lets the next runner onto the track based on their previously recorded track position ledger.

🧬 fork() — The Complete Clone

One process becomes two — identical in every way except PID

What gets copied at fork()
Address space text, data, heap, stack
File descriptors fd 0, 1, 2 + all open
Environment all env vars
Program counter same instruction
CPU registers all 16 saved
PID NEW — different
What actually happens

The kernel clones the calling process. It allocates a new PCB, copies the parent's register state into it, marks a new PID, and sets up a duplicate address space (lazily — we'll see COW next).

The result

Two runnable processes. Both have identical memory contents. Both are at the same instruction. Both will next execute the instruction after the fork() call. The only way to tell them apart is the return value of fork().

What is NOT copied

PID (obviously), parent PID (PPid changes), CPU time counters, memory locks, certain signals. So "identical" isn't quite right — but for the memory contents and program state, it is.

💡
Analogy sharpened: fork is like a save-and-fork in a video game — two save slots with identical state. From now on, they diverge independently.
🎯 fork() — The Return Value Branch

One call, two different return values — that's the branching mechanism

The fork() return value determines the branch
pid_t rc = fork();
→
rc < 0 · fork failed
pid_t rc = fork();
→
rc == 0 · this is the CHILD
pid_t rc = fork();
→
rc > 0 · this is the PARENT (rc = child's PID)

Both processes return from fork() at the same line of code — but with different return values. That's how each side knows which branch to take.

Why 0 in the child?

Because the child doesn't need to know the parent's PID to do its job. The parent, however, needs to know the child's PID to be able to wait() on it, send it signals, or report it.

What failure looks like

rc < 0 means the kernel couldn't allocate a new PCB or address space — usually due to a process limit (ulimit -u) or out of memory. Only the parent continues; no child is created.

The classic beginner bug

Forgetting that both processes return from the same line. New programmers often write fork(); printf("hi\n"); and get "hi" printed twice — once per process.

📋 Copy-on-Write — Why fork() Is Actually Fast

Modern kernels do not copy the whole address space at fork

Naive approach (old)

Copy every page of the parent's memory into new physical pages. For a browser with 2 GB of RAM, fork() would take hundreds of milliseconds — way too slow for a shell prompt.

Copy-on-Write (modern)

The kernel copies only the page table, and marks all shared pages read-only in both processes. Both process page tables now point to the same physical frames. No data is copied.

The "write" trigger

If either process tries to write to a shared page, the MMU fires a page fault. The kernel catches it, copies that one page to a new frame, updates the page table, and resumes — with each process now owning its own copy of that page.

♿
Micro-Accessibility Context: COW is why fork() is nearly instant even for huge processes. Most processes only modify a few pages after fork — usually only the ones in the fork-then-exec pattern, which we'll see next get replaced entirely by exec anyway.

🔄 exec() — The Complete Replacement

Same process, entirely new program

FDs0,1,2 (kept)

What exec does

Wipes the current process's address space — text, data, heap, stack all gone — and loads a brand new executable binary from disk into it. The process becomes a different program.

What stays

The PID stays. Open file descriptors stay (unless marked FD_CLOEXEC). The parent PID stays. Environment variables pass through. So the shell's child process becomes the program you ran — but stays the same process from the kernel's point of view.

What dies

Any memory allocated in the parent process — even if the child is about to exec — is thrown away when exec runs. This is why fork+exec is efficient: the COW copies get discarded before they ever happen.

💡
The clever bit: if exec succeeds, it never returns. Control transfers to the new program's entry point (main()). Only if exec fails does it return with -1.
🧬 The exec Family — 6 Variants, One Job

Same operation, different argument-passing conventions

The family tree
execl list args · path
execv vector args · path
execle list args · envp
execve vector args · envp · the syscall
execlp list args · PATH search
execvp vector args · PATH search
The naming convention

l = list args (varargs)
v = vector args (array)
e = custom envp
p = search PATH
none = full path required

The one that matters

execve is the actual syscall. Every other variant is a libc wrapper that massages arguments and calls execve underneath. If you know execve, you know them all.

When to use which

execvp is the most common in shell-like code — it searches PATH for you. execve is what you use if you know the full path and want to control the environment exactly.

🔀 The Context Switch — The Third Mechanism

The kernel saves one process, loads another

Live · The four-step context switch
01
Save outgoing registers
Read all CPU registers, write them into process A's PCB
02
Save outgoing PC
Write A's program counter (RIP) into A's PCB
03
Load incoming registers
Read B's saved registers from B's PCB, write to CPU
04
Load incoming PC
Read B's saved PC, jump execution to that address
What triggers a context switch

1. Time slice expires (preemptive scheduling)
2. A process blocks on I/O
3. A higher-priority process becomes ready
4. A process calls yield() or sleep()

Where it happens

The switch occurs inside the kernel, in Ring 0. Usually inside the scheduler or in the timer interrupt handler. The user-space code never sees it.

What the processes observe

Nothing. Each process believes it was running continuously. Time simply "passed." Only the kernel tracks that other processes ran in the gap.

💡
How often? A modern Linux desktop at idle does about 100–500 context switches per second. Under load, it can be tens of thousands per second — the scheduler is very busy.
⏱️ The Context Switch Tax

Not free — and the cost is mostly invisible cache damage

The direct cost

Saving 16 registers + PC + flags + swapping the page table base (CR3 on x86) costs roughly 1–5 microseconds. Fast in absolute terms.

The indirect cost — cache pollution

After the switch, process B's code and data aren't in the L1 or L2 cache — those were full of A's. B runs slowly for the first few thousand instructions while its working set reloads from main memory. This dominates the real cost.

The TLB cost

On a context switch, the TLB (virtual-to-physical address cache) usually has to be flushed, because A's entries are for A's page table, not B's. The first N memory accesses after the switch must walk the page table — much slower than a TLB hit.

♿
Micro-Accessibility Context: This is exactly why the L07/L08 scheduling lectures obsess over quantum sizes. Too many switches = cache thrashing. Too few = poor responsiveness. There's a sweet spot.
Live · Relative costs (log scale)
Direct function call~5 ns
Context switch (direct)~2 µs
Context switch + cache reload~20 µs

The visible cost of ~2 µs is not the whole story. The real cost — cache reload — is ~10× higher and invisible to most profilers.

🌿 Analogy 2 · Git Branch vs. Project Overwrite

The pure technical structural match

fork() ≈ git branch

A git branch duplicates the exact state of the commit timeline into an isolated copy. The new branch shares every commit up to the branch point. From that point on, commits on one branch don't affect the other.

$ git branch child-branch

exec() ≈ project overwrite

Deleting all code files in a folder and cloning a completely different repository into that exact same directory path. Same folder, same path — entirely different content.

$ rm -rf * && git clone other-project

What the metaphor captures

fork preserves the original timeline; the new branch is a divergence. exec destroys the original timeline; the working directory becomes a completely different codebase.

Where the metaphor breaks

Git branches share physical disk storage (hardlinks / packed objects). fork's address space is truly independent — the child modifies its own memory. So think of fork as a full physical copy of the working tree, not a git branch with shared objects.

🔨 The Two-Step Shell Pattern

How every program you run gets launched: fork + exec + wait

The canonical launch sequence
Step 1 · fork()

The shell duplicates itself. Now two copies exist — both are running the same shell code at the same instruction.

Step 2 · exec()

The child calls execve("/bin/ls") and becomes ls — completely different program, same PID. The parent goes to sleep in wait().

Step 3 · wait()

Parent blocks until the child exits, then returns to the prompt. Every command you type runs through this exact pattern — even echo hi.

💡
Why not just exec in the shell? Because then the shell would be replaced by the command — and you'd lose your shell session after every command. The fork lets the shell stay alive.
💻 Code — The Classic fork + exec Shell

Six lines that launch every command in Linux

shell_launcher.c
#include <unistd.h>#include <sys/wait.h>#include <stdio.h>int main() {    pid_t rc = fork();       // clone the shell    if (rc < 0) {        perror("fork failed");        return 1;    } else if (rc == 0) {        // CHILD · replace self with /bin/ls        char *args[] = { "/bin/ls", "-l", NULL };        execv(args[0], args);        // exec only returns on failure        perror("exec failed");        _exit(1);    } else {        // PARENT · wait for child        wait(NULL);        printf("child exited\n");    }    return 0;}
Line 5 · the fork

One call, but execution now splits into two paths. rc will have a different value in each.

Lines 15–18 · the child

The child calls execv. If it succeeds, the child's shell code is gone — ls runs instead. If it returns, exec failed and we bail.

Lines 20–22 · the parent

The parent calls wait(NULL) to block until the child exits. Then the parent prints and returns to the prompt — ready for the next command.

💡
Note the _exit() in the child: not exit(). The underscore version is the raw syscall and doesn't run atexit handlers — important because after a failed exec the child shouldn't inherit the shell's buffered output.
🔍 Walkthrough — The Exact Timeline

What the CPU does, line by line

Live · Execution interleaving
[shell] pid 1000: rc = fork()
[parent] pid 1000: rc = 1001 (child's pid)
[child] pid 1001: rc = 0
[parent] pid 1000: rc > 0 → wait(NULL) blocks
[child] pid 1001: rc == 0 → execv("/bin/ls", ...)
[child] pid 1001: becomes ls · runs · prints files
[child] pid 1001: exit(0)
[parent] pid 1000: wait() returns · printf runs
[shell] pid 1000: back to prompt
The key insight

Notice the parent blocks at wait() and does nothing while the child runs. This is normal — the shell isn't consuming CPU, it's just waiting for the child to exit.

The PID stays the same

The child (pid 1001) is a different PID from the shell (pid 1000), even though it inherits everything. Then exec preserves 1001 — so the kernel sees ls as pid 1001 running from the shell's earlier state.

The prediction challenge

How many lines of "hi" will print?

a) 1     b) 2     c) 3     d) 4

The answer

4 lines. Because the first fork creates 2 processes, and the second fork creates 2 more from each of them. Total 4 processes, each printing once.

The mental model

N fork() calls in a row create 2^N processes. Two forks → 4 processes → 4 prints. This trips up beginners constantly.

💀 Aftermath — Zombie and Orphan Processes

What happens when processes outlive their parent — or vice versa?

Zombie Process

Child exits, parent hasn't waited

The child is dead but its PCB can't be reclaimed until the parent calls wait() and reads the exit status. The PID stays allocated. On ps, it shows as defunct.

Orphan Process

Parent exits before child

The child keeps running but loses its parent. It's immediately reparented to PID 1 (init/systemd), which adopts and eventually reaps it. Normal and harmless.

Why zombies are bad

A zombie uses a PID slot but no memory. Hundreds of zombies exhaust the process table — at which point fork() fails and the system can't create new processes. They're a real production incident.

The fix

Parents must call wait() or waitpid() to reap children. If a parent can't (or won't), the fix is to install a SIGCHLD handler that reaps automatically.

Why orphans are fine

Because the kernel reparents them to PID 1, which is guaranteed to call wait() — so no zombie accumulates. This is the design pattern behind daemons: fork, exit parent, and the child becomes an orphan adopted by init.

💣 The Classic Fork Bomb — When fork() Goes Too Far

Nine characters that freeze a machine

The famous fork bomb 
:(){ :|:& };:
What it does

A function named : that calls itself twice and backgrounds each call. Every process forks twice. Exponential growth: 1 → 2 → 4 → 8 → 16 → ... until the process table is full and the machine freezes.

Why modern systems survive it

Most Linux systems have a per-user process limit (ulimit -u) that stops the explosion. Container environments enforce stricter limits still. Never run this on a system without limits.

💡
Educational point: this is why ulimit, process isolation, and cgroups exist. A single malicious script should not be able to take down the system.

Term 02 of 04
Formal Definition

Returns

Running strace -f -e trace=fork,execve,wait4 <command> on any process shows you the actual lifecycle. It's the best way to build intuition about these mechanisms.

Not just shells

Python's subprocess.run(), Node's child_process.spawn(), Git's hooks, cron jobs, systemd services — all use this exact pattern.

🛑 Three Classic Pitfalls

What beginners always get wrong about fork/exec

Pitfall 01 — "fork returns once"

It returns twice — once in the parent and once in the child. If your code doesn't check the return value, both parent and child execute the same code path, often causing duplicate work or subtle bugs.

Pitfall 02 — "exec is like fork"

They're opposites. fork copies. exec replaces. exec doesn't create a new process — it turns the calling process into a different program, keeping the PID. If you exec without forking first, the calling program is gone forever.

Pitfall 03 — "context switch is instant"

No — it's ~2 µs direct but ~20 µs effective once you account for cache pollution and TLB flush. This is why 10,000 switches per second of very tiny work is slower than 1,000 switches of 10× work. Throughput vs. latency tradeoff.

🔬 Advanced — Beyond fork+exec

Three more modern mechanisms worth knowing

vfork()

A specialized fork that suspends the parent and shares its address space with the child until exec. No copy at all. Only safe if the child immediately execs. Older optimization — largely replaced by COW.

posix_spawn()

A combined fork+exec as a single function call, optimized by the libc to skip the fork entirely on systems that support it. What modern code should use when it just wants to launch a program.

clone()

The raw syscall underlying fork() on Linux. Takes flags that control what gets shared: memory, file descriptors, signal handlers. Threads are clone() with shared memory — this is the bridge to L09.

Why knowing these matters

When you're debugging why a forked process is slow, understanding vfork and clone is essential. When you write a shell, knowing posix_spawn saves you from common pitfalls.

🏆 Grand Summary — L06 Key Takeaways

Four things to walk out with

01

fork() duplicates the current process. It returns twice — 0 in the child, child's PID in the parent. Both branches now run independently.

02

exec() replaces the current process's address space with a new program. Same PID, entirely new code. If it succeeds, it never returns.

03

Context switch is how the kernel swaps between processes. It saves the outgoing PCB's registers and loads the incoming PCB's. Direct cost ~2 µs, real cost ~20 µs due to cache pollution.

04

fork + exec is the universal launch pattern. Every command you run through a shell uses it. Copy-on-Write makes fork fast; exec then discards the copies before they ever happen.
