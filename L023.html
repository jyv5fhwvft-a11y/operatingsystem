🎯 The Core Problem — Identity Before Policy

Access control assumes we already know who's asking

The gap L22 left open

Every ACL, capability, and mode bit answers a question of the form: "Can subject S perform action A on object O?" But the entire mechanism silently assumes we already know the subject.

The failure mode

If Alice can convince the kernel she is Bob, then every ACL protecting Bob's files becomes irrelevant. A perfect lock with a broken key check is useless. The stronger the lock, the more catastrophic the impersonation.

The resolution

Before the kernel can enforce access permissions, it must establish a verified identity through Authentication Factors — independent channels of proof that only the real subject can satisfy.

💡
The two separate halves of security: Authentication establishes identity (L23). Authorization decides what that identity may do (L22). Both must be correct. A failure in either invalidates the whole model.
Authentication precedes authorization
🔐 Analogy 1 · The Secret Password, The Safe Key, and The Fingerprint

Three ways to prove who you are

The setup

Proving who you are down at a secure facility relies on three core human vectors. The security industry calls them authentication factors — and the strongest systems combine more than one.

Factor 1 · Knowledge

Something you know — a typed combination password, a memorized PIN, a secret phrase. Only you (ideally) know it. If someone else learns it, your identity is compromised.

Factor 2 · Possession

Something you have — a physical brass key, an access fob token, a smartphone with an authenticator app, a hardware security key like a YubiKey.

Factor 3 · Inherence

Something you are — your physical fingerprint pattern, your iris geometry, your facial structure, your voiceprint. Biologically bound to you.

The key observation

Notice that knowledge and possession factors share a critical property: they can be replaced. A leaked password can be reset. A stolen key fob can be revoked and reissued. This is not true for biometrics.

The irreversibility problem

If your fingerprint database is compromised — if someone manages to steal the template used to verify you — you cannot issue yourself new fingers. This is the unalterable systemic vulnerability the lecture asks us to identify.

The reason MFA exists

Because each factor fails differently, combining two different categories means an attacker must defeat both simultaneously. A phished password (knowledge) is useless without the hardware key (possession).

💡
Cross-factor synergy: the strongest systems combine factors that fail in unrelated ways. Two knowledge factors (password + security question) is not MFA — it's the same category twice.
🔗 Analogy 2 · Pure Technical — SHA-256 One-Way Engine vs. Biometric Vector Reader

Two mechanisms. Two very different guarantees.

The software side

Software credential checks run a string through an arithmetic compression function to match a database key. This is a one-way hash — the same input always produces the same output, but you cannot go backwards from the output to the input.

The biometric side

Biometric scanners translate analog organic geometric structures into static data signatures. A fingerprint reader produces a template — a small set of numeric feature points extracted from the ridge pattern. Verification compares templates, not the raw fingerprint.

The fundamental asymmetry

A hash is deterministic: same password, same hash (given the same salt). A biometric template is fuzzy: the same finger pressed twice produces slightly different readings, so verification is a similarity threshold, not an equality test.

💡
Why this matters: a hash can be compared with cryptographic certainty (bit-identical or not). A biometric template must be compared with a statistical tolerance — which means someone else's fingerprint might occasionally match yours if the threshold is loose.

📖 Core Breakdown · The Three Authentication Factors

Every credential belongs to exactly one category

The formal taxonomy

Before the kernel can enforce access permissions, it must establish a verified identity through Authentication Factors. Every mechanism in the field falls into one of three categories:

Knowledge · something you know

A typed combination password, a memorized PIN, a secret question's answer. The proof is information held in your head. If someone learns it, they can impersonate you.

Possession · something you have

A physical brass key, an access fob token, a smartphone with an authenticator app, a YubiKey. The proof is a physical object in your possession. If it's stolen, they can impersonate you (until you revoke it).

Inherence · something you are

Your physical fingerprint pattern, your iris geometry, your facial structure, your voiceprint. The proof is a biological trait. If it's compromised, it cannot be reset.

The three categories
📖 Core Breakdown · Password Model + Salted Hash

Never store the password. Store a salted hash.

The rule

Passwords represent "something you know." To prevent local storage theft, modern kernels never save plaintext characters. Instead, they run inputs through a one-way mathematical function appended with a random string (Salted Hash).

What a hash gives you

A cryptographic hash is a one-way function: easy to compute in the forward direction, infeasible to reverse. From the hash, an attacker cannot recover the original password in any practical time. The system never needs to know your password — only whether the hash of what you typed matches the stored hash.

Why salt matters

If two users both have password hunter2, they'd produce the same hash. An attacker could pre-compute a giant table (a rainbow table) mapping every common password to its hash, then instantly reverse any leaked hash.

Adding a random salt — unique per user — makes every hash different, even for identical passwords. Rainbow tables become useless.

💡
The exact definition: a salted hash appends a random sequence of characters to a user password before passing it through a cryptographic one-way hashing function, specifically to neutralize dictionary and rainbow-table lookup attacks.

🧪 Live Demo — Where Linux Stores Password Hashes

The $algorithm$salt$hash format

Live · /etc/shadow on a real system
user@box — sudo cat /etc/shadow
$ sudo cat /etc/shadow | head -5
What /etc/shadow is

A root-only file containing each user's password hash, never the password itself. Mode bits are typically 640 root:shadow — the ACL from L22 protects the file, so only root (or the shadow group) can read it.

The format

$6 — algorithm (SHA-512 crypt)
$salt — the per-user random salt
$hash — SHA-512(salt + password)
:fields — aging, expiry, etc.

What it tells you

A leading * or ! means "no password / locked account" — used for service accounts that should never log in interactively.

💡
The design lesson: /etc/passwd used to hold the hash — but that was readable by everyone. Shadow moved the hash to a root-only file. Same pattern as L22: tighten the ACL on the sensitive resource.
📖 Core Breakdown · Why Salt Defeats Rainbow Tables

Same password. Different hash. Every time.

Without salt

If Alice and Bob both have password password123, they produce the same hash. An attacker who pre-computes a rainbow table — mapping millions of common passwords to their hashes — can reverse both accounts at once from a single lookup.

With salt

Each user gets their own random salt, prepended to the password before hashing. Now the same password yields two completely different hashes. The rainbow table an attacker pre-computed no longer works — they'd have to precompute one table per salt, which is economically impossible.

Why salts are safe to store

The salt is stored in plaintext alongside the hash. That's fine — its job isn't secrecy. Its job is uniqueness: ensuring every user's hash computation uses a different input, even for identical passwords.

💡
Think of it like this: a hash is like a padlock whose key is the password. Salt is like putting a unique stamp on each lock so that even identical keys open differently-numbered locks. An attacker's skeleton key works on one lock, not all of them.

📖 Core Breakdown · Biometric Authentication

"Something you are" — and the reset paradox

The model

Biometrics represent "something you are" — a biological trait unique to you. Fingerprint ridge patterns, iris geometry, facial structure, voiceprints, gait, even heartbeat patterns. The scanner reads the trait, extracts a template, and compares it to a stored one.

The verification mechanism

Unlike a password hash (deterministic), biometric verification is probabilistic. Two scans of the same finger never produce bit-identical templates — small variations in pressure, angle, moisture, and sensor noise make every reading unique. The system uses a similarity threshold: if the match score exceeds a configured value, access is granted.

The unalterable vulnerability

While passwords can be leaked, they can easily be altered or reset. Biometric traits can never be "reset" if compromised — this permanently changes the baseline risk calculations of a secure system topology.

💡
The key insight: a leaked password can be changed in 30 seconds. A leaked fingerprint cannot be changed — ever. If someone copies your biometric template, they carry a permanent key that you can never revoke. This is the unalterable systemic vulnerability.
The reset paradox
📖 The Unalterable Vulnerability · Password vs. Biometrics

Both designs have one unalterable flaw

The two failure modes side by side
PASSWORD · THE UNALTERABLE FLAW
Phishability. No matter how strong the password is, the user can always be tricked into typing it into the wrong window — a fake bank login page, a malicious proxy, a lookalike app. Once phished, the attacker has the password in cleartext.

What can be done: rotate the password (attacker loses access), use MFA (phishing one factor isn't enough), and educate the user.
What cannot be done: prevent every phish. The flaw is inherent to the knowledge channel — users must "know" the secret, and knowledge can be extracted.
BIOMETRIC · THE UNALTERABLE FLAW
Irreversibility. If the biometric template database is breached — or if a sensor is spoofed and the attacker captures a high-quality image of your face — the trait is compromised forever. There is no password reset for your own body.

What can be done: store derived templates (cancelable biometrics), use liveness detection, keep the biometric entirely on-device (e.g. TPM).
What cannot be done: reset the underlying trait. Once your fingerprint is "out," it's out.
Why this is called "unalterable"

Every authentication factor fails. That's not the problem. The problem is what happens after the failure. Knowledge and possession factors can be swapped for fresh ones; inherence cannot. This is a permanent asymmetry.

The mitigation pattern

For passwords: MFA + password manager + phishing-resistant hardware keys
For biometrics: on-device templates + cancelable biometrics + liveness detection + treat biometrics as a convenience, not the sole factor

The honest conclusion

Neither model is "more secure." They fail differently. The strongest systems use biometrics as a possession-equivalent on a trusted device (e.g. Windows Hello, Touch ID, Android BiometricPrompt), not as the sole authenticator.

💡
The exam answer: "Password's unalterable flaw is phishability — mitigated by rotation and MFA. Biometric's unalterable flaw is irreversibility — mitigated by on-device storage and cancelable templates, and by never using biometrics as the sole factor."
🧪 Live Demo — What Happens When Passwords Aren't Hashed

A database leak. Every password. Instantly.

Live · Simulated plaintext database leak
user@box — database breach simulation
$ sqlite3 leaked.db "SELECT * FROM users"
The vulnerability

When a user authenticates with a plaintext password, a local database breach exposes the target vector to dictionary attacks if left unhashed. Every stored password is readable in cleartext — and users reuse passwords, so a leak here becomes a leak everywhere.

Why dictionary attacks work

Because humans choose weak, common, or predictable passwords. An attacker with a plaintext database doesn't need to "crack" anything — the passwords are right there. They can immediately try those same credentials on email, social media, banking, and cloud accounts.

The fix (recap from slide 08)

Never store plaintext. Use a slow, memory-hard hash (bcrypt, scrypt, Argon2) with a per-user salt. Even if the database leaks, an attacker faces an economically infeasible computational task per account.

💡
The practical example from the source: "When a user authenticates using a plaintext password string, a local database breach exposes the target vector to dictionary attacks if left unhashed." That's exactly what we're showing — the wrong way.
🧪 Live Demo — Windows Hello: Hardware-Locked Biometric Auth

The right way to use biometrics

Live · Windows Hello sign-in flow
windows@hello — sign-in flow
👋 Windows Hello · face recognition
What Windows Hello does

Windows Hello converts local fingerprint or facial scans into a localized hardware-locked cryptographic signature key. The biometric template never leaves the device — it's stored in the TPM (Trusted Platform Module) chip and cannot be extracted, even by an attacker with root on the OS.

The signature — not the biometric

The OS doesn't verify your fingerprint directly. Instead, the TPM uses your biometric match to unlock a cryptographic private key. The OS authenticates by verifying a signature from that key. Stolen biometric templates from a server can't be replayed because there is no server-side template — it's all local.

Why this is the correct design

1. Template stays local — never sent to a server
2. TPM is tamper-resistant — HW never exposes the key
3. Non-replayable — signatures can't be replayed
4. Fallback exists — PIN / password still works if HW fails

💡
The design pattern: this is called hardware-backed biometric authentication. The biometric is a convenience layer for unlocking a private key — not the authentication proof itself. The proof is always the signature. The unalterable vulnerability is contained.
📖 Multi-Factor Authentication — Combining Categories

Two different categories. Not two of the same.

The definition

Multi-Factor Authentication (MFA) requires a user to validate two or more distinct authentication categories before granting entry access. "Distinct" is the key word — the categories must be different.

What counts as MFA

✓ password + phone code (know + have)
✓ password + YubiKey (know + have)
✓ password + fingerprint (know + are)
✓ smart card + PIN (have + know)

What does not count as MFA

✕ password + security question (know + know)
✕ password + PIN (know + know)
✕ two fingerprints (are + are)
✕ SMS code + email code (have + have)

💡
Why distinctness matters: if both factors are the same category, defeating one attack defeats both. Two knowledge factors both fall to phishing. Two possession factors both fall to a stolen bag. Only different categories require the attacker to defeat two unrelated attack surfaces simultaneously.

🛑 Three Student Pitfalls

What beginners get wrong about authentication

PITFALL 01
"Hashing is the same as encryption"
They're opposites. Encryption is reversible — with the right key, you get your input back. Hashing is one-way — no key, no reverse, ever. If someone says "we encrypt passwords," they're either using the wrong word or storing something reversible — and that's a critical vulnerability. Passwords should be hashed, not encrypted.
PITFALL 02
"Biometrics are more secure than passwords"
They're not "more secure" — they're differently secure. Biometrics can't be phished remotely (good), but they can never be reset (bad). Passwords can be phished (bad), but can be reset (good). Real systems treat biometrics as a convenience layer for unlocking a hardware key — not as the sole authentication factor. Windows Hello does this correctly; using fingerprints as a server-side password replacement does not.
PITFALL 03
"MFA means two passwords"
No — MFA requires distinct categories. Password + security question = two knowledge factors = not MFA. Password + PIN = two knowledge factors = not MFA. The point of MFA is that the two proofs fail in unrelated ways. Two knowledge factors both fall to phishing. You need knowledge + possession (password + phone), or knowledge + inherence (password + fingerprint), or possession + inherence (hardware key + fingerprint).

⚠️ The SMS warning

SMS-based OTP is MFA on paper only. It's a possession factor — but the possession is your phone number, which can be stolen by SIM-swap attacks or intercepted by hostile carriers. Industry recommendations (NIST SP 800-63B) actively discourage SMS for high-security systems. Prefer hardware tokens (FIDO2) or app-based TOTP where possible.

💡
Try this at home: check your bank's 2FA options. If it offers "SMS only," try to upgrade to TOTP or a hardware key if available. If it doesn't offer any MFA at all, that's a strong indicator the security team hasn't thought about the threat model in this lecture.

🌉 The Exploit Question — A Bridge to L24

Authentication failures open the door for exploitation

The link L23 → L24

A failure to secure stored authentication keys allows rogue threads to hijack system control streams. If an attacker can extract password hashes, forge session tokens, or replay biometric signatures, they've already bypassed every access check L22 could impose.

The exploit that follows

L24 opens with the classic stack buffer overflow — a memory-safety bug that lets an attacker overwrite a return address and redirect execution to code they control. Where does the attacker get that code? Often from stolen credentials, embedded shellcode, or a hijacked authenticated session.

The pattern across L22–L24

L22 — defines what's allowed (the policy)
L23 — establishes who's asking (the identity)
L24 — exploits where either can break (the attack)

💡
Real-world chain: phishing (L23) → stolen password → remote shell → stack buffer overflow (L24) → privilege escalation → full system compromise. Every layer of the security model exists because the layer below it can fail.

🏆 Grand Summary — L23 Key Takeaways

Four things to walk out with

01

Authentication is the first step, not the last. Access control (L22) assumes we already know who's asking. Authentication (L23) establishes that identity via Authentication Factors: something you know, something you have, or something you are.

02

Passwords must never be stored in plaintext. Modern systems run them through a salted one-way hash — random per-user salt + cryptographic hash. This neutralizes rainbow tables and makes leaked databases economically infeasible to crack.

03

Each factor has an unalterable flaw. Passwords are phishable (mitigated by MFA + rotation). Biometrics can never be "reset" if compromised (mitigated by on-device storage + cancelable templates + never using them as the sole factor).

04

MFA means distinct categories. Password + security question is not MFA — it's two knowledge factors, both phishable. Password + phone, password + hardware key, password + fingerprint are MFA. The whole point is that the two factors fail in unrelated ways.
